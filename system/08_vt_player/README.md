# 08 · Metal 滤镜视频帧处理

> 让 GPU 并行处理 150 帧 640×360 测试图案，逐帧执行饱和度滤镜，再从 GPU 回读结果验证正确性。读完本篇你能掌握用 Metal 逐像素处理视频帧的完整闭环：纹理上传、内核派发、结果回读与验证。

## Background

视频处理里的滤镜、调色、降噪，本质都是同一件事：对一帧图像的每个像素做一遍相同的小运算。以饱和度为例，就是"把每个像素颜色偏离灰色的部分放大两倍"。

在 GPU 通用计算普及之前，这类处理通常在 CPU 上做：写一个双重循环逐像素读写，或者用向量函数库一次算几个像素。

痛点出现在实时场景。一帧 1080p 图像约 200 万像素，30 fps 的视频意味着每秒要处理约 6000 万像素。CPU 逐像素循环即使吃满几个核心也未必跟得上帧率，还会占用处理器、抬高功耗，拖慢同机的其他任务。

GPU 正是为"海量数据做同一种简单运算"设计的：它内部有数千个小计算单元，可以同时各算一个像素。Apple 平台上直接驱动 GPU 的底层接口是 Metal，把逐像素滤镜放进视频管线时，它就是标准工具。

## What

Metal 是 Apple 平台的底层 GPU 编程框架，让开发者直接向 GPU 提交计算和绘制任务。本实验用的是其中最基础的一种：compute 内核（kernel，一段跑在 GPU 上、由大量线程同时执行的小函数），对每帧图像做逐像素运算。

可以把整个流程想象成工厂质检流水线：CPU 把一帧图像（纹理，texture，即 GPU 内存里的一张二维像素数组）搬上流水线，GPU 给每个像素派一名工人，每人拿着同一份操作说明书（内核函数）处理自己负责的那个像素，处理完再搬回来。

但和真实流水线不同的是：GPU 的"工人"之间互不通信，每个像素的计算只依赖自己的输入。这个限制正是它能同时并行几十万份计算的原因。

## When to Use

典型场景（写"在做什么事"）：

- 给播放中的视频加实时滤镜或调色：每一帧都要在十几毫秒内处理完。
- 视频帧送 AI 模型前的预处理：缩放、归一化、色彩空间转换（把颜色的表示格式从一种换成另一种）。
- 相机取景器这类每秒几十帧的流水线中做逐像素小运算。

何时不用：只处理一张小图，或者写一次性脚本，CPU 几行循环更直接；想用现成滤镜效果而不自己写算法，用 Core Image（Apple 的高层图像处理框架）更省事。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CPU 循环 | 无需 GPU 知识，调试直观；并行度受核心数限制 | 像素少、一次性处理 |
| Accelerate / vDSP | CPU 上的向量化计算库（vDSP 是其中信号与图像子库），仍是 CPU 在算 | 想留在 CPU 又要性能 |
| Core Image | 滤镜现成、可拼接成处理链 | 需求能用现成滤镜组合满足 |
| Metal compute | 自己写逐像素逻辑，控制最细、管线开销最小 | 自定义算法，或嵌入视频管线 |

## How It Works

一次实验分四步，与源码 `vt_player.swift` 一一对应。

1. 运行时编译内核：`makeLibrary(source:)` 把一段 Metal 着色语言（MSL，语法接近 C++ 的 GPU 编程语言）源码编译成 GPU 函数，再包成 compute pipeline state（PSO，管线状态对象，即"内核加固定配置"的编译产物）。
2. CPU 生成测试帧并上传：`makeTestFrame` 用正弦公式在 CPU 填一张 640×360 像素数组，`tex.replace(region:...)` 把它拷进 GPU 纹理。
3. 每帧派发一次 GPU 计算：命令缓冲（command buffer，装着一串待执行 GPU 命令的容器）里开一个计算编码器（encoder，负责往命令缓冲里填写具体命令的对象），设置内核、两张纹理和饱和度参数，`dispatchThreadgroups` 提交，`waitUntilCompleted` 等 GPU 做完。
4. 抽帧回读验证：每 30 帧用 `getBytes`（把 GPU 纹理的一个区域拷回 CPU 内存）读出坐标 (10,10) 的一个像素，非零即通过。

核心是下面这个内核，逐行看它为什么这样写：

```metal
kernel void saturate(texture2d<half, access::read> src [[texture(0)]],
                     texture2d<half, access::write> dst [[texture(1)]],
                     constant float& sat [[buffer(0)]],
                     uint2 gid [[thread_position_in_grid]]) {
    half4 c = src.read(gid);
    half avg = (c.r + c.g + c.b) / 3.0h;
    dst.write(half4(half3(avg) + (c.rgb - half3(avg)) * half(sat), 1.0h), gid);
}
```

- 一读一写两张纹理：`src` 只读、`dst` 只写，数据方向一目了然，也避免同一纹理边读边写的相互干扰。
- `texture2d<half, access::read>`：half 是 16 位浮点数。图像以 rgba8Unorm 格式（每通道 8 bit 无符号整数）存储，内核读取时会自动转成 half4，不需要手工转换。
- `gid [[thread_position_in_grid]]`：每个 GPU 线程拿到自己在整个网格里的二维坐标，正好当像素坐标用。
- 饱和度公式 `avg + (c.rgb - avg) * sat`：sat 等于 1 时图像不变，大于 1 增强，小于 1 趋向灰色。
- 派发网格按 `ceil(宽/16) × ceil(高/16)` 计算：360 除以 16 除不尽，最后一行线程组（threadgroup，GPU 一次一起调度的一小队线程）会越出图像下缘。完整源码在内核开头有一行边界检查，gid 超出图像范围直接 return；上面代码为突出主体省略了它。

你在输出里看到的 `860 fps`，就来自第 3 步的循环：每帧一次"上传 → 计算 → 等待"，循环 150 次后用总耗时折算。

## Pitfalls & Q&A

坑：回读输出纹理得到全 0 或旧数据。现象是 `getBytes` 读出的像素永远是 0。原因是 GPU 命令异步执行，提交后立刻回读，计算可能还没跑。

解法是 `commit` 之后先 `waitUntilCompleted()` 再 `getBytes`——shared 存储模式（CPU 与 GPU 共享同一块内存的模式）的纹理没有自动的 GPU 到 CPU 同步，必须显式等待。源码里就是这么做的。

Q：为什么网格按 16×16 切？线程组是 GPU 调度的基本单位，16×16 共 256 个线程是常见选择；网格用 ceil 包住整幅图，宁可多派线程也不能漏像素。

Q：150 帧为什么只验证 5 帧？全量回读要把全部 150 帧的像素从 GPU 拷回 CPU，开销大；每 30 帧抽一个像素（`frame % 30 == 0`）足以确认管线接对了。

Q：同一帧数据在 CPU 和 GPU 之间来回搬，不是开销吗？是。实验里每帧都在 CPU 生成再上传，是为了让测试自包含；真实视频管线里帧数据通常本来就在 GPU 侧（例如解码器直接输出 GPU 纹理），不需要这一步拷贝。
