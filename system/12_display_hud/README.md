# 12 · 帧率 HUD：帧时间曲线画进 Metal

> 用环形缓冲记录最近 120 帧的帧时间，并按"场景 + HUD"两个 Pass 的设计准备曲线渲染管线。读完本篇你能掌握帧时间的测量方法、在 GPU 里画折线（lineStrip）的写法，以及为什么定位卡顿要看帧时间而不是帧率。

## Background

图形程序变卡时，开发者首先要知道"卡在哪几帧、卡多少毫秒"。新手的常用手段有两种：往渲染循环里 print 日志，或用 Xcode 自带的性能分析器 Instruments（可定位到函数和 GPU 阶段的专业工具）。

两种手段都有代价。日志要事后翻，而且打印本身占时间，循环里打多了程序反而更慢（观察者效应）；Instruments 功能全但流程重，只是想快速确认"这次改动有没有引入卡顿"时太绕。

游戏与图形开发因此流行一种轻量做法：把每帧耗时画成一条叠加在画面角落的小曲线，卡顿在屏幕上一眼可见，改一行代码立刻能看到曲线变化。这条曲线层就叫 HUD（Heads-Up Display，平视显示，借自飞行仪表盘，指叠加在主画面上的信息层）。

## What

帧率 HUD 是叠加在渲染画面上的性能信息层。本实验画的是"最近 120 帧的帧时间曲线"——帧时间指画完一帧花了多少秒，数据存进一个环形缓冲（ring buffer，固定大小数组，写满后从头覆盖的循环结构）。

看帧时间比看帧率更能定位卡顿。帧率 60 fps 与 59 fps 在数字上几乎没差别，但一帧 16.7 ms 与一帧 100 ms 的尖刺在曲线上一目了然——平均值会把尖刺藏起来，曲线不会。

可以把 120 个帧时间槽想成传送带上的 120 个格子：每来一帧就把最老的格子换成本帧耗时，曲线随之向左滚动。

但和传送带不同的是：格子里的数字更新后不会自动变成曲线。本实验的设计分两个渲染 Pass（pass，一次"清屏—画—存"的渲染过程）：Pass1 画场景，Pass2 在其上叠加 HUD 曲线；两个 Pass 的管线都已建好，但当前源码只执行了 Pass1（详见 How It Works 与 Pitfalls）。

## When to Use

典型场景：

- 调优渲染循环：改动一行代码后，立刻从曲线上确认帧耗时有没有变化。
- 演示与教学：向别人直观展示"掉帧"长什么样。
- 测试构建里内置性能自检画面，跑自动化时顺带盯曲线。

何时不用：只需要一个平均帧率数字时，打一行日志更省事；要定位卡顿根因（哪个函数、哪个 GPU 阶段），直接用 Instruments，HUD 只负责"发现"不负责"定位"。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| print 日志 | 零成本接入；事后看，有观察者效应 | 偶尔确认平均帧率 |
| 帧率 HUD（本实验） | 实时逐帧，尖刺一眼可见 | 调渲染循环时的快速迭代 |
| Instruments | 能定位到函数与 GPU 阶段 | 追查卡顿根因 |

## How It Works

对应源码 `display_hud.swift`，分四步。

1. 记录帧时间：每次刷新回调里 `dt = now - lastTick` 算出本帧距上帧的秒数，写入 `frameTimes[frameIdx % 120]`。取模让写指针循环，120 格在 60 fps 下约等于最近 2 秒。
2. 场景 Pass：全屏三角形铺满窗口，片元颜色 `0.1 + 0.1*sin(time)` 随时间缓慢脉动。
3. HUD 管线：单独编译一对顶点着色器（vertex shader，算出每个顶点在屏幕上位置的 GPU 程序）与片元着色器（fragment shader，为每个像素算颜色的 GPU 程序），负责把 120 个帧时间映射成屏幕上的折线，代码见下。
4. （设计中的）HUD Pass：在场景编码器结束后再开一个渲染编码器叠加曲线。

HUD 着色器是整个设计的核心（`HudVOut` 是顶点输出的数据结构）：

```metal
struct HudVOut { float4 pos [[position]]; };
vertex HudVOut hud_vs(device const float *frameTimes [[buffer(0)]], uint vid [[vertex_id]]) {
    float x = float(vid) / 119.0 * 2.0 - 1.0;
    float ms = frameTimes[vid] * 1000.0;
    float y = clamp(ms / 16.67 * 2.0 - 1.0, -1.0, 1.0);
    return { float4(x, y, 0, 1) };
}
fragment float4 hud_fs() {
    return float4(0.2, 1.0, 0.3, 1.0);
}
```

- `device const float *frameTimes`：帧时间数组直接以指针形式给顶点着色器读（device 地址空间，即 GPU 可直接访问的内存）。数据每帧都在变，不预拷顶点缓冲是最省事的做法。
- x 坐标：`vid / 119 * 2 - 1` 把 120 个采样点均匀铺满画面宽度。
- y 坐标：16.67 ms 是 60 fps 的单帧预算，映射到 y=1；帧耗时越接近预算越靠上，超过预算的帧被 clamp 顶格。所以曲线整体趴在顶格，就说明帧帧超预算。
- `hud_fs` 恒返回亮绿色：曲线单色，够用。

当前源码缺的一环在 `tick`：它只设置了场景管线并画了全屏三角形，`hudPipeline` 创建后从未被任何渲染命令引用，`frameTimes` 也在持续更新但无人消费。

按 `hud_vs` 的设计，接上曲线需要第二个渲染编码器：设置 `hudPipeline`，把 `frameTimes` 绑定为 buffer(0)，以 lineStrip（折线拓扑，相邻顶点两两连成线段）提交 120 个顶点（`vertexStart: 0, vertexCount: 120`）。

接上后，帧时间的波动就以绿色曲线叠在场景上。

## Pitfalls & Q&A

坑：窗口里看不到 HUD 曲线。现象是只有蓝色背景在明暗变化。原因是当前源码的 `tick` 只执行了场景 Pass，HUD 管线已建好但未接入渲染命令。解法是按 How It Works 末尾的说明补上第二个 Pass（设管线、绑 buffer(0)、lineStrip 画 120 顶点）。

坑：开了 HUD 帧率反而变低。现象是叠加曲线后帧耗时上升。原因是测量与绘制本身消耗 CPU 时间。解法是保持 HUD 逻辑轻量——本实验每帧只做一次减法和一次数组写入；追根因时换用 Instruments。

Q：为什么盯帧时间而不是帧率？帧率是平均值，几秒一次的 100 ms 卡顿帧会被平均抹平；帧时间曲线逐帧呈现，尖刺直接可见。y 轴的 16.67 ms 预算线就是为"一眼看出超标"设计的。

Q：为什么缓冲是 120 帧？60 fps 下约为最近 2 秒，滚动节奏适合肉眼观察。需要更长历史时改环形缓冲大小即可，着色器里的 `119.0` 要同步改成"长度减一"。
