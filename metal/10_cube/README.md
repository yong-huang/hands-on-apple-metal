# 10 · 3D 立方体：透视投影与深度测试

> 把一个六色立方体画进 3D 世界，要回答两个问题：3D 点落在屏幕哪里（投影），谁挡住谁（深度）。本实验用透视投影矩阵、深度缓冲（逐像素记录离相机远近的一块内存）和一台绕物体转的相机搭出最小 3D 场景。读完本篇，你能掌握实时 3D 渲染共用的骨架——MVP 变换加深度测试。

## Background

二维绘图时代，颜色由公式或贴图逐像素决定，"谁在前"这个问题不存在——画的本来就是平面。一旦进入 3D，一个立方体是 12 个三角形，直接画出来是一团乱色：后面的面会盖住前面的面，因为没有机制判断遮挡。

靠安排绘制顺序也解决不了：物体互相穿插、相机角度任意时，"先画远的"没有统一的次序可排。要让立方体"像"立方体，必须回答两个新问题——3D 点落在屏幕哪里（投影），以及谁挡住谁（深度）。

这两个机制由此成为所有实时 3D 的地基：透视投影（近大远小的成像方式）把 3D 空间压缩到屏幕，深度缓冲逐像素记录"目前谁离相机最近"。光照、阴影等效果都建立在这副骨架上。

## What

本实验的画面由两套机制合成。MVP 矩阵（Model-View-Projection，模型、视图、投影三个矩阵的合称）负责把立方体的 36 个顶点变换到屏幕位置；深度缓冲负责在像素落屏时比较先后，留下更近的。

一句话心智模型：**MVP 决定"在哪"，深度缓冲决定"谁在前"**。

可以把深度缓冲想象成每像素一格的"擂台"：新片元（候选像素）报出自己的深度（离相机的远近），比台上已有的更近才留下并刷新纪录。但和擂台不同的是，这场比较由硬件在每帧几十万个像素上并行完成，"远近"是相对相机的投影距离。

## When to Use

典型场景——在做什么事的时候会用到：

- 任何 3D 物体上屏：模型查看器、游戏里的角色与场景物体，都需要投影矩阵把它们落到屏幕。
- 多物体且有遮挡的场景：深度缓冲让"谁挡住谁"与绘制顺序无关。
- 相机运动：绕物体旋转、推进拉远，本质只是每帧改一次视图矩阵。

何时不用：

- 纯 2D 界面与图案：不需要透视与深度，正交投影（不产生近大远小、所有方向平行投影的方式）或直接用 UV 更简单。
- 场景简单到只有几块平面：不用深度缓冲也能靠绘制顺序排好，省一份深度内存。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| SpriteKit | 2D 场景框架，自带动作与物理，无需投影矩阵 | 2D 游戏与动画 |
| SceneKit | 现成场景图、相机与光照，不用手写矩阵 | 快速搭 3D 原型 |
| OpenGL ES | 跨平台老 API；z 范围约定与 Metal 不同 | 维护历史跨平台项目 |
| 手写 MVP + 深度（本实验） | 逐层控制矩阵与渲染状态 | 学习渲染管线（GPU 从顶点到像素的完整处理流程）本质、需要定制渲染时 |

## Quick Start

前置：macOS + Xcode（本实验基于 Metal，Apple 的底层 GPU 图形 API）。运行：

```bash
./cube.sh               # 一条龙：build → observe → clean
AUTO_QUIT=6 ./cube.sh observe   # 6 秒自动退出
```

控制台真实输出：

```
立方体顶点数: 36（6 面 × 6 顶点），深度格式 depth16Unorm
```

窗口中可见六色立方体绕 Y 轴缓慢旋转。验证方法：旋转时近面始终遮挡远面——关闭深度状态（注释 `setDepthStencilState` 一行）重跑，画面立刻"内外翻转"。

这 36 个顶点从哪来：6 个面 × 每面 2 个三角形 × 3 顶点。面由 4 个角点加面色定义，法线（垂直于表面的方向向量，光照计算要用）由两条边向量叉积算出。不含索引时顶点有重复——8 个角点被相邻面反复书写；换索引缓冲（存顶点编号、复用顶点数据的缓冲）能减少重复，取舍见文末问答。

每帧更新与绘制的代码来自 `cube.swift`。这段在做什么：算矩阵、传参数、开深度测试、发起绘制：

```swift
// 每帧：角度→矩阵→Uniform 缓冲（16 个 float）
var uni = Uniforms(mvp: proj * viewM * model)
memcpy(uniformBuffer.contents(), &uni, MemoryLayout<Uniforms>.stride)
encoder.setDepthStencilState(depthState)          // 深度测试开启
encoder.drawPrimitives(type: .triangle, vertexStart: 0, vertexCount: 36)
```

- 第 1 行：把三份矩阵相乘得到 MVP，装进 uniform（CPU 传入、所有顶点共享的只读参数）结构体。
- 第 2 行：把结构体拷进 GPU 可见的 uniform 缓冲。
- 第 3 行启用深度测试状态，第 4 行提交 36 个顶点的三角形绘制。

为什么每帧只更新 Uniform：矩阵 64 字节，替换成本几乎为零；重传 36 个顶点则浪费——能只换参数就不动几何。

## How It Works

数据流：顶点缓冲（GPU 里存顶点数据的内存块）与 MVP 矩阵汇入顶点着色器（vertex shader，运行在 GPU 上、对每个顶点执行一遍的小程序）`vertex_main`，算出每个顶点的屏幕位置；三角形光栅化（把三角形覆盖的区域拆成一个个候选像素）后，每个片元经深度测试决定去留。

**MVP 三步（乘法从右往左作用）**：

- 模型矩阵：负责自转。
- 视图矩阵：把相机（观察位置与朝向，本实验放在 z=3.2 看原点）摆好。
- 投影矩阵：按 60° 视锥（相机能看到的空间范围，形如截掉顶尖的锥体）压缩。

矩阵全部用 simd（Apple 平台自带的向量/矩阵数学框架）手写：`perspective` / `lookAt` / `rotationY`，不依赖第三方库。

**透视投影矩阵做了什么**：把视锥体压缩成标准立方体——x/y 除以深度产生近大远小，z 归一到 [0,1] 供深度测试使用。你在输出里看到的 `depth16Unorm`（16 位归一化深度格式）就是为存这个 z 准备的。

**深度测试链路（四步）**：

- view 声明深度格式 `.depth16Unorm`。
- 管线描述符声明 `depthAttachmentPixelFormat`（必须与 view 一致，否则创建管线直接失败）。
- 渲染过程（render pass，一次完整的渲染提交）的深度附件（存放每像素深度值的缓冲区）以 clear=1（清成最远值）开始。
- `DepthStencilState` 设 `less` 比较、写入深度。

验证方法里看到的"内外翻转"，就是这条链路被掐断后的样子。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- 立方体整体消失且无报错（常见于从 OpenGL 抄投影代码）。原因：Metal 裁剪空间（变换后的标准化坐标系，范围外的内容被丢弃）的 z 范围是 [0,1]，OpenGL 是 [-1,1]；GL 风格投影把 z 变换出范围，三角形被整体裁剪。解法：投影矩阵按 Metal 约定生成。
- 前后关系随机，后画的面盖住先画的面。原因：忘了给 view 设深度格式，深度附件不存在，深度测试无从生效。解法：设置 `depthStencilPixelFormat` 并保持管线描述符一致。
- 立方体"消失"但几何无误。原因：MVP 乘法顺序写反，顶点被变换出裁剪空间。解法：保持 `proj * view * model`，乘法从右往左作用。

深入问答：

- **36 顶点还是 8 顶点 + 24 索引？** 每面需要独立法线/颜色时顶点不能共享——顶点复用与属性解耦是网格（组成模型的三角形集合）设计的核心权衡。
- **投影矩阵和深度格式有什么耦合？** 投影矩阵把 z 归一到 [0,1]，深度格式（如 `depth16Unorm`）就按这个范围存储比较值——两者约定必须配套，改动任何一个都要检查另一个。
