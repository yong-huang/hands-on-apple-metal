# 24 · 加载 OBJ 模型并渲染

> 之前的几何都是代码里手写的数组——真实世界的模型来自文件。
> OBJ 是最朴素的 3D 格式：纯文本、逐行可读、40 行代码就能写个解析器。
> 本实验从 cube.obj 一路喂到屏幕，打通"资产 → 渲染"的工程链路。

## 1. 为什么需要它

模型加载是所有 3D 引擎的第一道工序。OBJ 的 v/vn/f 三类行覆盖了顶点、法线、面索引的全部要素——手写解析器是理解"几何数据如何流动"的最快路径，也为之后接 glTF 等格式打下结构基础。

## 4. 核心概念

### 4.1 OBJ 三类行

```
v  -0.5 -0.5  0.5      顶点
vn  0  0  1            法线
f  1//1 2//1 3//1      面：顶点索引//法线索引（1-based）
```

斜杠是 OBJ 的"连接暗号"：`f v//vn` 表示"用这个顶点配这个法线"。

### 4.2 索引展开

OBJ 是索引几何（8 顶点被 12 个面复用），教学版直接展开成 36 个流式顶点喂给管线——与 04 的索引缓冲思想互为表里：省内存用索引，省代码用展开。

### 4.3 面法线的坑

OBJ 法线索引对应 vn 行；若模型不带 vn，需要按叉积现算——与 11 的做法一致。

### 4.4 易错点

- OBJ 索引 1-based，直接当数组下标会越界/错位。
- 路径解析：演示脚本以实验目录为 cwd，程序里做了 cwd 与可执行文件双路径兜底。

## 5. 关键 API 与字段

```swift
switch t.first {
case "v":  verts.append(SIMD3(Float(t[1])!, Float(t[2])!, Float(t[3])!))
case "vn": normals.append(SIMD3(...))
case "f":  // "1//1" → 索引对，各减 1 转 0-based
}
```

为什么 `Float(t[1])!` 敢强解：OBJ 数字行格式固定，格式错误本该在资产制作期暴露。

## 7. 深入要点

- **索引几何 vs 展开几何的取舍？** 索引省内存且利于顶点缓存；展开省一次间接寻址。流式管线常用展开起步。
- **OBJ 的局限性？** 无层级/动画/PBR 材质，多物体靠多文件——所以工业界转向 glTF。
- **模型加载的健壮性要点？** 格式校验、越界索引防御、法线缺失时的重算、坐标系差异（Y-up/Z-up）。
