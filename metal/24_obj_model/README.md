# 24 · 加载 OBJ 模型并渲染
> 真实世界的 3D 模型来自文件，不是代码里手写的数组。OBJ 是最朴素的 3D 模型格式：纯文本、逐行可读，40 行代码就能写个解析器。本实验从 cube.obj 一路喂到屏幕，打通"资产文件 → 解析 → GPU 缓冲 → 光照渲染"的工程链路。读完本篇你能看懂 OBJ 的行格式，并亲手把一个模型渲染出来。

## Background

在没有模型加载的渲染程序里，几何通常以顶点数组的形式硬编码在代码中。真实世界的模型来自建模软件导出的文件，所以每个 3D 引擎的第一道工序都是模型加载：读文件、验格式、转成 GPU 能吃的缓冲（buffer，GPU 显存里连续存放的原始数据区域）。

模型格式众多（FBX、glTF、USD 等），大多是二进制、带层级与动画，解析需要现成库。想理解"几何数据如何流动"，先被格式复杂度挡在门外——哪怕只是想把一个几百行的立方体文件画出来。

OBJ 是这条路上门槛最低的一站：它是 Wavefront 公司为建模软件定义的纯文本格式，只靠三类核心行就能描述一个静态网格（mesh，由三角形拼成的模型表面），逐行可读、手写解析器就能吃下。本实验用它打通"文件 → 解析 → 缓冲 → 屏幕"的完整链路，也为之后接 glTF 等工业格式打下结构基础。

## What

OBJ 文件是索引化的几何清单：`v` 行列顶点（构成三角形的空间坐标点）坐标，`vn` 行列法线（normal，垂直于表面的方向向量，光照计算要用），`f` 行列三角形——每个角写成 `顶点索引//法线索引`。

本实验用 Metal——苹果的 GPU 编程框架——手写一个最小解析器，只认 `v` / `vn` / `f v//vn` 三类行，把解析结果展开成 Metal 顶点缓冲，再走光照渲染画到屏幕。

cube.obj 的内容：8 个顶点、6 条法线、12 个三角形面（立方体 6 个正方形面，每面拆 2 个三角形）。

一句话心智模型：**OBJ = 索引化的几何清单，渲染前展开成流式顶点**。可以把 OBJ 想象成"零件目录 + 装配清单"：v/vn 行是零件目录（8 个顶点、6 条法线，每个有编号），f 行是装配单（12 个三角形，各自引用目录编号）。

但和真实产品目录不同的是：OBJ 的编号从 1 开始（1-based），而 Swift/Metal 的数组下标从 0 开始（0-based），读入后必须整体减 1。

## When to Use

这一节给判断力：什么时候选 OBJ 这条路，什么时候该换格式。

典型场景：

- 给自己的渲染程序喂真实资产：从建模软件导出 OBJ，验证管线能吃"真模型"而不是手写数组。
- 学习或原型：想看清几何数据从文件到屏幕的每一步，OBJ 是可全手写的最低门槛。
- 小工具之间交换静态网格：文本格式到处能读。

何时不用：

- 场景需要层级、动画或 PBR 材质（基于物理的材质系统，含粗糙度、金属度等参数）：OBJ 只存静态几何，这类需求用 glTF。
- 资产量大、加载性能敏感：二进制格式体积更小、解析更快。
- 不想手写解析器：苹果自带的 Model I/O 框架可直接加载 OBJ。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 代码内写死几何数组 | 零解析成本；改形状要改代码重编译 | 教学 demo、程序化图形 |
| OBJ + 手写解析器（本实验） | 纯文本好读好调；只覆盖顶点/法线/面的静态几何 | 学习几何数据流、加载简单静态模型 |
| Model I/O（苹果资产框架） | 直接加载 OBJ 等格式，功能全；格式细节被隐藏 | 工程里快速用资产 |
| glTF（JSON 文本加二进制缓冲的工业格式） | 支持层级/动画/PBR 材质；解析复杂度高 | 完整 3D 场景、引擎级资产管线 |

## Quick Start

前置条件：macOS 加 Xcode 的 Swift 工具链。在 `metal/24_obj_model/` 目录下运行：

```bash
./obj_model.sh               # 一条龙
AUTO_QUIT=6 ./obj_model.sh observe
```

控制台输出（真实输出）：

```
OBJ 解析: 8 顶点 / 6 法线 / 12 个三角形面
已上传 36 个展开顶点（12 个三角形）到 GPU
```

窗口显示带光照的旋转彩色立方体。验证方法：把 cube.obj 的某个面索引改错，画面立刻出现破面——数据驱动的渲染，改数据即改画面。

解析器的骨架在 `obj_model.swift` 的 `ObjParser` 里：

```swift
switch t.first {
case "v":  verts.append(SIMD3(Float(t[1])!, Float(t[2])!, Float(t[3])!))
case "vn": normals.append(SIMD3(...))
case "f":  // "1//1" → 索引对，各减 1 转 0-based
}
```

这段在做什么：逐行读文件、按空格切词；`v` 行存顶点坐标，`vn` 行存法线，`f` 行把 `1//1` 这样的角拆成索引对、各减 1 转成 0-based。注释行（# 开头）与其他标签一律忽略。为什么 `Float(t[1])!` 敢强解：OBJ 数字行格式固定，格式错误本该在资产制作期暴露。

## How It Works

按数据流展开：OBJ 的三类行长什么样、怎么展开成顶点、怎么被光照渲染。

**三类行。** cube.obj 的核心行长这样：

```
v  -0.5 -0.5  0.5      顶点
vn  0  0  1            法线
f  1//1 2//1 3//1      面：顶点索引//法线索引（1-based）
```

斜杠是 OBJ 的"连接暗号"：`f v//vn` 表示"用这个顶点配这个法线"。`f` 行的三个角就是一个三角形的三个角。

**索引展开。** OBJ 是索引几何——8 个顶点被 12 个面反复引用。本实验采用教学从简的展开策略：每个三角形输出 3 个独立顶点，12 个面共 36 个：

```swift
for (fi, face) in obj.faces.enumerated() {
    let color = palette[fi % palette.count]
    for k in 0..<3 {
        out.append(ModelVertex(
            position: obj.vertices[face.v[k]],
            normal: obj.normals[face.n[k]],
            color: color))
    }
}
```

为什么这样写：展开省去索引缓冲的间接寻址，管线直接吃流式顶点——与索引缓冲的思想互为表里：省内存用索引，省代码用展开（索引缓冲见 lab 04）。每个面从 6 色调色板取色（`fi % palette.count`），12 个三角形颜色可辨。

**法线的来源。** `face.n[k]` 引用的是 vn 行的法线索引。若某个角只写了顶点索引（如 `f 1 2 3`），本解析器退回第 0 条法线；若模型干脆不带 vn 行，就要按叉积（两条边向量叉乘得到垂直方向的运算）现算面法线——lab 11 的光照实验用的正是这个做法。

**光照渲染。** 顶点着色器（vertex shader，为每个顶点执行一次的 GPU 函数）用 mvp 矩阵（模型、视图、投影三个矩阵的乘积，把模型坐标一路变到屏幕空间）变换位置；

片元着色器（fragment shader，为每个屏幕像素执行一次的函数）算兰伯特漫反射：`diffuse = max(dot(法线, 光方向), 0)`，最终颜色 = 顶点色 × (0.25 + diffuse)——0.25 是环境光（ambient，无方向、处处存在的基础亮度）的底数。

这与 lab 11 的光照方程一致：换的只是几何的来源，渲染端不动。

**路径兜底。** 演示脚本把工作目录设为实验目录；程序同时尝试"当前目录"与"可执行文件旁"两条路径找 cube.obj，两条都找不到才报错。

## Pitfalls & Q&A

**数组越界或顶点整体错位。** 现象：渲染出的模型扭曲，或运行时越界崩溃。原因：OBJ 索引是 1-based，直接当数组下标用会越界（最大索引 = 元素数）或读错元素（整体偏 1）。解法：解析时统一减 1，转成 0-based 再存。

**光照看起来不对，所有面一个亮度。** 现象：立方体没有明暗面。原因：模型不带 vn 行时法线无从引用，本解析器会退回第 0 条法线，所有面共享同一方向。解法：加载后按叉积现算面法线，或导出模型时勾选"包含法线"。

**报"找不到 cube.obj"。** 现象：程序初始化失败退出。原因：从别的目录启动程序，工作目录不是实验目录，文件相对路径失效。解法：用演示脚本启动；自己嵌代码时保留"当前目录 + 可执行文件旁"的双路径兜底。

**索引几何和展开几何怎么选？** 索引几何省内存，且 GPU 的顶点缓存会复用最近处理过的顶点；展开几何省一次间接寻址、代码最短。流式管线常用展开起步，网格大了再换索引缓冲。

**OBJ 的局限是什么？** 无层级、无动画、无 PBR 材质，多物体靠多文件组织——所以工业界的资产管线转向 glTF。OBJ 的价值在"够朴素"：它是理解几何数据流动的最小标本，不是生产格式的终点。
