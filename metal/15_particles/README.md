# 15 · GPU 粒子系统：一万个粒子的 GPU 自治
> 把一万颗粒子的运动全部搬到 GPU 上自治：每帧一次 GPU 并行计算（成千上万个线程同时执行同一段函数）更新所有粒子的位置与速度，渲染阶段把它们画成点，CPU 只递交一个时间步长。读完本篇你能跑通"GPU 更新状态、GPU 自己画出来"的最小闭环，并学会判断哪类计算值得交给 GPU。

## Background

粒子特效（烟花、雨雪、火花）动辄上万个粒子。传统做法是把粒子做成 CPU 内存里的对象数组，游戏循环每帧遍历一次：读出位置、按速度推进、检查边界，再把新坐标交给显卡去画。

这个做法在上千粒子时开始撞墙：更新是单线程串行循环，一万个粒子就是一万个依次执行的浮点更新；状态又在 CPU 内存里，每帧还得把结果搬到显卡。粒子数继续上涨，帧时间就被这个循环吃掉。

GPU 有数千个小执行单元，擅长把"同一条规则"同时作用到海量数据上。自然的改造方向由此出现：把粒子状态搬进 GPU 显存，让 GPU 自己更新、自己渲染，CPU 每帧只递交一个时间步长。本实验就是这条路径的最小完整案例。

## What

本实验用 Metal——苹果的 GPU 编程框架（Swift 侧负责提交命令，GPU 上执行的函数用专门的类 C++ 语言编写）——实现一个 GPU 粒子系统。每个粒子只有两个二维向量：位置和速度，存放在 GPU 显存的两块缓冲（buffer，一块连续的原始数据区域）里。

- **compute 内核**（kernel，GPU 上成千上万个线程各自执行一遍的同一段函数）：每帧更新全部粒子的位置和速度。
- **渲染管线**（把顶点——即待画的空间坐标点——变成屏幕像素的固定处理流程）：把更新后的位置画成点。

一句话心智模型：**缓冲即世界状态，kernel 即物理定律**。可以把每个 GPU 线程想象成一个只管自己账本的记录员：编号 i 的线程只读写第 i 个粒子的位置和速度，互不干涉。

但和真实物理引擎不同的是：这里的更新是每帧一步的显式欧拉积分（按"位置 += 速度 × 时间步长"推进），没有粒子间碰撞、没有流体，物理正确性不是目标。

## When to Use

这一节给判断力：什么活适合用这个结构干，什么活不适合。

典型场景：

- 做烟花、雨雪、火花这类动辄上万粒子的特效：每个粒子独立、每帧用同一条规则更新。
- 想把一份数值模拟的结果直接画出来：compute 更新加 render 画点是最短路径，改规则立刻能从画面上看到效果。
- 验证某个数值算法在 GPU 上的行为：画面本身就是调试输出。

何时不用：

- 粒子只有几十到几百个：CPU 每帧循环更新毫无压力，普通数组加一个 for 循环更简单。
- 粒子之间有强交互（相互碰撞、流体、吸附）：需要专门的算法和线程间同步，"一线程一粒子"的结构覆盖不了。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CPU 循环更新 | 状态在 CPU 内存，逻辑直观好调试；上千粒子后每帧串行更新开始占帧时间 | 粒子少，或每个粒子行为差异大、分支多 |
| SceneKit 内置粒子（苹果 3D 场景框架的 `SCNParticleSystem`） | 参数化配置，不写 GPU 代码；更新规则受限于提供的参数 | 3D 场景快速加常规特效 |
| SpriteKit 粒子发射器（苹果 2D 游戏框架的 `SKEmitterNode`） | 同样参数化配置 | 2D 界面或小游戏加特效 |
| Unity / Unreal 引擎粒子 | 自带可视化编辑器与模块化参数，适合美术调参 | 做完整游戏、特效由非程序员维护 |
| 本实验的手写 Metal 方案 | 每帧的更新规则与画法完全自定义；代码量最大 | 更新逻辑特殊，或要理解 GPU 上状态如何流转 |

## Quick Start

前置条件：macOS 加 Xcode 的 Swift 工具链（Metal 只在苹果平台上可用）。在 `metal/15_particles/` 目录下运行：

```bash
./particles.sh               # 一条龙
AUTO_QUIT=6 ./particles.sh observe   # 观察六秒烟花
```

控制台输出（真实输出）：

```
粒子数: 10000，compute 每帧更新位置/速度，render 画 10000 个点
```

窗口中粒子从中心炸开、撞墙反弹，颜色随速度从青到橙。验证方法：把 kernel 里的反弹边界从 1.0 改成 0.5，粒子活动范围立刻收缩——物理规则确实住在 kernel 里。

实现侧每帧只有两步，代码在 `particles.swift` 的 `draw(in:)` 里：

```swift
// Pass 1：compute 积分
enc.dispatchThreadgroups(...threadsPerThreadgroup: MTLSize(width: 256, ...))
// Pass 2：同一 commandBuffer 里消费
enc.drawPrimitives(type: .point, vertexStart: 0, vertexCount: particleCount)
```

这段在做什么：第一行启动一次 GPU 并行计算，一万个线程分批更新粒子；第二行在计算完成后把每个粒子画成一个点。两趟命令编进同一个 commandBuffer（GPU 的命令列表，命令按编码顺序执行）——所以窗口里的粒子永远是"刚更新完就画出来"的位置。

## How It Works

按一帧内的执行顺序展开：先看数据长什么样，再看 compute 怎么更新，最后看 render 怎么画。

**数据布局。** 每个粒子占两个 float2（两个 32 位浮点数拼成的二维向量），分别放在 `positions` 和 `velocities` 两块缓冲里。

初始位置聚在中心附近、方向随机，由 CPU 侧用固定种子的伪随机数生成一次；此后整个运行期，CPU 每帧只写 4 字节——把 dt（时间步长，本帧推进的秒数，约 1/60）填进一个小缓冲。

**第一趟：compute 积分。** 核心函数用 Metal 的着色语言（Metal Shading Language，类 C++）编写：

```metal
kernel void update_particles(
    device float2 *positions [[buffer(0)]],
    device float2 *velocities [[buffer(1)]],
    constant ParticleUniforms &u [[buffer(2)]],
    uint i [[thread_position_in_grid]])
{
    float2 p = positions[i];
    float2 v = velocities[i];
    p += v * u.dt;
    // 撞墙反弹：越界就把位置夹回、速度取反
    if (p.x >  1.0) { p.x =  1.0; v.x = -abs(v.x); }
    if (p.x < -1.0) { p.x = -1.0; v.x =  abs(v.x); }
    if (p.y >  1.0) { p.y =  1.0; v.y = -abs(v.y); }
    if (p.y < -1.0) { p.y = -1.0; v.y =  abs(v.y); }
    positions[i] = p;
    velocities[i] = v;
}
```

为什么这样写：

- `i` 来自 `thread_position_in_grid`（本线程在全体线程中的编号），一个线程只碰下标为 i 的两个槽位，一万个线程同时跑互不干扰。
- `positions`/`velocities` 用 `device` 地址空间（指向 GPU 显存、可读写的区域）；dt 用 `constant`（一次调度中所有线程共享的只读小数据）。
- 反弹不写速度的完整物理反射，只做"位置钳回边界、对应分量取反"——规则越简单，越能看清状态更新的模式本身。

线程组织上，`dispatchThreadgroups` 按每组 256 个线程切分，(10000 + 255) / 256 = 40 组。你在输出里看到的"compute 每帧更新位置/速度"，就是这一趟在跑。

**第二趟：render 画点。** 顶点着色器（vertex shader，为每个顶点执行一次的 GPU 函数）从同一块 `positions` 缓冲读位置，把每个粒子输出成一个点：点大小 2.0，由 `[[point_size]]` 属性控制；

`drawPrimitives(type: .point, ...)` 告诉管线每个顶点画成一个方形点。着色器（shader）是 GPU 上各图形阶段函数的统称。

**颜色编码速度。** 顶点着色器同时算出速度长度，clamp（钳制到区间）到 0~1 后从青色插值到橙红，片元着色器（fragment shader，为每个屏幕像素执行一次的函数）原样把颜色写回。慢粒子是青色、快粒子是橙红，把不可见的速度场变成可见的色彩——可视化即调试，这条经验适用于所有 GPU 数值程序。

**顺序保证。** 两趟命令编进同一个 commandBuffer 时，GPU 按编码顺序执行，compute 先于 render 完成，无需 CPU 插手等待。跨 commandBuffer 才需要事件/栅栏（显式声明"先做完 A 再做 B"的同步手段）。

## Pitfalls & Q&A

**这个结构为什么适合 GPU，什么时候失效？** 万级粒子彼此独立、每帧同构更新，是数据并行的典型场景；CPU 循环一帧就到瓶颈。反过来，一旦粒子之间需要交互——A 的更新依赖 B 的当前值——"一线程一槽位"的无锁结构就不再成立。

**一万个线程读写不会互相覆盖吗？** 不会。每个线程只读写自己的槽位（以索引划分），无共享即无竞争。这是用数据布局从结构上避免锁，而不是加一把锁保护共享数据。

**dt 为什么放一个小缓冲，而不是写死在 kernel 里？** dt 的三个特点：全局一致（所有粒子同一时间步长）、每帧变化、体积极小（一个 Float）。这正是 constant/Uniform 数据的定义性场景：写死则时间无法推进，逐粒子传又是浪费带宽。

**有状态更新和无状态生成差在哪？** 本实验的 kernel 读上一帧结果、写回下一帧，是跨帧状态；另一些 GPU 任务每帧从头生成、不读旧输出（见 lab 16 的无状态生成）。理解两者的边界，就理解了 GPU 计算的任务分类。

**显式欧拉积分的误差呢？** 每帧一步 `p += v * dt` 在时间步长大时会累积误差，本实验不追求物理正确，重点是状态更新模式的完整性；换成更稳定的积分格式属于同一模式内的替换，不改变"缓冲存状态、kernel 更新状态"的结构。
