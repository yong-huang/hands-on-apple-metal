# 30 · ML + 图形混合管线：跨队列编排

> 混合管线的难点不是"跑"，而是"同步"：机器学习（ML）的输出必须先于图形消费。读完本篇你能用 MTL4 计算队列 + 共享事件 + 传统渲染队列搭出这条同步骨架，并理解数据面缓冲的设计契约——ML 派发位原位预留，编码器就绪后即可替换。

## Background

AI 生成内容正在进入实时渲染管线：超分（用神经网络把低分辨率画面放大变清晰）、神经材质、生成式贴图，走的都是"推理 → 渲染"的流水线——先由网络算出一张数据，再由传统渲染把它画出来。

没有跨队列同步机制时，人们只有两种笨办法。一是把 ML 和渲染塞进同一条队列串行排队：顺序天然正确，但两段工作互相等待，谁也无法并行。二是 CPU 中转：等 ML 队列完成、CPU 把数据读回、再提交渲染——数据绕经 CPU 一趟，CPU 还得空转等待，时间线被打碎。

痛点在顺序与并行不可兼得：渲染必须等推理完成，否则采到的是半成品数据；但 CPU 在中间等待又浪费无所事事的时间片。共享事件（Shared Event，跨队列、跨 CPU/GPU 的带值信号）给出第三种编排：生产者完成后发信号，消费者的命令在 GPU 时间线上等信号——先后关系由 GPU 原生表达，CPU 全程不介入。

## What

ML + 图形混合管线是把"机器学习推理"与"传统渲染"编排成一条有先后依赖的 GPU 流水线：生产者在计算队列（MTL4 命令栈上的队列，见 lab 28）生成数据面（供下游消费的数据缓冲），消费者在传统渲染队列等事件信号后采样它。

本实验的生产者是一个计算内核（kernel，GPU 上大规模并行执行的小程序），它就是未来 ML 派发的插槽。

一句话心智模型：**事件是队列之间的红绿灯**。可以把共享事件想象成两个车间之间的信号灯——计算车间完工亮灯，渲染车间见灯才开工。但和红绿灯不同的是，事件带值语义：它能区分"第 1 次完工"和"第 2 次完工"，不只是红绿两态，因此可以表达多帧、多阶段的精细先后。

## When to Use

- 每帧先推理再呈现时：神经超分、画质增强网络的输出要喂给当帧渲染。
- 神经材质或生成式贴图时：网络算出的贴图数据由渲染管线按像素采样。
- 计算与渲染需要并行推进时：两条队列各自满负荷，只在交接点同步。

何时不用：

- 计算与渲染能在同一条队列排开：同队列天然按序执行，不需要事件。
- 数据量极小、一帧一算一用：CPU 直接算直接传，不必起第二条队列。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 同队列串行 | 顺序天然正确，实现最简；两段工作互相等待 | 顺序依赖简单、规模小 |
| 跨队列 + 共享事件（本文） | 两队列并行推进，事件表达先后 | ML 与渲染分属队列且需并行 |
| CPU 中转 | 数据读回 CPU 再提交渲染；同步直观但往返延迟大 | 原型调试，性能不敏感 |

## Quick Start

前置条件：macOS + Xcode（MTL4 部分需 macOS 26 及以上；无 MTL4 时脚本自动退化为同队列编排）。进入本目录运行：

```bash
./ml_graphics.sh               # 一条龙
AUTO_QUIT=6 ./ml_graphics.sh observe
```

第一条命令一条龙做完编译、运行、清理三步（窗口保持打开，关闭窗口结束）。

第二条只运行不编译，AUTO_QUIT=6 表示窗口打开 6 秒后自动退出，便于脚本化观察；但它直接执行 `.build/` 下的编译产物，而一条龙结束时产物已被清理——想分步运行，先执行 `./ml_graphics.sh build`（只编译不清理），再跑观察命令。

真实输出：

```
编排：计算队列生成数据 → SharedEvent 信号 → 渲染队列等信号后采样
数据面回读: 角=(-0.10,0.30,0.20) 中心=(0.90,0.55,0.50)
✅ 混合管线验证通过：跨队列同步后数据面内容正确
```

窗口显示 GPU 生成的径向渐变。验证方法：数据面数值与径向公式逐位吻合（角落 d≈1 → 红通道≈0；中心 d≈0 → 0.9）。

跨队列编排的核心代码只有四行：

```swift
argTable.setAddress(dataBuffer.gpuAddress, index: 0)   // MTL4 也走参数表
m4.commit([cmdBuf]); m4.signalEvent(sharedEvent, value: 1)
// 渲染侧（传统队列）：
cb.encodeWaitForEvent(sharedEvent, value: 1)
```

这段在做什么：第一行把数据缓冲绑进 MTL4 的参数表；第二行提交计算命令缓冲，并把事件信号排在其后；第四行让传统渲染队列的命令缓冲在采样之前等待该事件到达值 1。

## How It Works

编排按数据流走：**计算队列生成数据 → 共享事件信号 → 渲染队列等信号后采样**。

1. **生产者侧（MTL4 计算队列）**：数据缓冲（512×512 个 float4——四分量浮点向量，即每个像素一组 RGBA）绑进参数表并登记进 ResidencySet（资源常驻登记表，见 lab 28）；kernel 逐像素写入径向渐变；`commit` 之后 `signalEvent(value: 1)`——信号保证排在本队列已提交工作之后。
2. **消费者侧（传统渲染队列）**：渲染命令缓冲在绘制前 `encodeWaitForEvent(value: 1)`，后续绘制命令卡在这里，直到事件到达。这是命令缓冲级的等待，发生在 GPU 时间线上——CPU 不轮询、不打断，两个队列在此交接后各自继续。
3. **三方共享同一块数据面**：缓冲用 shared 存储（统一内存：CPU 与 GPU 访问同一块物理内存）。于是 MTL4 计算写它、渲染片元（光栅化——把三角形铺成像素的过程——产出的候选像素）按像素索引读它、CPU 直接回读验证它——三方零拷贝。

你在真实输出里看到的 `角=(-0.10,0.30,0.20) 中心=(0.90,0.55,0.50)`，正是第 3 步 CPU 回读的结果：径向公式 `r = 0.9 − d`（d 是到中心的归一化距离），角落 d≈1 所以红通道 0.9−1.0=−0.10，中心 d=0 所以 0.90。

数值逐位吻合说明"写入 → 同步 → 消费"全链路顺序正确。

**ML 插槽在哪里？** 生成内核所在的位置就是 ML 派发位：lab 28 定位的 ML Command Encoder 就绪后，把这段 kernel 替换为网络派发即可，数据面契约（缓冲布局与格式）保持不变——渲染侧一行代码都不用改。

## Pitfalls & Q&A

**1. 画面全黑，且没有任何报错。**
现象：MTL4 队列明明提交了写入，渲染拿到的却是空数据。原因：数据缓冲没有登记进 ResidencySet，MTL4 队列的写入被静默丢弃——本实验实测踩过。

解法：`residency.addAllocation(...)` 加 `cmdBuf.useResidencySet(...)`，资源常驻在 MTL4 上不是可选项。

**2. 渲染采样到半成品或上一帧的数据。**
现象：画面偶尔显示旧内容或未写完的数据。原因：两条队列各自推进，没有先后约束，渲染没等生产者完成就开始采样。解法：渲染命令前 `encodeWaitForEvent`，等事件值到达后再绘制。

**Q：跨队列同步有哪些手段？**
事件（带值语义的信号）、栅栏（fence，缓冲级的顺序约束）、共享事件（GPU 间与 CPU 等待通用）。本实验用共享事件贯穿三端：MTL4 写入、渲染等待、CPU 验证，一套语义走完。

**Q：CPU 不介入的同步有什么好处？**
没有忙等（CPU 空转轮询），没有时间片浪费，先后关系完全由 GPU 时间线自治表达。对帧管线而言，这直接转化为更低的交接延迟。

**Q：数据面该怎么设计？**
三条原则：统一内存缓冲（三方零拷贝）、明确的布局契约（512×512 float4，写读两端对齐）、单一写者（只有生产者写，消费者只读）。三条立住，ML/渲染/调试三方共享不冲突，插件替换不动契约。
