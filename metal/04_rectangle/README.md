# 04 · 索引缓冲画矩形：4 个顶点拼 2 个三角形

> 一个矩形 = 2 个三角形，直接存顶点要 6 个，其中 2 个完全重复。本实验引入索引缓冲（index buffer）：顶点只存一份，靠一份序号序列决定拼装顺序——这是所有网格建模省显存的基础手段。

## Background

GPU 画图元（primitive，点、线、三角形这类基本图形）的单位是三角形，而相邻三角形几乎总要共享顶点。不引入任何复用机制时，每个三角形都带自己的一套顶点：一个矩形要存 6 个顶点，其中对角线上的 2 个被原样存了两遍。

浪费在小图形上不明显，放到真实 3D 网格里就不可接受：一个顶点平均被 6 个三角形复用，按"每三角形三份顶点"的方式存储，显存占用和读取带宽会膨胀数倍，顶点着色器（GPU 上逐顶点执行的函数）也在对同一个顶点反复做同样的计算。

索引缓冲的思路应运而生：把"顶点数据"与"顶点使用顺序"解耦——顶点缓冲去重存数据，索引缓冲存 `0,1,2,3` 这样的序号序列。数据存一份，顺序按需点名。

## What

索引缓冲是一块存放顶点序号的缓冲区，通常用 `uint16` 或 `uint32` 整数。绘制时 GPU 先读索引，再按序号从顶点缓冲取数据——顶点数据的顺序与拼装顺序从此无关。

可以把索引缓冲想象成剧组的点名册：演员（顶点）只登记一次，每场戏（三角形）按名字点人上台。但和普通点名册不同的是，索引每 3 个连续一组、按固定规则折叠成三角形，同一个序号可以连续出现在两组里——那正是被共享的顶点。

本实验的数据流：顶点缓冲（4 个四角）与索引缓冲（4 个序号）汇入 `TriangleStrip` 组装器 → 折叠出 2 个三角形 → 填充成四色矩形。心智模型：**索引是顶点的点名册，每 3 个连续索引唱名出一个三角形**。

## When to Use

这节回答：什么时候值得引入索引，什么时候直接画顶点更省事。

典型场景：

- 画任何共享顶点的图形：矩形、多边形、网格——只要顶点被两个以上三角形用到，索引就开始省。
- 加载 3D 模型：模型文件里的网格几乎都以索引形式存储，读取后直接对应索引绘制。
- 顶点着色器较重时：顶点去重 + GPU 顶点缓存可以减少重复的逐顶点计算。

何时不用：只有一两个孤立三角形、顶点零复用时，索引没有收益，`drawPrimitives` 直接画更简单。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| CPU 绘制 | 自己拼多边形、无索引概念；大面积画面慢 | 顶点极少的小图形 |
| OpenGL / OpenGL ES | 同样提供索引绘制（`glDrawElements`）；Apple 平台已废弃 | 维护历史跨平台代码 |
| SpriteKit / SceneKit | 网格与索引由框架托管，不用手动建 | 标准 2D/3D 内容 |
| Metal 索引绘制 | 显式建索引缓冲与拼装模式；样板代码多 | 自定义网格、性能敏感渲染 |

## Quick Start

前置条件：一台支持 Metal 的 Mac，实验目录自带 `rectangle.sh` 脚本；程序会打开一个窗口。

```bash
./rectangle.sh               # 一条龙：build → observe → clean
AUTO_QUIT=6 ./rectangle.sh observe   # 6 秒自动退出
```

观察要点：窗口里一个矩形，四个角各一色（红/绿/蓝/黄），颜色在矩形内部平滑过渡——顶点色插值在更大面积上的重演。

验证方法：把索引倒序成 `[3,2,1,0]`，画面应该不变——两个三角形的顶点集合没变，本实验未开背面剔除（cull mode，不绘制背对相机的面），绕序（三个顶点的排列方向）翻转不影响显示。这正是"索引只是顺序"的证明。

下面是本实验新增的核心代码，它在做的事：创建 4 个 `uint16` 序号的索引缓冲，再以条带模式提交一次索引绘制。

```swift
// 索引缓冲：4 个 uint16 序号，点名 4 个顶点
let indices: [UInt16] = [0, 1, 2, 3]
let indexBuffer = device.makeBuffer(bytes: indices, length: indices.count * MemoryLayout<UInt16>.size)

// 条带模式绘制：indexCount 是"索引数"（4），由条带规则折出 2 个三角形
encoder.drawIndexedPrimitives(
    type: .triangleStrip, indexCount: indices.count,
    indexType: .uint16, indexBuffer: indexBuffer, indexBufferOffset: 0)
```

## How It Works

这节拆开索引绘制从取数到折叠的机制。

两种拼装模式的成本差异：

| 模式 | 画 N 个三角形需要 | 适用 |
|:---|:---|:---|
| `.triangle` | 3N 个索引 | 互不相连的散三角形 |
| `.triangleStrip` | N+2 个索引 | 条带相连的三角形（本实验） |

TriangleStrip 的折叠规则：第 n 个三角形取索引 `n, n+1, n+2`，相邻三角形共享一条边。本实验 `[0,1,2,3]` 共 4 个索引，正好是 N+2：三角形 1 取 `0,1,2`，三角形 2 取 `1,2,3`。

为什么 4 顶点 + 4 索引就够了：三角形 1 用顶点 0-1-2，三角形 2 用顶点 1-2-3——共享了对角线上的 1 和 2，没有顶点被重复存储。你在窗口看到的四色矩形，就是这 4 个顶点的颜色经插值铺满 2 个三角形的结果。

用索引后绘制调用从 `drawPrimitives` 换成 `drawIndexedPrimitives`：GPU 先查索引再取顶点；有顶点缓存（GPU 对近期处理过的顶点结果的缓存）时，vertex shader 对被复用的顶点可能只跑一次。

`indexCount` 与顶点数的区别：前者是索引缓冲里序号的个数（决定画几个三角形），后者是顶点缓冲的容量。`drawIndexedPrimitives` 只关心前者——条带规则自动从 4 个索引折叠出 2 个三角形。

## Pitfalls & Q&A

坑一：画面出现垃圾图形或直接崩溃。
现象是三角形顶点飞到奇怪的位置，或程序异常退出。原因是索引越界（指向不存在的顶点），属于未定义行为，GPU 不做保护。解法：保证每个索引都小于顶点数，调试期逐一核对序列。

坑二：开启背面剔除后，条带网格的某些三角形消失。
现象是部分三角形整块不见。原因是条带里相邻三角形的绕序（winding order，三个顶点的排列方向，用于区分正反面）自动翻转，而背面剔除（cull mode，不绘制背对相机的面）按绕序丢弃三角形。解法：注意条带奇偶朝向，必要时调整剔除模式。

问：索引用 `uint16` 还是 `uint32`？
顶点数少于 65536 时用 `uint16`，单个索引从 4 字节减到 2 字节，索引缓冲体积减半、读取带宽相应减少；大网格，或不想在越界时处理类型重建，直接用 `uint32`。
