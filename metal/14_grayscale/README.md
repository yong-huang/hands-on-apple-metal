# 14 · GPU 灰度滤镜：纹理作为计算输出

> 这次不是"画"，而是"算"：用计算内核（compute kernel，不画图、只做数据运算的 GPU 函数）逐像素处理一张纹理（GPU 上的图像数据），再把结果当普通纹理渲染出来。读完本篇，你能跑通 GPU 图像处理的最小闭环——CPU 备图、内核读写、回读验证、渲染消费——并认识 MTLTexture 的另一重身份：GPU 上最通用的数据容器。

## Background

在 CPU 上做滤镜，传统做法是双层循环遍历每个像素、逐个改颜色；Core Image 这类系统框架把这些循环封装成了滤镜库。

规模一大就撞上瓶颈：一张 512×512 的图有 26 万个像素，处理一次就是 26 万次循环。滤镜实时预览、视频逐帧后处理（对渲染完成的画面再加工）时，像素数以百万计还要逐帧刷新，CPU 遍历的耗时成为瓶颈。GPU 恰好有上千个小核心，适合把同一个操作同时铺到每个像素上。

compute 管线由此承担了这件事：把图像当数据，内核函数逐像素并行执行。滤镜、后处理、CV（Computer Vision，计算机视觉）预处理，从此都是 GPU 计算的日常场景。

本实验是这个方向的最小闭环：CPU 备图 → compute 读 A 写 B → 验证 → 渲染消费。模糊、融合、AI 输出这类"纹理进纹理出"的算子，都是它的变体。

## What

MTLTexture 不只是"一张图片"——它是带像素格式（声明每个像素的数值如何解释成颜色）与坐标的二维数组，GPU 上最通用的数据容器；compute kernel 则是"对每个像素执行一遍的函数"，两者配合完成图像变换。

一句话心智模型：**纹理 = 带坐标的二维数组，kernel = 逐像素函数**。

可以把整张纹理想象成一张电子表格，kernel 是套用到每个单元格的公式，行列号就是像素坐标。但和表格公式不同的是：GPU 让所有单元格同时计算，而不是从左到右逐格算。

## When to Use

典型场景——在做什么事的时候会用到：

- 图像滤镜与调色：灰度、反色、亮度曲线，对整图做逐像素变换。
- 渲染后处理：先把场景画进一张纹理，再用 kernel 做模糊、调色，最后上屏。
- AI/CV 预处理：把图片归一化成模型输入张量（多维度数组），compute 负责搬运与变换。

何时不用：

- 一次性处理一张小图：CPU 几行循环更省事，不值得建管线。
- 现成滤镜能满足：Core Image 拿来就用，不必手写内核。
- 要"画"几何图形：用渲染管线（把几何变成屏幕像素的绘制流程），compute 不负责光栅化。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CPU 双层循环 | 无 GPU 依赖，逻辑直白 | 一次性小图、原型验证 |
| Core Image | 系统滤镜库，链式组合，自带 GPU 加速 | 常见滤镜需求，不想写内核 |
| 渲染管线（片元着色器） | 用片元着色器（shader，运行在 GPU 上、逐像素执行的小程序）边画边算，结果直接上屏 | 全屏效果处理并即时显示 |
| compute kernel（本实验） | 读写自由，结果可回读验证、可作中间数据 | 图像进图像出的数据加工 |

## Quick Start

前置：macOS + Xcode（本实验基于 Metal，Apple 的底层 GPU 图形 API）。运行：

```bash
./grayscale.sh               # 一条龙：build → observe → clean
```

真实输出：

```
测试图 512×512 rgba8Unorm 已生成；compute 管线就绪
  采样0 (10,10) → R=145 G=145 B=145 ✅
  采样1 (256,256) → R=99 G=99 B=99 ✅
  ...
✅ 灰度转换验证通过：所有采样点 R=G=B
```

窗口显示灰度化的测试图。验证方法：5 个采样点的 R、G、B 相等——这正是灰度的定义，回读即证明。

内核代码来自 `grayscale.swift`。这段在做什么：每个线程读一个像素，加权求出亮度，写出灰度像素：

```metal
kernel void grayscale_kernel(
    texture2d<float, access::read>  src [[texture(0)]],
    texture2d<float, access::write> dst [[texture(1)]],
    uint2 gid [[thread_position_in_grid]]) {
    float4 c = src.read(gid);
    float y = 0.299*c.r + 0.587*c.g + 0.114*c.b;
    dst.write(float4(y, y, y, 1.0), gid);
}
```

- 参数表：只读的 `src`、只写的 `dst` 两个纹理，加上 `gid`（当前线程负责的像素坐标）。
- `src.read(gid)`：读入该坐标的 RGBA 四通道。
- `float y = ...`：按人眼敏感度对三通道加权求亮度（系数来由见 How It Works）。
- `dst.write(...)`：把灰度值写回同一坐标，alpha（透明度通道）补 1。

Swift 侧的 `setTexture(src, index: 0)` 对应着色器的 `[[texture(0)]]`——与缓冲绑定是同一套编号对应体系，只是资源类型换成了纹理。

## How It Works

数据流：CPU 生成的测试图（512×512 的 `rgba8Unorm`，每通道 8 位、0–255 归一化到 0–1）经 `replace()` 上传；compute 逐像素读 src 写 dst；dst 一边供渲染采样（当普通纹理画到窗口）、一边供 CPU 回读验证。

你在真实输出里看到的采样点列表，就来自回读验证这一步。

**调度**：512×512 像素、32×32 的线程组（一次调度出发的小队）→ 16×16 组。

dispatch（把线程网格提交给 GPU）时网格大小按 ceil(尺寸/组大小) 向上取整；内核内保留 `if (gid >= size) return` 边界检查——本例整除用不上，但非整除时它是唯一防线，防御成本为零。

**纹理访问**：kernel 里用 `access::read`（`src.read(gid)`）与 `access::write`（`dst.write(color, gid)`），不经过采样器（控制插值与越界行为的取数规则）

——逐纹素（纹理上的单个像素）精确访问，适合"输入输出一一对应"的滤镜；需要插值、缩放时才改用 sample。

**亮度系数**：`0.299R + 0.587G + 0.114B` 来自人眼视敏度（对不同颜色光的敏感程度）——人眼对绿光最敏感，绿色权重过半。直接取平均（各 1/3）会破坏亮度感知，绿色通道的细节丢失。

**验证通道**：dst 声明 `.storageModeShared`（CPU 与 GPU 共享同一份内存的存储方式），CPU `getBytes` 直接回读任意区域——统一内存（CPU 与 GPU 共享同一块物理内存的架构）让"算完立刻验证"接近零成本。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- 偶发崩溃，或图像边缘出现异常数据。原因：网格尺寸非整除时，边缘线程的 gid 超出纹理范围，而内核没有边界检查。解法：网格按 ceil 向上取整，内核开头保留 `if (gid >= size) return`，两道防线都不要省。

深入问答：

- **怎么证明 GPU 滤镜真的算对了？** shared 存储 + `getBytes` 回读若干采样点 + 数学性质断言（灰度的定义就是 R=G=B）——把"看起来对了"变成"算出来对了"。这套验证打法可以迁移到任何"纹理进纹理出"的算子。
- **这个闭环和渲染管线怎么分工？** 渲染管线回答"把几何画成像素"，compute 回答"把数据算成数据"；后处理场景里两者接力——先渲染进纹理，再 compute 加工，最后渲染上屏。本实验的 dst 被渲染消费，正是接力的最小样例。
