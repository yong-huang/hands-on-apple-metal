# 11 · 光照立方体：漫反射与环境光

> 立方体六个面颜色恒定时，立体感是假的——真正的立体感来自光照：面与光线的夹角决定亮度。本实验给立方体加上每个顶点的法线与最小光照方程。读完本篇，你能理解"环境光 + 漫反射"这一最小可行光照模型，它是 PBR（Physically Based Rendering，基于物理的渲染）的起点。

## Background

给每个面涂上固定颜色的立方体（颜色来自顶点色或贴图），怎么转都是那几块颜色。问题在旋转时暴露：六个面亮度完全相同，大脑无法从明暗判断哪面朝光、哪面背光，立体感崩塌。

真实世界的规律是：表面与光线的夹角决定接收到的光量——正对光的面亮，侧对的面暗，背光的面只剩环境余光。把这条规律写进渲染，就是光照模型。

最小可行的光照模型由此成为实时渲染的第一课：环境光（不依赖方向的保底亮度）加漫反射（亮度随夹角变化），本实验实现的就是这个最小版本。理解它就理解了 PBR 的起点，也是阴影（遮挡处变暗）、延迟着色（几何画完后再统一算光照的技术）等进阶技术的前置知识。

## What

两个新角色。法线（Normal）：垂直于表面的单位向量，标记"面朝哪"；本实验的面法线由叉积（两条边向量运算出同时垂直于它们的向量）`cross(e1, e2)` 现算，不手工填。光照方程：环境光保底，漫反射亮度由 `dot(N, L)`（点积：两个方向越接近值越大）决定。

一句话心智模型：**位置交给 MVP（Model-View-Projection，模型/视图/投影矩阵合称），亮度交给 dot(N, L)**。

可以把 dot(N, L) 想象成太阳能板的发电效率：板面正对太阳时接收最多，倾斜按角度打折，背对太阳为零。但和太阳能板不同的是，这里的"光"是平行光的方向向量（没有位置），而且最终亮度还要叠加一份不随角度变化的环境光。

## When to Use

典型场景——在做什么事的时候会用到：

- 给任何几何体加立体感：模型查看器、游戏物体，明暗随旋转流转。
- 光源会变的应用：光源方向是每帧可改的 uniform，即 CPU 传入、着色器（shader，运行在 GPU 上的小程序）只读的共享参数，改参数即改明暗。
- 学习实时渲染的第一层光照，后续高光、阴影都在它之上叠加。

何时不用：

- 界面、平面图案：没有体积就没有明暗需求。
- 需要真实质感时它只是起点：金属高光要 Phong/Blinn-Phong，接触阴影要阴影贴图，物理材质要 PBR——本模型是地基而非终点。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 无光照（顶点色/贴图） | 颜色恒定，无立体感 | 卡通风、UI、平面图案 |
| 环境光 + 漫反射（本实验） | 最小成本获得立体感 | 实时场景的光照基础层 |
| Phong / Blinn-Phong | 在漫反射上增加高光项 | 金属、光滑表面 |
| PBR | 基于物理的材质参数体系 | 追求真实感的现代渲染管线（GPU 从几何到像素的完整处理流程） |

## Quick Start

前置：macOS + Xcode（本实验基于 Metal，Apple 的底层 GPU 图形 API）。运行：

```bash
./lit_cube.sh               # 一条龙
AUTO_QUIT=6 ./lit_cube.sh observe
```

控制台真实输出：

```
顶点数: 36，每顶点带法线；光照 = 环境光 0.25 + 漫反射 dot(N,L)
```

窗口中立方体旋转时明暗面流转。验证方法：光源方向在片元（候选像素）里是经 0 号缓冲槽传入的常量（`[[buffer(0)]]`：CPU 把参数放进编号 0 的缓冲，着色器按同一编号取用）——把它改成 `(0,-1,0)`（从下方打光），底面立刻变亮顶面变暗。

顶点结构随之升级：从 `{position, color}` 变为 `{position, normal, color}` 三元组，stride（每个顶点占的字节数）从 28 字节变 40 字节。

着色器核心代码来自 `lit_cube.swift`。这段在做什么：顶点阶段把法线转到当前朝向，片元阶段用法线算亮度：

```metal
out.normal = (uni.model * float4(v.normal, 0.0)).xyz;   // w=0：只旋转不平移
float diffuse = max(dot(normalize(in.normal), normalize(lightDir)), 0.0);
return in.color * (0.25 + diffuse);
```

- 第 1 行（顶点着色器）：用 model 矩阵变换法线；w 传 0 表示这是方向不是位置。
- 第 2 行（片元着色器）：两侧各 normalize（缩放成长度为 1 的单位向量）后做点积，负值钳到 0。
- 第 3 行：颜色乘以"环境光 0.25 + 漫反射"，背光面保留 25% 亮度。

为什么法线的 w 是 0：向量不受平移影响——位置用 1、方向用 0，齐次坐标（用第 4 个分量区分点和向量的写法）的基础功。

## How It Works

数据流：顶点与法线、光源方向汇入顶点着色，法线经光栅化（把三角形覆盖的区域拆成候选像素）插值——片元拿到的是"平滑过渡的法线场"，再逐片元做光照。输出里那句"每顶点带法线"，对应顶点结构的这次升级。

核心方程（片元中执行）：

```
diffuse = max(dot(N, L), 0)     // 背面钳 0
color   = base * (0.25 + diffuse)
```

为什么这样写：

- `max(..., 0)` 防止背面出现负亮度。dot(N, L) 的数学本质是 Lambert 定律（接收光量正比于 cos(入射角)，即 dot(N,L)），背光面 cos 为负，直接用会越算越黑。
- `0.25` 环境光防止死黑。纯漫反射下背光面全黑，画面失去暗部结构；环境光是不依赖方向的全局保底，也是全局照明（把环境中互相反射的光也计算进来的渲染思路）的最廉价近似。

再对照 Quick Start 的代码：第 2 行的 `normalize` 是在处理插值副作用——法线经光栅化插值后长度不再保证为 1，先归一化再点积才准确。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- 缩放过的物体光照错乱。原因：法线变换直接用 model 矩阵，只对纯旋转成立；非均匀缩放伴随的切变（把形状斜向拉歪的变形）会扭曲法线方向。解法：改用逆转置矩阵（inverse transpose，先求逆再转置，能抵消缩放扭曲）作为法线矩阵。
- 画面整体发暗。原因：忘了归一化插值后的法线，短法线让点积普遍偏小。解法：点积前 `normalize`。
- 想移动光源却怎么改都不对。原因：把"光的位置"与"光源方向"混用——方向光照（平行光，光源无限远、只有方向，如阳光）只需要一个向量。解法：本模型按平行光写，传方向向量即可。

深入问答：

- **在顶点算光照和在片元算有什么区别？** 前者叫 Gouraud 着色：顶点算完插值颜色，便宜但高光失真；后者叫 Phong shading：逐片元用插值法线算光照，本实验属于后者。两者在高光上的差异巨大。
