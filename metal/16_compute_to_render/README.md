# 16 · Compute → Render：同一命令缓冲的编排
> GPU 的一段并行计算（compute）凭公式一次算出几何顶点，紧接着的渲染阶段（render）把同一批顶点画成图形；两段命令编在同一个命令缓冲（GPU 按顺序执行的命令列表）里，中间不经过 CPU。读完本篇你能掌握"算几何、画几何"的最短接线方式，并理解"编码顺序即执行顺序"这一关键语义。

## Background

在屏幕上画一个圆环、一条波面曲线，传统做法有两种：要么在建模软件里把模型做好、导出成文件再加载，要么在 CPU 上逐个算出顶点坐标、填进数组后上传给显卡。两种做法的共同点是：顶点数据在画之前就已经准备好，存在 CPU 侧。

程序化几何（波面、粒子轨迹、程序化地形）撞的就是这堵墙：顶点是"算出来的"，形状可能随参数每帧变化。CPU 逐点计算是串行的，算完还要每帧往显卡搬一次数据；如果生成和绘制又分属两个提交批次，还得写代码保证"先算完再画"。

把"生成顶点"这一步也交给 GPU 的并行计算，并且把生成与绘制编进同一个提交批次，靠 GPU 自身的顺序语义衔接两者——这就是 compute→render 的最短路径。掌握它，就掌握了 GPU 程序化建模的骨架。

## What

本实验用 Metal——苹果的 GPU 编程框架（Swift 侧提交命令，GPU 上执行的函数用专门的类 C++ 语言编写）——做一个"compute 产几何、render 吃几何"的最小编排：

- **生成**：一个 compute 内核（kernel，GPU 上成千上万个线程各自执行一遍的同一段函数）按圆的参数方程，把 256 个顶点（构成线与面的空间坐标点）算进一块缓冲（buffer，GPU 显存里连续的原始数据区域）。
- **消费**：渲染管线（把顶点变成屏幕像素的固定处理流程）紧接着把这块缓冲当作顶点数据，连成一个圆环。

这里的生成是**无状态**的：kernel 不记得上一帧画过什么，每次都是全量重算 `顶点[i] = 圆公式(i)`。代价是每次 256 次三角函数（微不足道），换来零状态管理。

一句话心智模型：**编码顺序 = 执行顺序**。可以把命令缓冲想象成一张按行执行的工单：先写"算几何"、再写"画几何"，GPU 就严格按这个顺序干活。但和人工排工单不同的是：这个保证只对同一个命令缓冲成立，跨命令缓冲的先后要靠事件/栅栏这类显式同步（跨队列的版本见 lab 26）。

## When to Use

这一节给判断力：什么活适合"compute 生成、render 消费"，什么活不适合。

典型场景：

- 画形状由公式定义、随参数变化的图形（圆环、波面、轨迹线）：每帧重算顶点，改参数立即生效。
- 程序化地形、程序化建模的原型验证：先用几百个顶点确认生成公式，再上规模。
- 需要把一次数学计算的结果直接可视化：画面就是输出。

何时不用：

- 几何是固定的静态模型（建模软件导出的网格）：直接加载资产，不必每帧重算。
- 顶点数极少（几个点、一条线）：CPU 算完填数组更直接。
- 生成本次结果依赖上一帧结果（模拟类任务）：那是"有状态更新"的场景，结构不同（见 lab 15 的粒子系统）。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CPU 生成顶点再上传 GPU | 简单直观；每帧要把新顶点从内存搬到显存 | 顶点少、形状很少变 |
| 建模软件导出静态网格 | 零运行期计算；资产体积随精度增大 | 形状固定不变的模型 |
| SceneKit（苹果 3D 场景框架） | 直接渲染现成的场景与模型 | 用现成 3D 资产做界面或演示 |
| 本实验的 compute 生成 | 参数化、分辨率无关、零资产体积；代价是每帧 GPU 计算开销，且只能表达公式写得出的形状 | 形状由公式定义、可能随参数变化的几何 |

## Quick Start

前置条件：macOS 加 Xcode 的 Swift 工具链。在 `metal/16_compute_to_render/` 目录下运行：

```bash
./compute_to_render.sh               # 一条龙
AUTO_QUIT=6 ./compute_to_render.sh observe
```

真实输出：

```
  顶点[0] = (0.700, 0.000) |len|=0.7000 ✅
  顶点[64] = (-0.000, 0.700) |len|=0.7000 ✅
  顶点[128] = (-0.700, -0.000) |len|=0.7000 ✅
  顶点[192] = (0.000, -0.700) |len|=0.7000 ✅
✅ compute 生成的 256 个顶点全部落在半径 0.7 的圆上
```

窗口显示一个青色圆环。验证方法：回读的每个顶点模长都是 0.7000——"生成正确"由数学断言而非肉眼确认。

每帧的编排代码在 `compute_to_render.swift` 的 `draw(in:)` 里：

```swift
// 同一个 cb：先 compute 后 render
if let enc = cb.makeComputeCommandEncoder() { /* dispatch 256 线程 */ enc.endEncoding() }
if let enc = cb.makeRenderCommandEncoder(descriptor: pass) { /* draw lineStrip */ enc.endEncoding() }
cb.present(drawable); cb.commit()
```

这段在做什么：第一个编码器（向命令缓冲写入命令的对象）把"算几何"的并行计算命令写进缓冲，第二个编码器紧随其后写入"画几何"的绘制命令；`commit` 一次提交，GPU 按写入顺序执行。生成内核按全局索引寻址——每个线程"以我的编号写我的槽位"，渲染端按同一编号取用。

## How It Works

按一帧内的执行顺序展开：生成内核怎么算顶点、验证怎么保证可靠、渲染怎么连成环。

**生成内核。** 核心函数用 Metal 的着色语言（Metal Shading Language，类 C++）编写：

```metal
kernel void generate_circle(
    device float2 *vertices [[buffer(0)]],
    constant GenUniforms &u [[buffer(1)]],
    uint i [[thread_position_in_grid]])
{
    if (i >= u.count) { return; }   // 多余线程直接退出：线程按组调度，数量可能超过点数
    float a = float(i) / float(u.count) * 2.0 * M_PI_F;
    vertices[i] = float2(cos(a), sin(a)) * u.radius;   // 圆的参数方程
}
```

为什么这样写：

- 角度 `a` 把圆周均分成 count 份，第 i 个线程算第 i 个顶点；cos/sin 给出单位圆坐标，乘半径得到最终位置。
- `if (i >= u.count)` 是边界兜底：线程按 64 个一组调度（(256 + 63) / 64 = 4 组），总线程数可能大于点数，越界写入必须挡住。
- `i` 来自 `thread_position_in_grid`（本线程在全体线程中的编号）；`vertices` 用 `device` 地址空间（GPU 显存里可读写），count/radius 这类小参数用 `constant`（一次调度中所有线程共享的只读数据）。
- Metal 着色语言里 π 的常量名是 `M_PI_F`。

**验证为什么可靠。** 程序启动时独立跑一次 compute，调用 `waitUntilCompleted()`（阻塞 CPU，直到 GPU 把这个命令缓冲执行完）之后才由 CPU 回读缓冲，抽查四个象限点：每个点的模长与半径 0.7 的偏差小于 0.001 才算通过。

你在真实输出里看到的四行坐标和 ✅，就来自这次抽查。

**渲染成环。** `drawPrimitives(type: .lineStrip, vertexCount: 256)` 把 256 个顶点按顺序两两相连（lineStrip，即折线图元；图元是 GPU 绘制的基本形状单位：点、线段、三角形）。

相比三角形"填充"的画法，线段能直观暴露几何质量——缺一个顶点、错一段弧，线上一眼可见。注意 lineStrip 不自动闭合：第 255 个顶点与第 0 个顶点之间差一段，视觉上是接近闭合的圆环。

**顺序语义。** compute 先编码、render 后编码，GPU 严格按序执行，compute 写完的缓冲 render 直接可用——同命令缓冲内不需要任何显式同步，资源依赖天然满足。跨命令缓冲才需要事件/栅栏（显式声明"先做完 A 再做 B"的同步手段）。

## Pitfalls & Q&A

**圆环上出现缺口，缺了几个顶点。** 现象：线环某处断开。原因：启动的生成线程数没有覆盖全部点数，部分顶点没被写入。解法：分组数向上取整——(点数 + 组大小 − 1) / 组大小，本实验即 (256 + 63) / 64 = 4 组。专门的边界反例见 lab 22。

**CPU 回读缓冲读到旧数据。** 现象：验证函数偶发失败，或读到上一次的值。原因：GPU 命令是异步执行的，compute 还没跑完，CPU 就开始读缓冲。解法：回读前调用 `waitUntilCompleted()` 等待 GPU 完成——本实验的验证函数就是这么写的。

**π 常量在 Metal 着色语言里编译不过。** 现象：照搬 C 代码里的 `M_PI` 报错。原因：着色语言的标准库里 π 写作 `M_PI_F`。解法：替换为 `M_PI_F`。

**有状态还是无状态，怎么选？** 这是 GPU 任务设计的第一决策。有状态省计算但引入时间依赖（上一帧影响下一帧）；无状态可重算、可回放、易并行。结果只由当前输入决定就选无状态，结果要累积历史就选有状态。

**生成的几何怎么验证才可信？** 数学不变量（模长、对称性）加 CPU 回读断言，比肉眼看截图可靠——截图能看出"大概是个圆"，断言能证明"每个点都在半径 0.7 的圆上"。
