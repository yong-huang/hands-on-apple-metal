# 26 · 延迟着色：G-Buffer + 屏幕空间光照

> 延迟着色（Deferred Shading）是现代游戏引擎的标准光照架构：先把几何属性"拍照"存下来，光照推迟到全屏一次做完，也是 MRT（多渲染目标）的教科书案例。读完本篇你能理解 G-Buffer 的分工、MRT 的用法，以及前向/延迟两条管线的选型依据。

## Background

传统做法叫前向渲染（forward rendering）：逐个物体绘制，绘制到某个像素时立刻把所有光源的光照算完、写出最终颜色。这是最直观的顺序，也长期是实时渲染的默认路径。

光源一多它就撞墙。设想一条夜景街道有一百盏灯：每个物体绘制时都要和一百盏灯各算一遍。更糟的是遮挡——一个像素可能被前后多个物体先后覆盖（即 overdraw，重复着色），被最终挡住的像素照样把光照白算一遍。光源数量直接拖累几何管线，成本随"物体数 × 光源数"增长。

延迟着色把顺序倒过来：第一遍只记录"每个像素看到了什么表面"，完全不碰光照；第二遍对全屏每个可见像素统一算一次光照。几何成本与光源数量脱钩，2000 年代中后期起成为游戏引擎的主流架构。

## What

延迟着色是一种两遍渲染架构：第一遍（G-Buffer Pass，Pass 即渲染通道：一次完整的"清屏—绘制—提交"过程）把每个像素可见表面的几何属性写进多张全屏纹理；第二遍（光照 Pass）在屏幕空间（以像素坐标为坐标系的二维处理阶段）逐像素读出这些属性计算光照。

第一遍写下的那组纹理合称 G-Buffer（geometry buffer，几何缓冲）。本实验存两样：反照率（albedo，表面本身的固有色，不含光照影响）与法线（normal，表面朝向的单位向量）。

一次绘制同时写多张纹理，靠的是 MRT（Multiple Render Targets，多渲染目标）。

一句话心智模型：**先拍照存证据，再统一审案**。可以把 G-Buffer Pass 想象成现场勘查拍照——先不判断、只留档；但和照片不同的是，G-Buffer 记录的是每个像素的"表面档案"（颜色、朝向、深度）而非影像，审案（光照）时不需要回到现场重看几何。

## When to Use

- 场景里光源多且在动时：夜景、霓虹街道、大量动态点光源——加灯只增加全屏一遍的循环量，几何遍纹丝不动。
- 几何复杂、遮挡严重时：overdraw 严重的场景里，延迟着色只对最终可见像素算光照，浪费天然更少。
- 要叠加屏幕空间后处理时：屏幕空间环境光遮蔽（SSAO，用深度/法线估算角落变暗）这类效果正好复用 G-Buffer 的数据。

何时不用：

- 透明物体多的场景：每像素只存一份表面，透明混合无法"延迟"，需要额外的前向通道补。
- 带宽紧张的移动端：G-Buffer 的读写带宽随分辨率线性增长。
- 光源很少的简单场景：直接前向渲染，少两张全屏纹理和一次全屏绘制。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 前向渲染 | 逐物体当场算光照；实现简单，对透明物体和 MSAA（多重采样抗锯齿）友好 | 光源少、场景简单、移动端 |
| 延迟着色（本文） | 几何与光照解耦，光源扩展成本低；G-Buffer 带宽大，透明与 MSAA 麻烦 | 光源多、几何复杂的桌面/主机场景 |
| Forward+（分簇前向） | 前向渲染 + 把光源按屏幕区域分簇；多光源下兼顾透明物体 | 现代引擎常见的折中方案 |

## Quick Start

前置条件：macOS + Xcode（Swift 直连 Metal，无第三方依赖）。进入本目录运行：

```bash
./deferred.sh               # 一条龙
AUTO_QUIT=6 ./deferred.sh observe
```

第一条命令一条龙做完编译、运行、清理三步（窗口保持打开，关闭窗口结束）。

第二条只运行不编译，AUTO_QUIT=6 表示窗口打开 6 秒后自动退出，便于脚本化观察；但它直接执行 `.build/` 下的编译产物，而一条龙结束时产物已被清理——想分步运行，先执行 `./deferred.sh build`（只编译不清理），再跑观察命令。

真实输出：

```
G-Buffer: 1024×768 albedo + normal（MRT 两张）+ depth32Float；场景 78 顶点
G-Buffer 统计: 红立方体 4.35% | 蓝立方体 5.02% | 朝上法线(地面) 53.0%
✅ MRT 验证通过：反照率与法线两张目标都被正确写入
```

窗口显示两个立方体与地面的延迟光照。验证方法：回读（把 GPU 纹理内容拷回 CPU 统计）两张 G-Buffer 做全图统计——红/蓝立方体占比与朝上法线占比都可解析预期。

建立 MRT 管线的代码只有一段，在管线描述符（告诉 GPU 片元——光栅化（把三角形铺成像素的过程）产出的候选像素——输出写到什么样式的目标上）里为两张颜色附件（render pass 里承接片元颜色输出的纹理槽位）各声明像素格式：

```swift
let g = MTLRenderPipelineDescriptor()
g.colorAttachments[0].pixelFormat = .rgba8Unorm   // albedo
g.colorAttachments[1].pixelFormat = .rgba8Unorm   // normal（MRT）
g.depthAttachmentPixelFormat = .depth32Float
```

这段在做什么：声明本管线有两个颜色输出槽位（都是 rgba8Unorm——每像素 4 字节的普通颜色格式）加一个深度附件（存每个像素远近值的附件），与片元着色器的两个输出一一对应。

## How It Works

整个流程由两个 Pass 组成：

1. **G-Buffer Pass**：正常渲染几何，但片元（光栅化产出的候选像素）不输出最终颜色，而是把反照率与法线分别写进两张纹理。这是 MRT：一次 draw 同时产出两张全屏图。
2. **光照 Pass**：画一个铺满屏幕的四边形，片元着色器（GPU 上逐片元执行的小程序）逐像素读两张 G-Buffer，套一个简化的光照公式 `base * (0.3 + 0.7 * dot(N,L))` 输出最终颜色。

MRT 的关键在片元输出结构体——每个输出用槽位标明写到哪张目标：

```metal
struct GOutFrag {
    float4 albedo [[color(0)]];
    float4 normal [[color(1)]];
};
```

`[[color(0)]]`、`[[color(1)]]` 就是把结构体字段绑定到 Quick Start 里声明的两个颜色附件槽位，所以片元执行一次，两张纹理同时各得一个值。你在真实输出里看到的"红立方体 4.35%"，就来自对 `[[color(0)]]` 那张图回读统计。

法线的写入有个编码细节。法线每个分量范围是 [−1,1]，而 rgba8Unorm 只能存 [0,1]，直接写入会被截断。所以写入时编码 `*0.5+0.5`，光照 Pass 读回时解码 `*2−1`。这是 G-Buffer 的通用技巧；精度敏感的场景会改用 rg32Float 之类的浮点格式存法线，免掉编解码。

你在输出里看到的"朝上法线(地面) 53.0%"正是这条编码链路的验证：地面像素的法线 (0,1,0) 编码后是 (0.5,1.0,0.5)，回读解码比例正确，说明写读两端对齐。

加第 N 盏灯只是光照 Pass 的循环多跑一轮——G-Buffer 与几何遍完全不用动。这就是"几何成本与光源数量脱钩"落到代码里的样子。

## Pitfalls & Q&A

**1. `[[color(n)]]` 标错位置，直接编译失败。**
现象：着色器编译报错。原因：`[[color(n)]]` 是片元输出的属性，标到顶点输出结构体上类型系统不接受。解法：只在片元输出结构体（如上文 `GOutFrag`）上标槽位。

**2. 光照 Pass 输出全空。**
现象：G-Buffer 正常但最终画面没有内容。原因：全屏四边形的顶点 z 超出了 Metal 的 NDC（归一化设备坐标，GPU 使用的标准化坐标范围）z 范围 [0,1]，被裁剪。解法：全屏四边形顶点 z 放 0.5（本实验的做法）。

**3. 光照方向看起来不对、法线相关数据异常。**
现象：明暗与光源方向对不上，或回读统计里法线比例错误。原因：法线 [−1,1] 未编码直接写进 rgba8Unorm，负值被截断成 0。解法：写入 `*0.5+0.5`、读回 `*2−1`，两端必须成对出现。

**4. 分辨率一高帧率骤降。**
现象：G-Buffer 分辨率翻倍后性能明显下滑。原因：每像素要写多张、读多张全屏纹理，带宽随分辨率线性增长。解法：精简 G-Buffer——更少的附件或更小的格式。

**Q：G-Buffer 通常还存什么？**
反照率、法线、深度（或位置）之外，工业级管线常再存材质参数（roughness/metallic）。布局永远是带宽与质量的权衡，本实验只存前两样以保持最小可读。

**Q：透明物体为什么是延迟着色的难点？**
G-Buffer 每像素只存一份"最靠前的表面"，透明需要把前后多层混起来，而混合必须按绘制顺序当场做、无法推迟。通行解法是透明物体走单独的前向通道，与延迟管线叠加使用。
