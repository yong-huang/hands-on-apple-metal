# 08 · 颜色渐变：mix 是着色器里的万能胶水

> `mix` 是着色器（shader，运行在 GPU 上的小程序）里使用频率最高的函数之一：颜色过渡、权重混合、光照衰减、坐标变形都由它完成。本实验用它铺一条从红到蓝的全屏渐变，并讲清它与 `smoothstep`（在区间内做 S 形平滑过渡的函数）的分工。读完本篇，你能掌握把任意两个状态"平滑缝合"的通用写法。

## Background

在屏幕上做一条颜色过渡，传统做法有两条。一是预先在 CPU 上生成渐变位图——比如用 Core Graphics（Apple 的 CPU 绘图框架）画好，再当贴图用；二是让三角形两端的顶点（构成三角形的角点）各带一种颜色，由 GPU 在三角形面上自动插值。

两条路都有代价：位图方案改两端颜色就要重新生成图片；顶点色方案把颜色绑在几何数据上，改渐变要重建顶点缓冲，颜色分布也受限于几何的插值方式。

片元着色器（为每个候选像素计算颜色的 GPU 程序，片元即"候选像素"）逐像素算颜色的做法应运而生：两端颜色成为着色器参数，改渐变只需改两个数字。完成"从 A 平滑走到 B"的基本操作就是线性插值（在两端之间按比例取中间值）函数 `mix(a, b, t) = a * (1-t) + b * t`。

## What

`mix(x, y, t)` 对标量和向量一视同仁：对 `float3` 是逐通道线性插值。t=0 完全取 x，t=1 完全取 y，0.5 是中点。它是 GPU 硬件直接支持的指令级操作，几乎零成本。

一句话心智模型：**渐变 = 两端颜色 + 一个 0…1 的权重，`mix` 负责在中间走钢丝**。

可以把 t 想象成一根进度条：0 是起点色，1 是终点色，mix 沿直线轨道按进度取点。但和真实进度条不同的是，t 超出 [0,1] 时 mix 不会停在端点，而会继续沿直线外插（按直线趋势取区间外的值）出越界颜色——边界要自己守。

## When to Use

典型场景——在做什么事的时候会用到：

- 界面与背景渐变：按钮高亮、进度填充、3D 场景的天空背景。两端颜色随状态实时变化时，参数化的 mix 比预生成图片灵活。
- 光照衰减与雾效：把表面颜色按距离权重 mix 向环境色，权重通常先过一遍 smoothstep 整形。
- 动画缓动（easing，动画进度的快慢安排）：在两个姿态、两种颜色之间按 0…1 权重过渡，权重曲线决定节奏。

何时不用：

- 两端固定的一次性渐变：Core Graphics 预先生成一张图片（离屏渲染到内存）即可，不必逐帧算。
- 对色彩准确性要求高的图像处理：直接在 sRGB（显示器常用的非线性色彩编码）数值上插值，与线性空间插值观感不同，专业流程要交给专门的色彩管理环节。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 顶点色插值 | 颜色存在顶点里，GPU 在三角形上自动插值 | 每个顶点本就携带颜色（如地形、粒子） |
| CPU 预生成渐变位图 | 一次生成，运行时零计算 | 渐变固定不变，当贴图用 |
| Core Image 滤镜链 | 对已有图像做渐变合成、遮罩 | 图像后处理，而非逐帧程序化绘制 |
| 片元着色器 mix（本实验） | 逐像素计算，两端是着色器参数 | 渐变随时间或状态变化、需与其他逐像素效果叠加 |

## Quick Start

前置：macOS + Xcode（本实验基于 Metal，Apple 的底层 GPU 图形 API）。运行：

```bash
./gradient.sh               # 一条龙：build → observe → clean
AUTO_QUIT=6 ./gradient.sh observe   # 6 秒自动退出
```

控制台真实输出（节选）。Swift 程序本身不打印任何内容，结果看窗口画面。若窗口未出现，回到终端看 build 段是否报错——未安装 Xcode 命令行工具时 `swiftc` 命令不存在：

```
=====> [build] swiftc -O main.swift gradient.swift（几秒钟）
编译完成 → .build/gradient
=====> [observe] 运行实验（窗口会打开；……）
实验结束。
=====> [clean] 删除 gradient 等编译产物
已清理。
```

观察要点：全屏从左到右红→蓝的平滑渐变，两端颜色"停顿"、中段过渡更快（smoothstep 的 S 形曲线）。

验证方法：把权重从 `smoothstep(0,1,uv.x)` 换成裸的 `uv.x`——渐变变成严格匀速的线性过渡，首尾的"减速感"消失。这一 A/B 就是下文"为什么先 smoothstep 再 mix"要讲的差别。

着色器核心代码来自 `gradient.swift`，每个像素执行一遍。这段在做什么：把水平坐标整形成权重，再用权重混合红蓝两色：

```metal
float t = smoothstep(0.0, 1.0, in.uv.x);     // 权重整形：S 形 0…1
float3 color = mix(float3(1, 0, 0),          // 端点 A：红
                   float3(0, 0, 1),          // 端点 B：蓝
                   t);                        // 逐通道线性插值
```

- 第 1 行：`in.uv.x` 是 UV（把像素位置除以视口——即绘图窗口的像素区域——归一到 [0,1] 的坐标，左 0 → 右 1）的水平分量，`smoothstep` 把它整形成 S 形权重 t（两端慢、中间快，两端点值被钳在 0 和 1）。
- 第 2 行：`mix` 对红、蓝两个 `float3` 逐通道插值，得到该像素的最终颜色。

## How It Works

数据流三步：`uv.x` 经 `smoothstep` 变成首尾减速的权重 t → 红、蓝两端值送入 `mix` → 每像素输出一个插值色。屏幕上的渐变，就是这三步在几十万个像素上各跑一遍的结果。

为什么先 `smoothstep` 再 `mix`：裸 `uv.x` 做权重，渐变严格匀速，两端没有"呼吸感"；`smoothstep(0,1,t)` 的 S 形曲线把权重在首尾压慢、中段提速，渐变两端从容、过渡集中。

**`smoothstep` 不产生颜色，它只整形权重**——这个"权重整形"思路可以套用到任何混合场景（阴影边缘、雾效、动画缓动）。

每个片元独立执行整套公式，像素之间零通信。渐变不是"画"上去的，是每个像素各自算出了自己的颜色——图案是坐标的纯函数（同样的坐标必得同样的颜色），这种编程模型天然适合 GPU 大规模并行。

为什么把两端颜色写成字面量而不是顶点色：端点颜色成为**着色器参数**后，改渐变只需改两行代码，或改从 uniform（CPU 传入、所有像素共享的只读参数）读入，不用动顶点数据。参数化是程序化范式的红利。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- 画面出现比端点更极端的异常颜色。原因：`mix` 的 t 超出 [0,1] 不报错，会沿直线趋势外插出 >1 或 <0 的颜色值。解法：钳位（clamp，把数值限制在区间内）自己做；显示前也可统一 clamp，或经色调映射（tone mapping，把超出显示范围的亮度压缩进可显示区间）处理。
- `smoothstep` 结果不可预期。原因：`smoothstep(edge0, edge1, x)` 的 edge0 ≥ edge1 属于未定义行为（规范不保证结果）。解法：保证过渡带起点小于终点。
- 渐变的亮度过渡与人眼预期不一致。原因：直接在 sRGB 数值上插值，与线性空间插值观感不同。解法：对色彩有要求时区分色彩空间再插值（进阶话题）。

深入问答：

- **这类全屏图案实验的公共脚手架是什么？** 全屏四边形（铺满屏幕的两个三角形）+ 直通 vertex shader（顶点着色器，原样传递坐标不做变换）；只替换片元着色器函数，就能在棋盘、圆、渐变之间切换——一架多花。06、07 两个实验与此同构。
