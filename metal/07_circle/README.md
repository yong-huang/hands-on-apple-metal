# 07 · 距离场画圆：length + smoothstep

> 在片元着色器（为每个候选像素计算颜色的 GPU 程序，片元即"候选像素"）里，用"每个像素到圆心的距离"决定每个像素的颜色：`length`（求向量长度）算出距离，`smoothstep`（区间内平滑过渡）把硬边界换成一段平滑渐变带，锯齿随之消失。
>
> 读完本篇，你能得到一套可复用的抗锯齿画形写法，并理解距离场（SDF）思维为何是字体渲染、UI 图标与 ray marching（光线步进渲染）的共同地基。先说明一处与直觉不符的实测结果：窗口里画出来的是横向拉宽的椭圆而非正圆——源码宽高比占位导致的真实坑，见踩坑清单第 1 条。

## Background

在屏幕上画一个圆，最直接的写法是逐像素判定"在不在圆内"：用 `step(edge, x)`（x 小于 edge 取 0，否则取 1）这类硬判定函数。结果只有内外两种取值，边界像素非黑即白，放大看是一圈阶梯状的锯齿（aliasing，边界像素在两种颜色间硬切换造成的毛边）。

传统几何做法有另一层代价：用一组三角形逼近圆周，边缘有折线感，想更圆就得加密三角形；改一个半径，整套顶点（构成三角形的角点）数据都要重建。

按"到边界的距离"过渡的思路应运而生：在边界两侧留一小段过渡带做平滑插值，锯齿随之消失，改半径也只是换一个数字。这套思路后来成为字体渲染、UI 图标与 ray marching 的共同地基，画圆是它的最小入门案例。

## What

距离场（Signed Distance Field，简称 SDF，有向距离场）是一个"每个位置都存着到最近表面的距离"的标量场（每个位置对应一个数值的场）。"有向"指距离带符号：表面内侧为负、外侧为正，距离为 0 的等值线（场上取同一值的点连成的线）就是形状本身。

本实验取它的最简变体：只算每个像素到圆心的距离 d（恒为非负），圆定义为 `d < r` 的区域，用不到符号。

可以把 d 想象成一张高度图（每个位置存一个"海拔"数值的图）：圆心海拔 0，越远越高，海拔恰为 r 的那圈等高线就是圆。但和地图不同的是，这张高度图不是预先存好的数据，而是每个像素用 `length(uv)` 现场算出来的（uv：归一化屏幕坐标，定义见 Quick Start 的代码）。

一句话心智模型：**圆不是画出来的，是距离场 `d < r` 的等值线**。

## When to Use

典型场景——在做什么事的时候会用到：

- 界面里的圆形与软边光斑：血条底圈、进度环、粒子光点。半径可以用 uniform 参数（CPU 传入、所有像素共享同一份值的只读参数）传入，动画中改数字即可，不必重建几何（本实验简化为写死的常量）。
- 字体与图标的 SDF 渲染：把字形预先算成距离图存进纹理（GPU 上的图像数据），缩放到任意大小边缘都平滑，游戏界面与地图文字常用此方案。
- ray marching：整个场景用距离场描述，光线沿射线方向逐步查询距离求交，球、盒、环都是同一套写法派生。

何时不用：

- 只要一张静态圆图标：矢量绘图工具或 Core Graphics（Apple 的 CPU 绘图框架）预先生成一张图片即可，不必动用着色器（shader，运行在 GPU 上的小程序）。
- 圆要参与常规 3D 遮挡排序（按远近决定谁挡住谁）与光照：用三角形逼近的几何圆走渲染管线（GPU 从几何到像素的固定处理流程）更顺。
- 纯原生界面：SpriteKit / SwiftUI 自带形状视图，没有逐像素控制需求时更简单。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CPU 绘制（Core Graphics） | CPU 出静态位图，不走 GPU 逐像素 | 一次性图标、离屏导出 |
| SpriteKit / SwiftUI 形状 | 框架现成 shape，无需写着色器 | 原生界面元素，无自定义像素需求 |
| SceneKit | 现成 3D 场景图，球体几何与光照内置 | 需要完整 3D 场景而非屏幕上的 2D 形状 |
| 几何圆（三角形逼近） | 有真实几何，可参与深度与光照 | 圆要和其他 3D 物体统一渲染时 |
| 距离场（本实验） | 逐像素计算，参数即时可调，天然抗锯齿 | 软边、动画形变、程序化形状 |

## Quick Start

前置：macOS + Xcode（本实验基于 Metal，Apple 的底层 GPU 图形 API）。运行：

```bash
./circle.sh               # 一条龙：build → observe → clean
AUTO_QUIT=6 ./circle.sh observe   # 6 秒自动退出
```

控制台真实输出（节选）。Swift 程序本身不打印任何内容，结果看窗口画面。若窗口未出现，回到终端看 build 段是否报错——未安装 Xcode 命令行工具时 `swiftc` 命令不存在：

```
=====> [build] swiftc -O main.swift circle.swift（几秒钟）
编译完成 → .build/circle
=====> [observe] 运行实验（窗口会打开；……）
实验结束。
=====> [clean] 删除 circle 等编译产物
已清理。
```

观察要点：窗口中心一个边缘柔和的椭圆——横向拉宽的，不是正圆；外接框比例与窗口一致（800×600 下实测约 648×486 像素），边缘是一段平滑渐变带，圆外是背景色。这不是显示故障：源码把宽高比 aspect 写死为 1.0，横向没有按窗口比例校正，详见踩坑清单第 1 条。

验证方法：把 `smoothstep` 换成 `step` 重编译——边缘立刻锯齿化。这一个 A/B 对比就是抗锯齿原理最直观的实验。

着色器核心代码逐字摘自 `circle.swift`（保留原注释），每个像素都会执行一遍。这段在做什么：把坐标平移到圆心、算出到圆心的距离、把距离变成 0…1 的权重：

```metal
// Transform UV coordinates to center origin
float2 uv = in.texCoord * 2.0 - 1.0;

// Adjust for aspect ratio to keep circle round
float aspect = 1.0; // Will be passed as uniform later
uv.x *= aspect;

// Calculate distance from center
float dist = length(uv);

// Smooth circle with anti-aliasing
float radius = 0.8;
float smoothness = 0.02;
float circle = 1.0 - smoothstep(radius - smoothness, radius + smoothness, dist);
```

逐行拆解：

- `uv` 三行：`in.texCoord`（GPU 在全屏四边形上逐像素插值出的 0…1 坐标）先乘 2 减 1，把原点搬到屏幕中心、范围变成 ±1；`aspect`（宽高比，宽与高之比）写死为 1.0，横向没有按窗口比例校正——形状因此是横向拉宽的椭圆（踩坑清单第 1 条）。
- `dist` 行：`length(uv)` 求向量模长，即该像素到圆心的直线距离 d。
- `radius` 与 `smoothness` 两行：半径 0.8、过渡半宽 0.02，都是编译进着色器的常量——程序里没有任何 uniform，CPU 不传参数，改数值只能改源码重编译。
- `circle` 行：`smoothstep` 在过渡带内插值，`1.0 -` 翻转方向，让圆心实、圆外虚。
- 这段之后是上色与光晕：`mix(bgColor, circleColor, circle)` 按权重混合深灰背景与蓝色前景；`float glow = exp(-dist * 4.0) * 0.3; color += glow * circleColor;` 是随距离指数衰减的淡蓝光晕，与抗锯齿机制无关。

## How It Works

数据流四步：居中 UV（各分量范围 ±1 的屏幕坐标）→ `length(uv)` 得每像素到圆心的距离 d → d 与半径 r 一起送进 `smoothstep` → 输出 0…1 的混合权重。每个像素手里拿着一个"以圆心为原点的向量"，第 2 步对它取模长。屏幕上的这个图形，就是这四步在每个像素各跑一遍的结果。

机制核心是一行（对照 Quick Start 里的完整片段）：

```metal
float circle = 1.0 - smoothstep(radius - smoothness, radius + smoothness, dist);
```

为什么这样写：

- `smoothstep(a, b, x)` 在 [a,b] 区间内做三次多项式平滑过渡（两端慢、中间快的 S 形曲线），区外钳位（超出范围按边界值取）到 0 或 1。
- 过渡带取 `radius - smoothness` 到 `radius + smoothness`：边界像素拿到中间值，硬切换变成加权平均（盒式滤波，对边界附近的颜色取平均）——这就是锯齿消失的机制。
- 前缀 `1.0 -`：smoothstep 自 0 涨到 1，而圆内应为 1。翻转后 d 越小值越大，圆心实、圆外虚。
- 本实验的 `smoothness` 写死为 0.02：过渡带宽 0.04 个 UV 单位，默认 800×600 窗口里横向约 16 像素、纵向约 12 像素，随窗口尺寸等比变化——比"约 1 像素"的理想值宽一个数量级，边缘偏糊但无锯齿。黄金准则是带宽约 1 像素且随分辨率自适应，做法见踩坑清单第 2 条。

## Pitfalls & Q&A

踩坑清单（现象 + 原因 + 解法）：

- 画出来是横向拉宽的椭圆，不是正圆。原因：`aspect` 写死为 1.0（源码注释自述"以后再作为 uniform 传入"），横向半径没有乘视口（绘图窗口的像素区域）宽高比，x、y 方向每单位 UV 对应的像素数不同。解法：把窗口尺寸作为 uniform 传入，对 uv.x 乘以真实宽高比（宽/高），椭圆即成正圆。
- 边缘发糊，窗口缩放后跟着变。原因：过渡带写死成常数 0.02，物理像素数随窗口大小变化，800×600 下已宽达 12–16 像素。解法：让带宽随分辨率自适应——用 `fwidth(d)`（求相邻像素间数值变化率的内置函数）或 1/分辨率计算，压到约 1 像素；带宽小于 1 像素仍有锯齿，宽太多边界发糊。
- 圆内外整体反转。原因：`smoothstep` 的过渡带两端参数写反，或漏写 `1.0 -` 前缀。解法：核对调用是 `(radius - smoothness, radius + smoothness, dist)` 加 `1.0 -`。

深入问答：

- **距离场怎么推广到别的形状？** 环 = 把 d 换成"到圆周的距离" `abs(d - r)`；多个形状的并/交/差 = 对两个距离场逐点取 min/max，过渡带依然平滑。全程零几何，改参数即时生效，是程序化建模（用数学表达式生成形状，而非手工建模）的基础。
- **距离场画圆和几何圆如何取舍？** 距离场胜在零几何、参数即时可调、天然抗锯齿；几何圆胜在能参与深度排序与光照。只在屏幕上画形状选前者，要进 3D 场景统一渲染选后者。
