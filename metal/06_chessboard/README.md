# 06 · 片元着色器棋盘格：fract/step 的空间重复

> 想画图案又不想堆几何？给 GPU 一个全屏四边形当画布，让片元着色器逐像素用数学公式决定颜色。本实验用两个内建函数 `fract` + `step`，零几何成本画出一块规整的黑白棋盘。

## Background

此前的画面颜色都来自顶点：给每个顶点配一种颜色，GPU 插值铺出色块。顶点色只能表达"大面渐变"——想让画面有细节，就得靠几何去拼。

拼几何在画图案时会撞墙：棋盘、条纹、圆点这类规则图案，每个色块都要顶点和三角形去描述，一块 8×8 的棋盘就是上百个三角形；想改密度还得重建几何。图案越细，顶点数越爆炸，而 GPU 的大部分算力根本没被用上。

另一种范式应运而生：程序化图案（procedural pattern）——不给图案建几何，而是让每个像素根据自身坐标套公式算颜色。公式是纯计算，改密度只改一个数字，分辨率多高都不失真。

## What

程序化图案是不依赖贴图与额外几何、由公式逐像素算出颜色的图案。载体是全屏四边形（Fullscreen Quad）：铺满屏幕的两个三角形，顶点着色器几乎直通（passthrough，把输入原样传给下一站）。

四边形的唯一使命是产生足够多的片元（fragment，候选像素），让 fragment shader 有发挥的画布——这也是后处理（在整幅画面渲染完成后对每个像素再加工的效果，如调色、暗角）与程序化图案的标准载体。

本实验用到两个内建函数：`fract`（取小数部分）与 `step`（按阈值输出 0 或 1）。

可以把 `fract` 的作用想象成一面无限重复的花砖墙：每块砖内部花纹完全相同，坐标除以砖宽就得到砖内位置。但和真砖墙不同的是，这里的"砖"没有任何边界几何，是公式在数学上折叠出来的，改一个数就能变密变疏。

棋盘的完整数据流：顶点传来的 0…1 坐标（着色器里叫 texCoord）→ 乘格子数 N（本实验为 10）后 `fract` 折叠进 0…1（空间重复）→ 两个方向各经 `step` 判 0/1，求和折成奇偶 → 黑白上色。心智模型：**fract 把无限平面折叠进一个格子，step 在格子内一分为二**。

## When to Use

这节回答：什么时候用公式生成图案，什么时候换别的办法。

典型场景：

- 规则图案背景：棋盘、条纹、圆点、网格线——周期明确、能用坐标公式描述的图案。
- 后处理效果：全屏四边形 + fragment shader 是调色、暗角等整屏效果的标准画布。
- 参数化调试可视化：密度、相位都是函数参数，改一行就能验证。

何时不用：照片级或手绘素材直接用贴图（纹理）更直接；自然纹理（木纹、岩石）纯公式推导成本高，通常配合噪声函数或贴图。程序化图案相比贴图的优势是零内存占用、任意分辨率无失真、参数即时可调；代价是每个像素都要付一遍 ALU（算术逻辑单元，GPU 的计算单元）开销。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| CPU 绘制 | CPU 逐像素算好再上传 GPU；每帧开销大 | 静态小图 |
| 贴图（纹理） | 素材直接可用；占内存，缩放会失真 | 照片级或复杂手绘素材 |
| SpriteKit / SceneKit | 图案做成纹理贴给精灵/模型 | 标准 2D/3D 内容 |
| Metal 程序化图案 | 零贴图内存、任意分辨率、参数即时可调 | 规则图案、参数化背景、后处理 |

## Quick Start

前置条件：一台支持 Metal 的 Mac，实验目录自带 `chessboard.sh` 脚本；程序会打开一个窗口。

```bash
./chessboard.sh               # 一条龙：build → observe → clean
AUTO_QUIT=6 ./chessboard.sh observe   # 6 秒自动退出
```

观察要点：全屏黑白棋盘格，格子规整无锯齿感（远看）；拖拽窗口大小，格子数量不变——密度由着色器里的固定乘数决定，变的只是格子尺寸。

验证方法：把着色器里的乘数改大（`texCoord * 10.0` 的 10 改成 20），重编译后格子翻倍变密——证明图案完全由公式生成，与几何无关。

下面是片元着色器的核心代码（Metal Shading Language，Apple 的着色器语言），它在做的事：乘出重复单元 → 逐方向判 0/1 → 求和折成奇偶 → 黑白上色。

```metal
// 用顶点传来的 texCoord 生成棋盘（摘自 chessboard.swift 的片元着色器）
float2 coord = in.texCoord * 10.0;               // 0…1 坐标 ×10：划出 10×10 个重复单元
float2 grid = floor(coord);                      // floor（向下取整）：格子编号，源码保留了此行但判定未用到
float2 pattern = step(0.5, fract(coord));        // 每个方向：格内位置过半记 1，否则记 0
float chess = pattern.x + pattern.y;             // 两个方向的 0/1 相加：0、1 或 2
chess = fract(chess * 0.5);                      // 折叠：0→0、1→0.5、2→0
chess = step(0.5, chess);                        // 折回 0/1：和恰好为 1（奇）时输出 1

// 黑白上色：0 取深灰 0.1，1 取亮白 0.9
float3 color = mix(float3(0.1, 0.1, 0.1), float3(0.9, 0.9, 0.9), chess);
return float4(color, 1.0);
```

## How It Works

这节拆开公式里每一步的机制。

`fract(x)` 取小数部分，把任意大的坐标折叠进 [0,1)。顶点传来的 texCoord 横竖已归一化在 0…1，乘格子数 10（代码里的 `10.0`），经 `fract` 后每个重复单元内部都得到一套完整的 0…1 局部坐标——这就是"无限重复"的实现原理，乘数控制重复密度。

你在验证方法里把乘数从 10 改到 20 后格子翻倍，就来自这一步。

`step(edge, x)` 返回 `x >= edge ? 1 : 0`，输出只有两个值、边界锐利。

棋盘判定分两步：两个方向各自 `step(0.5, fract(coord))` 判出 0/1，相加得 0、1 或 2，再经 `fract(chess * 0.5)` 与 `step` 折回 0/1——恰好一个方向过半（和为 1）时输出 1。

相邻方块的奇偶天然相反，黑白因此交错；0.5 的阈值还把每个重复单元再一分为二，屏幕上每边的方块数是乘数的两倍。

它没有过渡带——这正是棋盘需要的"硬朗"；要柔和边缘（画圆、渐变）时应换成带平滑过渡的 `smoothstep`。

为什么用顶点传来的 texCoord 而不是片元的屏幕像素坐标 `in.position.xy`：texCoord 横竖已归一化在 0…1，乘固定乘数后格子密度与窗口大小无关；`position` 的单位是像素，直接进公式会让格子数跟着分辨率走，必须先除以视口尺寸归一化（坑一的场景）。

## Pitfalls & Q&A

坑一：缩放窗口时格子数跟着变。
现象是同一块棋盘，窗口大小一改密度就变。原因是公式用了屏幕像素坐标（`in.position.xy`）却没先归一化，坐标直接跟分辨率走——本实验用顶点传来的 texCoord，所以没这个问题。解法：改用 texCoord（天然 0…1），或先除以视口尺寸归一化再乘格子数。

坑二：格子边界像素偶发闪烁。
现象是静止画面上边界处偶有像素跳色。原因是奇偶判定建立在浮点数上，格子边界处 `fract` 的值存在精度抖动。解法：生产代码常用 `floor` 后的整数奇偶判定代替浮点比较。
