# 03 · 向量点积规约：两阶段树形归并

> 规约（reduction）把一百万个数加成一个数——GPU 线程第一次需要协作的算子。本篇用两阶段树形规约实现向量点积，读完可掌握 threadgroup 共享内存、barrier 同步与树形归并：所有归约类算子（求和/最大值/直方图）的公共骨架。

## Background

这节解释：求和这个看起来最简单的运算，为什么在 GPU 上需要一套专门的协作算法。

没有协作机制时，CPU 上的求和就是一个顺序循环：一个变量从第 0 个数一路累加到第 N 个。想并行化，最朴素的做法是开多线程共用一个累加变量，每次加法前先加锁——一锁一加。

痛点在一百万个数求和的场景：单线程要做 O(N) 步；而一锁一加的朴素并行里，所有线程挤在同一把锁后面排队，锁竞争吃掉并行化带来的全部收益。求和是点积、损失函数（衡量机器学习模型预测与正确答案差距的函数）、统计量的内层操作，它跑不快，上层运算就整体跑不快。

树形规约应运而生：把 O(N) 步的串行累加变成 log₂(N) 步的两两合并，配合 GPU 的组内同步原语完成协作。理解它，才能理解 simdgroup（线程组内更小的 32 线程硬件单元）、threadgroup 内存这些硬件设施为什么存在。

## What

规约（reduction）是把一组数按某个二元运算（加法、取最大值等）合并成单个值的计算。本篇的载体是向量点积：两个等长向量对应元素相乘再求和——乘的部分是逐元素运算（线程独立），求和的部分就是规约（线程协作）。

一句话心智模型：**组内做树，组间做接力**。

可以把组内树形规约想象成淘汰赛：每轮两两配对相加（对手相距半个队列，逐轮靠近），"参赛者"每轮减半，256 → 128 → … → 1，8 轮后只剩总冠军（总和）。但和淘汰赛不同的是，每轮结束所有线程必须全员到齐才能开始下一轮（由 barrier 同步保证），否则有人会拿"半成品"相加。

一百万个数据一个组装不下，所以完整流程分两个阶段：1M 个乘积先由 4096 个组各自做组内树形规约，压成 4096 个部分和；再由一个组接力收尾，归并成一个结果。两个阶段的细节见 How It Works。

## When to Use

这节给出判断：什么样的计算值得上规约算法，什么场景有更简单的选择。

典型场景：

- 在把大量数据合并成少量结果时——求和、求最大值、统计直方图，以及机器学习里损失函数计算的内层点积。
- 在理解 MPS、MLX 等框架的 reduce 类接口时——它们底层就是本篇这类两阶段树形结构。
- 在为其他 GPU 算子搭验证流程时——"CPU 算期望值 + GPU 算实际值 + 相对误差判定"是浮点算子的通用验证法。

何时不用：

- 数据量小（单组就能装下、总量几千以内）时，CPU 顺序累加更快——GPU 派发的固定开销会超过规约本身的收益。
- 数据已在 CPU 且只做一次求和时，不必搬去 GPU——往返搬运的代价不划算。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| CPU 顺序累加 | 单线程 O(N) 步，无同步开销 | 数据量小、追求代码最简 |
| CPU 多线程分块 | 多核各算一块再合并，需处理合并逻辑 | 中等数据量、数据已在内存里 |
| vDSP 等向量化库 | 现成的 CPU 向量化求和接口，无需手写 | CPU 上的求和，不想自己管理线程 |
| MLX 等高层框架的 `.sum()` | 一行调用，框架内部自动做 GPU 归约 | 机器学习实验，不关心实现细节 |
| 手写 GPU 树形规约（本篇） | 两阶段树形，利用共享内存与组同步 | 数据量大、数据已在 GPU 或需与其他 GPU 算子串联 |

## Quick Start

前置条件：一台装有 Xcode 的 Apple Silicon Mac。实现在 `reduction.swift`：双内核（kernel，运行在 GPU 上的函数；这里用两个 kernel 分别负责两个阶段）加 CPU 端验证。

```bash
./reduction.sh           # 一条龙：build → observe → clean
```

真实输出：

```
GPU 规约结果: 58710732.00（CPU 期望 58712152.00，相对误差 2.42e-05）
两阶段: 4096 组 × 256 线程 → 4096 部分和 → 1；耗时 2.3 ms
✅ 规约验证通过
```

验证方法：浮点求和有顺序误差，用相对误差（<1e-3）而非逐位比对判定——这也是浮点算子验证的通用准则。

输出的第二行就是两阶段数据流的浓缩：`4096 组 × 256 线程 → 4096 部分和 → 1`；`2.3 ms` 是整个规约的耗时。每个数字与哪段代码对应，见 How It Works。

## How It Works

这节按数据流顺序拆解：threadgroup 内存是什么、组内树怎么长、两阶段如何接力、取数模式为何重要。

**threadgroup 内存：组内共享的片上黑板**。声明 `threadgroup float scratch[256]` 即可在 kernel 里拿到一块同组线程共享的片上内存，比显存快一个量级。规约的中间值全部住在它里面，显存流量只有首尾两次——读入乘积、写回部分和。

**组内树形规约**。每步把相距 `s` 的两个数相加，活跃线程数减半（256 → 128 → … → 1，共 8 步）；每步之后放一个 barrier，保证没人用半成品相加：

```metal
threadgroup_barrier(mem_flags::mem_threadgroup);   // 组内同步点
for (uint s = lsize/2; s > 0; s >>= 1) {
    if (lid < s) scratch[lid] += scratch[lid + s];
    threadgroup_barrier(mem_flags::mem_threadgroup);
}
```

为什么这样写：`s` 从组大小的一半开始每轮折半，编号小于 `s` 的线程把"自己 + 对面距离 `s` 的邻居"合并写回自己的槽位——与淘汰赛同理，只是配对距离每轮减半。`threadgroup_barrier` 的语义是组内全员到齐才放行，所以它必须放在循环体内而不是循环外。

**两阶段接力**。第一阶段的 4096 个组各交出一个部分和；第二阶段由单个组收尾：每个线程先跨步串行累加 16 个部分和（4096 = 256 × 16），把 4096 压到 256，再走一遍组内树形归并。

这里没有"全局 barrier"可用——组与组之间无法同步——所以用"部分和 + 二次内核"的结构代替全局同步。

**取数模式**。相邻线程要取相邻地址（`data[gid]`），这样硬件才能合并访存（coalescing，把多次相邻访问合并成更少的显存事务）让带宽打满；取数模式错了，规约逻辑再对也快不起来。

## Pitfalls & Q&A

这节收集两个真实踩过的坑，和一个关于验证阈值的问答。

**坑 1：收尾阶段结果差了 94%**。现象：GPU 结果与 CPU 期望差距巨大（实测差 94%）。原因：第一版收尾内核漏了"每线程跨步串行累加 16 个"这一步，只对前 256 个部分和做了树形归并，剩下的 3840 个根本没参与。解法：先跨步串行累加把 4096 压到 256，再做树形归并——两步缺一不可。

**坑 2：偶发性错误结果，且每次位置不同**。现象：结果时对时错。原因：漏写或放错 `threadgroup_barrier`，产生竞态——有线程读到别的线程尚未写入的 scratch 槽位。解法：每步归约之后放一个 barrier，确保"上一轮全部写完，下一轮才开始读"。

**Q：为什么用相对误差而不是逐位比对？** 浮点加法不满足结合律，求和顺序不同结果就不同，1M 元素下 ~1e-5 量级的相对误差属正常现象。逐位相等反而是错误的检验目标——它意味着 GPU 与 CPU 碰巧用了完全相同的顺序，而不能说明逻辑正确。阈值取 <1e-3 留有余量即可。
