# 23 · 自定义 GEMV 内核

> LLM（大语言模型）解码期（batch=1，一次只算一个位置）的算力大头是 GEMV（General Matrix-Vector multiplication，矩阵-向量乘 y = W·x）。读完你能写出"一个线程组承包一行"的 GEMV 内核——组内分摊乘加、共享内存归约，与 numpy（Python 的数值计算库）对答案、与 MLX 原生实现比性能。

## Background

LLM 逐个生成文字的阶段叫解码期：每生成一个位置，都要把模型里所有权重矩阵与当前向量做一遍矩阵-向量乘。此时批大小（batch，一次同时处理的样本数）为 1，权重矩阵巨大而输入向量只有一个。

通用矩阵乘内核面向"矩阵乘矩阵"设计。batch=1 时用它，计算设备的算力大量闲置——数据还没从显存搬完，运算单元就等在那里。这个场景的瓶颈不在算而在搬数据，值得为它写专用内核。

GEMV 是"归约 × GEMM（general matrix multiplication，通用矩阵乘）"的合体练习：既要有每行的点乘结构，又要有组内协作。跑通它，自定义内核就从"玩具"进入了"生产形态"。

## What

GEMV 定义：y = W·x，W 是 [M,K] 矩阵、x 是 [K] 向量，输出 y 是 [M] 向量——每行与 x 做一次点积（对应元素相乘再求和）。

一句话心智模型：**一行一组，组内吃干**。可以把内核想象成流水线上的 256 人小组承包矩阵的一行：每人先各算一小段乘加（分摊），再把各人的小计汇总成一个总数（归约，reduction，把一组数合并成一个数）。失效边界：真实生产内核还有更快的组内汇总方式，教学版用的是共享内存加树形归并。

| 部件 | 角色 |
|---|---|
| W [M,K] | 权重矩阵，数据读取的大头 |
| x [K] | 输入向量 |
| y [M] | 输出，每行一个点积结果 |
| 线程组 | 一个组承包一行，组内协作 |

## When to Use

典型场景：

- **LLM 解码期优化**：batch=1 逐位置生成时，把矩阵-向量乘换成专用内核，尽量占满显存带宽。
- **学习带组内协作的内核**：需要共享内存与同步的算子，GEMV 是标准练习题。
- **带宽基准实验**：GEMV 是典型的带宽受限算子，适合测量显存带宽利用率。

何时不用：

- batch 大于 1 的训练或批量推理：计算变成矩阵乘矩阵（GEMM），用通用 matmul 内核更合适。
- 矩阵很小的玩具场景：直接调框架或 numpy，不值得写内核。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 自定义 GEMV 内核 | 面向 batch=1 定制，可持续调优 | 解码期专用优化 |
| MLX 原生 matmul | 通用实现，带 simd（单指令多数据并行）优化 | 一般场景与批量计算 |
| MPS 等系统加速库 | Apple 成熟的 GPU 算子库 | 想用系统库而非自研 |
| numpy | CPU 计算，无 GPU 并行 | 生成对照答案 |

## Quick Start

前置条件：macOS 与 Apple Silicon 设备，装有 MLX（Apple 为 Apple Silicon 出品的机器学习框架）。

```bash
./gemv.sh           # 一条龙
```

真实输出：

```
自定义 GEMV vs numpy 最大绝对差: 2.29e-05
自定义 GEMV: 0.182 ms | MLX 原生 matmul: 0.105 ms
✅ 验证通过：数值一致，性能同量级（原生内核有 simd 优化，教学版不必追平）
```

验证方法：与 numpy 矩阵乘的最大绝对差 < 1e-3；性能与原生同量级即可（教学版以正确性为先）。

关键代码（节选，省略号处是共享内存声明与树形归并；这段在做什么：`gid` 定位本组负责的行，for 循环从 `lid` 起步、每次跨 `lsize` 分摊 K 维乘加，最后由 `lid == 0` 的线程把组内归并出的结果写进 y）：

```python
gemv_kernel = metal_kernel(name="my_gemv",
    input_names=["w", "x", "k_dim"], output_names=["y"],
    source="""
    uint gid = threadgroup_position_in_grid.x;   // 一组一行
    ...
    for (uint k = lid; k < K; k += lsize) acc += row[k] * x[k];
    ...
    if (lid == 0) { y[gid] = scratch[0]; }
    """)
```

## How It Works

**一组一行。** `gid = threadgroup_position_in_grid` 定位本组负责哪一行；行内线程按 `lid`（组内编号，0 到 lsize−1）跨步（每隔 lsize 取一个 k）分摊 K 维乘加。每个线程攒自己的部分和，互不写同一格——组内天然无竞争。

**组内归约。** 各线程的部分和写入 `threadgroup float s[256]`——threadgroup 内存是组内线程共用的一块高速小内存；再树形归并（两两相加、范围折半）收缩到 s[0]。这是 lab 03 规约骨架的原样复用，验证了骨架的可迁移性。

**标量参数也是数组。** 维度 K 通过一个 uint32 数组传入（`input_names` 里声明为 k_dim），内核体里 `K = kdim[0]`——标量也走数组通道，这是 MLX 的统一 IO 哲学。

**grid 语义。** `grid=(M*256,1,1)` 是总线程数：M 行 × 每行 256 线程。lab 22 的坑在此复发一次——grid 是总线程数，不是组数。

**性能从哪来、差在哪。** GEMV 每 2 FLOP（浮点运算次数）只摊约 4 字节读取（读 W 的一行加 x 一列），算术强度 0.5——耗时几乎全由数据搬运决定，即带宽受限。

优化重点是占满带宽而不是省计算。你在输出里看到的 0.182 ms 对 0.105 ms，差距来自原生内核的 simd 级优化；教学版以正确性为先。

## Pitfalls & Q&A

**坑：grid 忘了乘每行线程数。** 现象：输出 y 只有前一部分行被更新，其余保持初始值且不报错。原因：grid 写成了 (M,1,1)，把"组数"当成了"总线程数"。解法：grid=(M*256,1,1)——行数乘以每行线程数。

**Q：组内跨步分摊的好处？** K 远大于组大小时负载均匀分到每个线程，避免个别线程累加到很晚的单线程长尾。

**Q：如何向原生内核看齐？** 路线图：simd shuffle 归约（SIMD 组内直接交换寄存器求和，不经过共享内存）、多行并行、float4 化（一次装载 4 个 float）。教学版到生产版依次补齐。
