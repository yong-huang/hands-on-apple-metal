# 30 · 算子基准测试框架

> 会写算子（operator，模型计算的基本单元）只是开始，会**测**算子才算专业：预热（计时前先空跑几轮）吸收编译成本、多轮取 min/median 抵消抖动（其他进程等随机干扰）、性能与精度双回归（改动后重跑，防止倒退）。读完你能把这三个计时纪律固化成一个可复用的基准测试（benchmark，给代码性能做标准化测量的方法）框架，并读懂一份延迟/算力/带宽报告。

## Background

测性能最朴素的做法是"跑一次、掐秒表"：在代码前后各记一次时间，取差值就是结果。

三个坑等着这种做法：

- 第一次运行包含内核（kernel，GPU 上大规模并行执行的小函数）选择、编译、缓存加载的冷启动（首次运行因一次性成本而变慢的现象）开销，数字可能差 10 倍。
- 单次计时受系统抖动（其他进程、后台任务等随机干扰）影响，好坏全凭运气。
- 只看时间不看结果——优化出一个“算得快但算得错”的内核，还浑然不觉。

用冷启动数字做优化决策，方向直接跑偏：错误的基准比没有基准更糟。

基准测试因此形成三条纪律：预热（正式计时前先空跑几轮，把首次运行的一次性成本消耗掉）、多轮统计、精度回归（regression，每次改动后重跑检查，防止结果倒退）。本实验把三原则固化成一个可复用框架，给 MatMul（矩阵乘）从 128 到 2048 全尺寸段跑一份可信报告。

## What

基准测试框架是一种把计时纪律固化的测量工具：预热、多轮统计、性能与精度同报，产出延迟/算力/带宽表，并给每个数字附上正确性证明。

一句话心智模型：**性能报告必须附带精度签证**。

可以把基准测试想象成体检：预热是热身（避免第一组数据失真），多轮取 min/median 是多次测量取代表值，精度回归是化验单（指标没对上，速度再快也不算数）。但和体检不同的是，基准的"正常范围"没有统一参考值——不同硬件、不同规模各不相同，要靠跨规模曲线自己定位瓶颈。

报告里的四个指标：

| 指标 | 含义 | 回答的问题 |
|---|---|---|
| 延迟 | 一次调用的耗时（min 与 median 双报） | 快不快 |
| 算力 | 每秒完成的浮点运算次数（TFLOPS，每秒 10^12 次浮点运算） | 计算单元用满没有 |
| 带宽 | 每秒读写内存的数据量 | 内存跟得上没有 |
| 相对误差 | 与 numpy（Python 的数值计算库，这里提供对照结果）的偏差比例 | 结果对不对 |

## When to Use

典型场景：

- 优化算子前后对比效果时——没有可信基准，优化方向全凭感觉。
- 做选型决策时——自研内核与现成库（PyTorch、MLX）谁快，需要同口径的数字。
- 给算子做回归验证时——每次改动后跑一遍，性能与精度双回归防止"改好了速度、改坏了结果"。

何时不用：

- 只想粗略感受快慢、不做决策：Python 内置 timeit 或手动计时足够。
- 一次性脚本：搭框架的成本大于收益。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 手动掐表（`time.perf_counter` 前后取差） | 零成本，但含冷启动与单次抖动 | 粗略感受量级 |
| Python 内置 timeit | 自动多轮取统计，面向 Python 代码片段 | 测纯 Python 逻辑 |
| 成熟框架自带工具（如 PyTorch 的 `torch.utils.benchmark`） | 统计规范，绑定在对应框架内 | 已在对应框架内做基准时 |
| 本框架（bench + 全尺寸扫描 + 精度回归） | 预热、min/median、GPU 同步与精度签证齐全 | 测 GPU 算子、要出报告 |

## Quick Start

本实验是 Python + MLX 程序，需要一台 Apple Silicon Mac。一条命令跑完全尺寸扫描与双回归：

```bash
./benchmark.sh           # 一条龙
```

真实输出：

```

   512³     0.35ms       0.34ms       7.8T       34G
  1024³     1.12ms       1.10ms      19.2T       69G
  2048³     8.72ms       8.66ms      19.3T      139G
峰值算力: 19.3 TFLOPS @ 2048³（FP32）
精度回归: 512³ 相对误差 7.69e-04（< 1e-3 通过）
✅ 基准框架验证通过：性能 + 精度双回归
```

验证方法：512³ MatMul 与 numpy 对照的相对误差 < 1e-3——被测代码的正确性也是基准的一部分。

怎么读这份输出：延迟中位与最优并排（典型体验 vs 能力上限）；算力随规模增长、1024³ 后趋平（19.2T → 19.3T）；带宽随规模上升；最后一行给出精度签证——7.69e-04 的相对误差低于 1e-3 阈值，报告才算数。

## How It Works

框架固化的三大纪律——预热、多轮统计、性能与精度同报——都落在这一个函数里。

### 核心代码

```python
def bench(fn, iters=20, warmup=3):
    for _ in range(warmup): mx.eval(fn())          # 预热
    times = []
    for _ in range(iters):
        t0 = time.perf_counter(); r = fn(); mx.eval(r)
        times.append((time.perf_counter() - t0) * 1000)
    return min(times), sorted(times)[len(times)//2]
```

这段在做什么：

- 预热 3 轮：首轮触发内核选择、编译、缓存加载，预热把它们吸收在计时之外。
- 计时 20 轮：`time.perf_counter()` 是纳秒级精度的单调时钟，适合测耗时；`mx.eval(r)` 强制 MLX（Apple 的数组计算框架）真正执行——MLX 默认惰性执行（先构建计算图、取值时才算数），没有这一行测到的只是建图时间。
- 返回 min 与 median：`sorted(times)[len(times)//2]` 取中位数（把耗时排序后取正中间那个）。

为什么这样写：min 是受干扰最小的那次、代表硬件能力上限；median 代表典型体验。只报其一都会误导优化决策——双报防"单点好运"。

### 三个指标的换算

TFLOPS = 2n³ / 时间（n×n 矩阵乘共 2n³ 次浮点运算：每个输出元素 n 次乘加，一次乘加算 2 次）；带宽 = 3n²×4 / 时间（读 A、读 B、写 C 各 n² 个 FP32（32 位浮点，4 字节）元素）。

看带宽随规模的增长，可以判断算子何时进入 compute-bound（计算受限：速度上限由计算能力而非数据搬运决定）。

### 读报告的方法

三条判读规则：

- 小规模延迟高 → 启动开销主导（可用 batching 缓解，即把多个小任务合成一批执行、摊薄固定开销）。
- 大规模算力趋平 → compute-bound，对照硬件上限（lab 06 实测 2.26T 上限；19.3T 本是 FP16（16 位浮点）的量级，本报告为 FP32）。
- 带宽远低于 220 GB/s → 查布局与分块（tiling，把大矩阵切成小块以改善访存的工作方式）。

这就是 Roofline（性能上限模型：实际速度受算力或带宽中较低者封顶）视角下的读法：先定位瓶颈在哪一侧，再决定往哪优化。

## Pitfalls & Q&A

**坑：冷启动数字混进报告。** 现象：第一次跑出的延迟比后续差好几倍，据此做优化决策方向跑偏。原因：首轮触发内核选择、编译、缓存加载，这些一次性成本远大于算子本身。解法：正式计时前预热 3 轮，把一次性成本吸收掉。

**坑：只测性能不测精度。** 现象：内核越改越快，最终结果却悄悄错了。原因：性能优化常改数值路径（累加顺序、近似公式），误差随之漂移；没有参照就不会被发现。解法：性能与精度同报——精度回归是报告的"签证"，每次基准都必须带着它。

**问：优化到什么程度算到头？** 当带宽逼近内存上限、或算力逼近 compute-bound 上限（Roofline 给出封顶）时，继续优化收益递减。先用报告定位瓶颈在哪一侧，再决定投入。
