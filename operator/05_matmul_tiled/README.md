# 05 · 矩阵乘法 Tiled：共享内存分块复用

> Naive GEMM 慢的原因只有一个：同一个数被反复从显存读取。Tiled（分块）的解法朴素而有效：把 A、B 切成 16×16 的小块搬进共享内存，块内所有线程复用同一份数据——显存流量立降 16 倍。读完本篇可掌握协作搬运、屏障同步与数据复用，这是 GEMM 优化的第一课。

## Background

这节从 Naive GEMM 的病根讲起：为什么"数据复用"是 GEMM 优化的第一课。

Naive GEMM（见 04_matmul_naive）里，每个线程直接从显存读 A 的一行和 B 的一列。以 256×256 的矩阵乘为例，A 的每一行会被全场线程读 256 遍——而显存带宽是所有线程共享的公共通道，容量有限。

痛点的场景是：矩阵一大，算力基本在"等数据"。GPU 每秒能做的乘加次数远超显存每秒能送来的数据量，重复访存把带宽吃满后，再多的计算单元也只能空转。

GEMM 优化的第一课因此不是 SIMD（单指令多数据，01 实验解释过的同步执行单元）也不是 tensor core（专用的矩阵乘硬件单元，见 How It Works），而是**数据复用**：CPU 有硬件缓存自动兜底，GPU 的对应手段是 threadgroup 共享内存——一块由代码手动管理的高速缓存。

Tiled 用最小的代码增量（协作搬运加两道屏障）演示了"共享内存 = 手动缓存"的思想；从本实验的 90 GFLOPS 到 MPS 实验的 1270，路上全是这个思想的变体。

## What

Tiled GEMM 是"分块复用"的矩阵乘法实现：把大矩阵切成 16×16 的小块（tile），每轮把 A、B 各一块协作搬进 threadgroup 共享内存，块内所有线程从共享内存取数做点乘累加，算完推进下一块。输出仍然是一个线程负责一个元素——变的是数据来源，从显存变成了共享内存。

一句话心智模型：**分块搬运，块内吃干榨尽**。

可以把共享内存想象成工地旁的临时料台：与其每个工人（线程）需要一颗钉子就跑一趟仓库（显存），不如全组先合作把一箱材料搬上料台，然后大家共用。但和料台不同的是，共享内存容量只有 KB 量级，装不下整个矩阵，所以必须切块轮换——"Tile"这个名字就来自这种瓷砖式铺法。

## When to Use

这节给出判断：什么时候值得写 Tiled 版本，什么时候有更好的选择。

典型场景：

- 在手写 GEMM 且矩阵规模让 Naive 版本带宽吃紧时——数据复用是第一个、也是收益密度最大的优化（本实验 7.5 倍）。
- 在写任何"多个线程要读同一份数据"的算子时——协作搬运加屏障的模式是通用的，卷积、转置等算子的优化都从这里出发。
- 在给算子定位性能瓶颈时——Tiled 与 Naive 的差距能告诉你卡在带宽还是算力（Roofline 视角见 06_roofline）。

何时不用：

- 矩阵很小、单块就能装进共享内存时，分块循环带来的复杂度收益有限，直接算更快。
- 生产场景优先用 MPS、MLX 等现成算子——Tiled 是手写路线的中间站，不是终点（对比见下表）。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| Accelerate / BLAS | CPU 上成熟的矩阵乘实现 | 数据在 CPU、规模中小 |
| Naive GEMM | 无数据复用，带宽受限（见 04） | 立基线、学原理 |
| Tiled GEMM（本篇） | 共享内存复用，代码增量小、收益 7.5 倍 | 手写优化的第一站 |
| MPS | Apple 预置算子，含寄存器分块、双缓冲等深层优化 | 生产中在 GPU 上跑 GEMM |
| MLX | 高层框架自动调度 | 模型实验，不关心 kernel |

## Quick Start

前置条件：一台装有 Xcode 的 Apple Silicon Mac。实现在 `matmul_tiled.swift`：Tiled 内核（kernel，运行在 GPU 上的函数，见 04_matmul_naive）加 CPU 端抽样验证。

```bash
./matmul_tiled.sh           # 一条龙
```

真实输出：

```
Tiled GEMM 512x512x512（tile=16）: 3.0 ms ≈ 90.3 GFLOPS
访存分析: Naive 每输出元素读 K×2 次；Tiled 复用后全局读量 ÷16
✅ 128 个抽样点与 CPU 一致
```

验证方法：与 04 相同的整数倍数据 + 128 点抽样。

输出的第二行是收益来源的浓缩：Naive 每个输出元素要从显存读 K×2 次；Tiled 让每个数从显存只读一次、之后在共享内存里被复用，全局读量除以 16（tile 边长）。性能与正确性数字如何得出，见 How It Works。

## How It Works

这节按 kernel 内每轮循环的执行顺序拆解：协作搬运、两道屏障、块内计算与越界补零。

核心代码（`matmul_tiled.swift`，节选主干）：

```metal
threadgroup float tileA[TILE][TILE], tileB[TILE][TILE];
tileA[lid.y][lid.x] = (row < M && aCol < K) ? A[row*K + aCol] : 0.0;
threadgroup_barrier(mem_flags::mem_threadgroup);
for (uint k = 0; k < TILE; k++) acc += tileA[lid.y][k] * tileB[k][lid.x];
```

**协作搬运**。每个线程搬一个元素：256 个线程恰好填满 16×16 的 tileA 与 tileB。

`lid` 是组内线程坐标（02 实验的 `thread_position_in_threadgroup`），`.x/.y` 是它的二维分量；`row`、`aCol` 是该线程负责的输出元素与所搬数据在全局矩阵中的行列号。

搬运是全组合作，不是各自为战——每个线程只搬自己坐标对应的那一个，这是"协作"在代码里的具体形态。

**两道屏障**。搬完（第一道 barrier）才能算；算完（第二道 barrier）才能覆盖搬下一块。屏障是共享内存正确性的税——漏一道就是竞态。你在 Quick Start 里看到的稳定正确结果，依赖的正是这两道屏障的严格次序。

**块内计算与越界补零**。`for` 循环让每个线程在自己的行、列上对 tile 内的 16 个数做点乘累加。K 不是 16 的整数倍时，tile 尾部会越界——三元表达式此时补 0：0 乘任何数都不影响累加和，边界被乘加天然吸收，无需任何分支。

**实测收益的来源**。512³ 规模下：Naive 12 GFLOPS → Tiled 90 GFLOPS（7.5 倍）。本质是算术强度提升——每字节显存流量摊到的浮点运算变多，性能从带宽受限向算力受限移动。

对照 MPS 实验（lab 12）的 1270 GFLOPS，剩下的差距属于寄存器分块、双缓冲（更细粒度的数据复用手段）与 tensor core（专用的矩阵乘硬件单元）的领域——它们都是"复用"思想在更细粒度上的延伸。

## Pitfalls & Q&A

这节收集本实验最典型的竞态坑，和 tile 大小的选型问答。

**坑：漏写或放错屏障，结果偶发错误**。现象：多数运行正确，偶尔个别元素算错。原因：两道屏障缺一不可——第一道保证 tile 已全部搬完，第二道防止下一轮搬运覆盖还没被读完的数据；漏掉任何一道，就出现"有人读、有人正在写"的竞态。

解法：搬运后、计算后各放一道 `threadgroup_barrier(mem_flags::mem_threadgroup)`，并确认它在 `if` 分支之外（全组必须同时到达）。

**Q：tile 大小怎么选？** 共享内存容量、占用率与每线程工作量三者的联合优化：tile 太大则共享内存装不下或占用率下降，太小则复用收益不足。16×16 是教学与真实工程常用的起点——本实验的全部数字都基于它。
