# 15 · MLX 惰性执行：记账与结账

> MLX 的每个操作都是"记账"：y = y*1.0001 + 0.5 重复 20 遍，GPU 一条命令都没跑——直到 mx.eval() 结账。这种"先记录、后计算"的模式叫惰性执行。本实验用同一段 20 层计算实测惰性与逐步执行两种模式的耗时差；读完你能掌握 eval 的批量语义，以及什么时候该手动 eval。

## Background

立即执行（eager）是 NumPy 和 PyTorch 默认的工作方式：每条语句立刻算完，把结果写回内存，下一条语句再读回来。每一步框架只看到一个算子（operator，一次基本的数组运算），算完即忘。

痛点在长计算链上：假设有 20 层连续变换、每层输入 256MB，立即执行意味着 20 次写回加 20 次读回，内存带宽全花在中间结果上；框架也因为没有"全局视野"，做不了任何跨步优化。

惰性执行把顺序反过来：先记账、后计算。每个操作只往一张未执行的计算图（描述"要做什么"的内部记录）里追加一条，直到显式结账才整批下发给 GPU。本实验把"为什么惰性"从口号变成数字。

## What

惰性执行是一种"先记录、后计算"的执行模式：运算不立即发生，而是逐条记入计算图；调用 `mx.eval()` 时，框架一次性触发整条依赖链的 GPU 计算。

一句话心智模型：**构建是免费的，eval 才花钱——攒一批再结**。

可以把这套流程想象成餐厅点单：服务员（Python）把菜记到单子上，几乎不花时间（构建阶段只是纯对象操作）；厨房（GPU）等整桌单子齐了一次性开做（eval 阶段）。但和餐厅不同的是，账单在内存里要一直占地方——计算图与中间结果的规划信息会驻留内存，而且实际计算时机变得不直观，这是惰性模式的代价。

## When to Use

典型场景：

- 长链变换连续套多层（逐元素、缩放、激活叠加）时，整链只 eval 一次，避免中间结果写回。
- 推理的一整段流程（前处理 + 模型前向）交给框架统一调度。
- 想做算子融合（把多个算子缝成一个内核）时——惰性是 mx.compile（MLX 的函数级编译接口）的前提（见 lab 16）。

何时不用：

- 交互式调试、需要立刻查看中间结果时，逐步 eval 更直观。
- 单个算子、数据量很小的计算，攒批没有收益。
- 需要严格控制每步内存峰值时，惰性下中间结果由框架自行规划，时机不完全可控。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| NumPy | 逐步立即执行，纯 CPU | 小数据、快速验证 |
| PyTorch eager | 逐步立即执行，每步写回-读回 | 需要逐步观察中间结果或依赖其生态 |
| MLX 惰性（本实验） | 默认记账，eval 整批下发 | Apple Silicon 上的长链计算 |
| mx.compile | 函数级编译，跨算子融合 | 结构固定的函数要进一步提速（见 lab 16） |

## Quick Start

前置条件：`pip3 install mlx`。脚本负责运行实验。

```bash
./mlx_lazy.sh           # 一条龙
```

真实输出：

```
构建 20 层算子链: 0.31 ms（只建图，未计算）
mx.eval 触发全部计算: 48.7 ms（20 层 × 256MB）
每层强制 eval: 61.3 ms（频繁同步破坏流水）
✅ 验证通过：惰性结果与逐步执行一致，且整体 eval 更快
```

验证方法：惰性结果与 numpy 逐步计算的 20 层参照做 allclose（允许浮点误差的近似相等判断）——快而不许错。

程序在做什么：准备 256MB 输入，分别对三种模式计时——只构建 20 层算子链、构建后一次 `mx.eval` 触发全部计算、每层都强制 eval；最后用 numpy 逐步计算的结果做逐元素比对（allclose，允许浮点误差的近似相等判断）。

## How It Works

两行代码就是全部机制：

```python
y = x
for _ in range(20): y = y * 1.0001 + 0.5   # 记账 ×20
mx.eval(y)                                  # 结账一次
```

逐行拆解"为什么这样写"：

- `y = y * 1.0001 + 0.5` 循环 20 次：每次运算返回新数组对象，但携带的是未计算的图。构建 20 层只花 0.3 ms——成本是纯 Python 对象操作，GPU 一条命令都没跑。这对应输出第一行的 0.31 ms。
- `mx.eval(y)` 触发整条依赖链的 GPU 执行。中间结果可以不物化（不写回内存，由框架自行规划），20 层 × 256MB 一次算完只花 48.7 ms。这对应输出第二行。
- 对照第三行：每层强制 eval 花 61.3 ms，慢约 25%。原因是每次 eval 都是一个同步点（CPU 等待 GPU 算完才能继续），同步点切断了流水——GPU 每层之间被迫空转等待。

惰性还是后续优化的地基：mx.compile 要做算子融合，前提就是"看见全链才能缝内核"，这是 lab 16 的主题。

## Pitfalls & Q&A

**Q：计时代码测出"诡异慢"，或者耗时机错位，怎么回事？**

现象：某一步莫名变慢，计时数字与预期对不上。原因：忘写 eval，实际计算被推迟到打印、取值等操作处才隐式触发（这些操作会自动补一次 eval）——MLX 新手第一大坑。解法：性能路径显式调用 `mx.eval` 管理评估时机；调试路径可以依赖隐式行为，但两条路径要分开。

**Q：什么时候该手动 eval？**

长链中间的大结果不再使用时。在切换点显式 eval，可以让框架释放中间数据、切换流水线，而不是让整张图一直挂着。

**Q：惰性执行的收益与代价各是什么？**

收益：框架获得跨算子优化的机会，中间结果可以不物化。代价：计算图与规划信息驻留内存，调试时实际计算时机不直观。两笔账都来自同一个设计——先记账、后计算。

**Q：与 PyTorch eager 的本质区别？**

eager 逐步立即执行，每步独立；MLX 默认惰性、整批下发，并在此基础上提供函数级编译（mx.compile）——前者看见的是每一步，后者看见的是整条链。
