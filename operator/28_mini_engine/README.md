# 28 · 轻量推理引擎算子层

> 五个算子（operator，模型计算的基本单元）、一个注册表（按名字登记与查找算子的表）、一张七节点的计算图（把计算排成节点序列的图），跑出一个完整的 MLP（多层感知机，最基础的全连接网络——每层与上一层的全部神经元相连）前向（从输入逐层算到输出的执行过程）——100 行代码看清推理引擎的骨架。读完你能亲手搭出“协议 + 注册表 + 编排器”这个最小结构。

## Background

会写单个算子（矩阵乘、激活……）之后，下一个问题是"组织"：怎么把算子拼成一个能跑完整模型的程序？直接的做法是为每个模型写专用脚本——第 1 层调矩阵乘、第 2 层调激活，一层层手写调用。

痛点在"变"字上：模型结构一改就要动主程序；换一个模型几乎重写；算子之间没有统一接口，组合、测试、复用都无从谈起。推理引擎要支持任意结构、任意算子组合，手写调用这条路走不通。

推理引擎（把模型跑起来的运行时软件，如 ONNX Runtime、MLC、llama.cpp）的解法是三层结构：所有算子实现统一的算子协议，注册表（按名字登记与查找算子的表）按名管理它们，编排器把算子串成计算图（把计算排成节点序列的图）按序执行。本实验在 CPU 上用最小标本把这个结构看全。

## What

轻量推理引擎是一种组织算子的程序骨架：算子实现统一接口、注册表按名管理、编排器按图顺序执行——三件套缺一不可。

一句话心智模型：**引擎 = 算子协议 + 注册表 + 编排器**。

可以把引擎想象成工厂流水线：协议规定每个工位的进出货规格，注册表是工位名牌墙，编排器是传送带的顺序。但和真实流水线不同的是，本实验的"传送带"只有一条直线，真实引擎还支持分叉与合并的图结构。

本实验的五个算子与两个基础部件：

| 部件 | 内容 | 角色 |
|---|---|---|
| `Operator` 协议 | 名字 + `forward([Tensor]) -> Tensor` | 所有算子的统一形状 |
| `registry` | 名字 → 算子实例的映射 | 按名查找与扩展 |
| `Tensor` | 张量（多维数组，算子之间传递的数据） | 数据载体 |
| MatMul / Add / ReLU / Softmax / LayerNorm | 矩阵乘 / 逐元素加 / 负数置零的激活 / 把一串数归一成概率分布（非负且总和为 1）/ 把每层的输出调整到均值 0、方差 1，稳定后续计算 | 被编排的算子 |

## When to Use

典型场景：

- 自研推理框架、或要把多个算子组装成可配置的推理流水线时——协议 + 注册表让新增算子不改引擎代码。
- 需要跨模型复用算子实现时——模型只是图的描述，算子实现与模型结构解耦。
- 读 ONNX Runtime、MLC、llama.cpp 源码前的准备——它们是同一骨架的工业级放大。

何时不用：

- 只有单一模型、结构固定：直接写调用序列更简单，引擎抽象是过度设计。
- 追求速度上限的稠密计算：图执行引入间接层开销，本实验的价值在结构不在速度。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 手写调用序列 | 最直接，无抽象开销 | 单一固定模型、一次性脚本 |
| 迷你引擎（本实验） | 协议 + 注册表 + 链式图，约百行 | 学结构、小规模可配置流水线 |
| ONNX Runtime / MLC / llama.cpp | 工业级：形状推断、内存规划、多后端 | 生产部署 |
| PyTorch（MPS 后端）/ MLX | 算子库、调度、内存管理全套内建 | 训练推理一体的日常开发 |

## Quick Start

本实验是 Swift 程序，需要一台 Apple Silicon Mac。一条命令跑完注册、编排与验证：

```bash
./mini_engine.sh           # 一条龙
```

## How It Works

引擎按"注册 → 编排 → 执行"三步工作，逐段拆开。

### 算子协议

```swift
protocol Operator { var name: String; func forward([Tensor]) -> Tensor }
```

协议（protocol，Swift 里规定方法签名的接口）只要求两件事：一个名字、一个 `forward`。所有算子长一个样——引擎的循环不关心具体算子，这是"框架化"的全部秘密。

### 注册表

`registry["MatMul"] = MatMul(...)`：按名索引。新增算子 = 注册一个类型，引擎代码零改动。

权重作为构造参数闭进算子实例——即权重在创建算子时就绑定进内部，而不是每次执行时传入。为什么这样写：权重编译期已知、可以预绑定；每次运行才出现的输入才是运行时数据流——两者生命周期不同，引擎因此与权重解耦。

### 链式图编排

`g.add(norm); g.add(matmul1)...` 顺序即数据流：上一层输出即下一层输入。核心执行代码：

```swift
func run(_ input: Tensor) -> Tensor {
    var stack: [Tensor] = [input]
    for (op, _) in nodes {
        let arg = stack.removeLast()
        stack.append(op.forward([arg]))
    }
    return stack[0]
}
```

这段在做什么：维护一个栈（后进先出的列表）——每次取出栈顶（上一层的输出），喂给当前算子，结果压回栈；链式执行就是"取顶、计算、压回"的循环。

为什么这样写：循环体只调 `op.forward`，完全不知道算子是什么——新增算子无需改动这十行。Quick Start 输出里的"MLP 前向: [1,64] → LayerNorm → 128 → ReLU → 10 → Softmax"，就是这个循环跑完的结果。

真实的 DAG（有向无环图，允许分叉合并的图结构）引擎在此之上加多输入拓扑排序（把多输入节点排成可执行顺序）——骨架不变。

## Pitfalls & Q&A

**问：不用标准答案怎么验证引擎？** 用结构不变量（invariant，无论输入是什么都应成立的性质）：Softmax 输出必须非负、总和必须为 1。复杂系统的验证要善用这类性质——它们不需要参照值，却能抓住结构性错误。

**问：从这 100 行到 ONNX Runtime 还差什么？** 推理引擎的核心抽象是四层：算子接口（形状推断 + 计算）、图 IR（IR，中间表示，图的程序化描述）、内存规划、调度。本实验覆盖前两个；补齐后三个还需要形状推断、DAG 拓扑排序（把多输入节点排成可执行顺序）、内存池复用、多后端分发与量化内核。
