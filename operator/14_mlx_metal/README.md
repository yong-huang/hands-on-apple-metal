# 14 · MLX 数组与统一内存

> MLX 是苹果为 Apple Silicon（苹果自研芯片）打造的 NumPy 风格数组框架：数组天生住在统一内存（CPU 与 GPU 共享同一份物理内存的设计）里，没有 host↔device 拷贝（CPU 内存与显卡内存之间来回搬运数据）这个概念。本实验验证这个红利，并测出它的真实成本曲线；读完你能确认零拷贝是否成立，并掌握"先记账、后执行"的惰性用法。

## Background

传统 GPU 框架（CUDA 生态、PyTorch）里，CPU 内存（host，主机）和显卡内存（device，设备）是两份独立的内存。想在 GPU 上算一笔账，得先用 `cudaMemcpy` 或 `tensor.to(device)` 把数据显式拷过去，算完再拷回来。

痛点出现在每个训练/推理步骤里：数据在 CPU 侧预处理（分词、清洗），再拷到 GPU 计算，拷贝本身就是性能大坑，还额外占双份内存。而在 Apple Silicon 上，CPU 与 GPU 本来就共享同一份物理内存，这些拷贝纯属多余——却仍要开发者自己写、自己管。

MLX 从架构上消灭了这一步：数组天生住在统一内存里，CPU 与 GPU 引用同一块物理内存。理解"零拷贝 + 惰性执行"这对基石，后面所有 MLX 实验的设计逻辑就都通了。

## What

MLX 是苹果专为 Apple Silicon 设计的 NumPy 风格数组计算框架。本实验关注它的第一块基石：统一内存带来的零拷贝；第二块基石惰性执行在本篇一并演示，机制细节展开在 lab 15。

一句话心智模型：**同一块内存，两颗芯片轮流用**。

可以把统一内存想象成一张共用办公桌：CPU 和 GPU 两位同事直接在桌上处理同一份文件，不用先复印一份递过去。但和共用办公桌不同的是，两颗芯片各有自己的高速缓存，硬件需要靠缓存一致性协议（保证多颗芯片对同一内存看到一致内容的机制）来维持视图统一——这是红利背后的代价。

## When to Use

典型场景：

- 在 Mac 上做本地大模型推理或微调：数据在 NumPy 侧预处理后直接交给 GPU，中间没有拷贝步骤。
- 把已有的 NumPy 原型代码挪上 GPU 提速：API 高度相似，数组换成了 mx.array（MLX 的数组类型，对应 NumPy 的 ndarray）。
- 内存吃紧的场景：数组只有一份，不必在"内存 + 显存"各放一份。

何时不用：

- 依赖 NVIDIA CUDA 生态（自定义 CUDA 内核、特定 GPU 库）的项目，MLX 不覆盖。
- 需要部署到 Linux/Windows 服务器时，MLX 只支持 Apple Silicon。
- 纯 CPU 的小数据任务，NumPy 更简单直接。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| NumPy | 纯 CPU，生态最全 | 小数据、离线分析 |
| PyTorch（MPS/CUDA 后端） | 需显式 `.to(device)` 搬运模型与数据 | 需要训练生态与现成模型库 |
| MLX（本实验） | 统一内存零拷贝 + 惰性执行，仅限 Apple Silicon | Mac 上的本地推理与研究实验 |
| 手写 Metal / MPS | 更底层，控制粒度最细 | 补缺失算子或逼近带宽上限（见 lab 13） |

## How It Works

四个关键动作各占一行：

```python
c = a + b            # 记账
mx.eval(c)           # GPU 执行
m = mx.array(n)      # numpy 零拷贝视图
s = mx.sum(m); mx.eval(s)   # 归约
```

逐行拆解"为什么这样写"：

- `c = a + b` 只是记账：惰性执行模式下 MLX 不立即计算，只在内部记录"有一个加法"。`mx.eval(c)` 才真正触发 GPU。MLX 等看到完整表达式后统一调度，这是 lab 15 的主题。
- `m = mx.array(n)` 不复制数据：mx.array 与 numpy 数组共享同一块缓冲，类型/布局兼容时转换是视图操作（不复制数据、直接指向原数据的别名）。首次 GPU 访问时框架按需实体化（真正分配并填充数据），对应输出里的"首次实体化 5.3 ms"。
- `s = mx.sum(m); mx.eval(s)` 在 GPU 上完成归约，全程无显式拷贝——你在输出里看到的"10 次归约 8.2 ms"就来自这里。

设备语义：默认跑 GPU，`mx.cpu` 可指定。统一内存下"搬运"不存在，但执行设备仍影响调度与算力。

## Pitfalls & Q&A

**Q：忘掉 eval 直接 `.tolist()` 或打印，会怎样？**

现象：代码能跑出正确结果，但性能敏感路径的耗时不可控。原因：打印、取值等操作会触发隐式 eval（MLX 自动补执行），评估时机脱离了你的控制。解法：性能路径显式调用 `mx.eval` 管理时机；调试路径可以依赖隐式行为，但两条路径要分开管理。

**Q：numpy 转 mx.array 每次都要付转换成本吗？**

现象：大数组首次转换偏慢（实测 64MB 约 5 ms，含首次 GPU 触达）。原因：这是按需实体化的一次性成本，不是每次转换都复制数据。解法：把转换放在初始化阶段完成，不要放进反复执行的热循环。

**Q：统一内存到底消除了什么成本？**

消除的是 host↔device 显式拷贝，以及数据在内存、显存各放一份的双份占用。代价是需要缓存一致性协议来保证两颗芯片看到同一份数据——这笔账由硬件付，不由代码付。
