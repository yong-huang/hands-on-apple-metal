# 25 · INT4 量化 GEMV：解量化融合

> 把解量化（计算前把 4-bit 整数权重还原成浮点数）藏进 GEMV（矩阵-向量乘）内核（GPU 上大规模并行执行的小函数）：权重在内存里始终是 4-bit，省 75% 空间。读完你能跑通一个带双验证的实现，并知道它精度结论的适用边界。

## Background

量化（把模型权重从 32 位浮点压成低比特整数存储）普及之前，LLM（大语言模型）的权重以 FP32（32 位浮点数，每个数占 4 字节）原样放进内存。以 70 亿参数（7B）的模型为例：70 亿 × 4 字节 ≈ 28 GB，仅权重就装不进大多数消费级设备。

退路是 FP16（16 位浮点，每个数占 2 字节），能把占用减半——但只省一半，手机和笔记本的内存预算依然装不下主流模型，加载这一步就撞墙。

INT4（即 4-bit：4 位整数，只有 16 个取值）因此成为端侧（手机、笔记本等本地设备）部署 LLM 的生命线：每个权重只存 4 位。

但存储省下的，要在计算前还回来。

本实验实现的 INT4-GEMV 内核，就是 llama.cpp、MLX 这类推理框架（在本地加载并运行模型的软件）量化栈（围绕量化的一整套实现）里的核心部件：它把打包（把两个 4-bit 数挤进一个字节）、解量化、点乘（对应元素相乘再求和）三步放进同一次 GPU 执行，理解这三步就理解了量化推理的一半。

## What

INT4 量化 GEMV 内核是一种"边还原边计算"的 GPU 内核：输入 4-bit 打包权重与 FP32 输入向量，直接输出矩阵-向量乘的结果。把解量化和乘加合并在同一个内核里执行，这一步合并就叫融合（fusion，中间结果不写回内存）。

一句话心智模型：**存的是 4-bit，算的时候才还原，还原不落显存**。

可以把打包权重想象成真空压缩袋里的被子：收纳时压到原体积的四分之一，要用哪床就取哪床、当场铺开。但和压缩袋不同的是，还原按元素逐个进行、即取即用，不存在"先整块解压完、再开始计算"的阶段。

内核读到的数据一共四样：

| 部件 | 内容 | 角色 |
|---|---|---|
| 打包权重 | 每个字节装两个 4-bit 数 | 存储态，省 75% 空间 |
| scale 表 | 每 16 个元素一个 FP32 缩放系数（scale，把整数刻度映射回真实数值范围的系数） | 还原时的换算依据 |
| 输入向量 x | FP32 的本层输入 | 被乘的一方 |
| 累加器 acc | FP32 累加变量 | 点乘结果逐项累加处 |

## When to Use

典型场景：

- 在内存受限的设备上本地跑 LLM 生成文字时。每生成一个 token（模型输出的最小文本单元）都要把全部权重读一遍，权重体积直接决定速度与内存占用。
- 给自研推理框架搭量化层时。INT4-GEMV 是 llama.cpp、MLX 量化栈的核心部件，读懂它等于读懂量化推理的一半。
- 要评估"量化后到底损失多少"时。本实验的双验证方法（正确性对齐 + 误差对标理论值）可以直接迁移到自己的内核开发里。

何时不用：

- 模型用 FP16 就装得下：直接用 FP16，省掉打包与还原的复杂度。
- 训练、微调等追求精度上限的场景：INT4 在合成数据上有 8~9% 的相对误差（见 Pitfalls & Q&A），不可接受。
- 生产部署：优先用 MLX 内置量化 API 或 llama.cpp 的成熟实现，不必手写内核。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| PyTorch（MPS 后端） | MPS 是 PyTorch 的 Apple GPU 加速后端，低比特量化支持不及 CPU/CUDA（NVIDIA GPU 的通用计算平台）路线完整 | 已有 PyTorch 代码、模型不大、对内存占用不敏感时 |
| MLX 量化 API（`nn.QuantizedLinear`） | 一行换层即可量化，底层内核已内置本实验的融合思路 | Apple Silicon 上做推理与实验的首选起点 |
| llama.cpp（GGUF 格式） | GGUF 是 llama.cpp 的模型文件格式，内置多种 INT4 方案，生态成熟，但属于 C++ 技术栈 | 纯推理部署、需要跨平台时 |
| 手写 Metal（Apple 的 GPU 编程框架）内核 | 完全可控，每一步都看得见 | 学习量化内核原理、需要定制打包格式时 |

## Quick Start

本实验是 Metal 程序，需要一台 Apple Silicon Mac。一条命令跑完量化、内核执行与双验证：

```bash
./int4_gemv.sh           # 一条龙
```

真实输出：

```
权重内存: FP32 2048 KB → INT4 256 KB（-75%）
内核 vs 反量化参照 最大差: 1.91e-05
量化误差（范数相对）: 8.88%
✅ 验证通过：显存省 75%，解量化完全融合在 GEMV 内核里，误差与 INT4 理论水平一致
```

验证方法：双验证——内核输出与“反量化参照”逐位对齐（打包/解包正确），相对 FP32 的范数误差符合 15 级刻度（量化值取 −8~7 共 16 档，其中非零刻度 15 个）的理论水平。

"反量化参照"指先解量化、再用普通乘加算出的对照结果：它与内核输出对齐，说明打包/解包正确。诚实预期：8.88% 的量化误差不是 bug，而是 15 级刻度的理论水平——4-bit 只能取有限个离散值，量化误差存在不可消除的下限。1.91e-05 的最大差在 FP32 舍入误差量级。

"范数相对"指误差按范数（norm，衡量向量整体长度的度量）归一，而不是逐元素比较。

## How It Works

内核按"打包 → 解量化 → 点乘"的顺序处理数据，逐段拆开。

### 打包与还原

FP32 权重先逐组量化成 0~15 的整数，再两两装进一个字节：低 4 位放偶数列、高 4 位放奇数列。一个 4-bit 数只占半字节（nibble，4 个二进制位）。

还原时把 0~15 映射回有符号数（可表示负数的整数编码）：`≥8 则 −16`。这是 4 位补码（计算机表示负数的编码，最高位为 1 时代表负值）的还原，三行位运算完成——输出里"FP32 2048 KB → INT4 256 KB"的节省就来自这里。

### 逐组 scale

每 16 个元素共用一个 FP32 scale。分组越细，scale 越贴合局部分布、精度越高，代价是 scale 表变大。工业实现常用 32~64 元素/组加更优的缩放策略；本实验取 16 是为了把机制讲清。

为什么必须分组？单个全局 scale 会被离群值（outlier，明显偏离整体的极大或极小数值）绑架——一个特别大的权重会把刻度间距撑大，其余权重的量化误差随之变大。分组让误差局部化在自己那 16 个元素之内。

### 核心代码

```metal
uchar b = row[p];
int e = int(b & 0xF);        e = (e >= 8) ? e - 16 : e;
int o = int((b >> 4) & 0xF); o = (o >= 8) ? o - 16 : o;
acc += float(e) * sc[gid*(K/16) + 2*p/16] * x[2*p]
     + float(o) * sc[gid*(K/16) + (2*p+1)/16] * x[2*p+1];
```

这几行同时完成解量化与点乘：

- 前三行还原数值：从字节 `b` 拆出两个 nibble——`b & 0xF` 取低 4 位（偶数列），`b >> 4` 取高 4 位（奇数列）；`≥8 则 −16` 把无符号刻度折回有符号数。
- 后两行累加：还原出的两个数各乘自己所在组的 scale（`sc` 表按行存放，第 `gid` 行有 K/16 个），再乘输入向量 `x` 的对应元素，累进 `acc`。
- 为什么这样写：还原结果只存在于计算过程中，从不写回内存再读出来——这正是"融合"二字的含义。

融合省在哪里？反量化后的 FP32 权重不落显存，与"先解量化存回内存再计算"相比，权重读取的带宽（bandwidth，内存与计算单元之间每秒能搬运的数据量）省 4 倍，还省掉等量写入。LLM 生成阶段每出一个字都要读一遍全部权重，权重搬运正是主要瓶颈，这笔节省直接兑现为速度。

## Pitfalls & Q&A

**坑：grid 参数传成线程组数。**

- 现象：内核能启动，结果却错乱或部分行没算。
- 原因：把 grid（GPU 一次内核启动的总线程布局）传成了线程组（threadgroup，GPU 线程的分队单位）的数量，而不是总线程数——本实验的正确布法是 M 行 × 每行 256 线程，grid 传的是总线程数。
- 解法：把“grid = 总线程数”当成每次启动内核前的固定检查项；Metal 入门期这个坑反复出现，值得形成肌肉记忆。

**坑：nibble 摆放约定不一致。** 现象：程序不报错，量化误差却巨大。原因：打包端低 4 位放偶数列、高 4 位放奇数列，解包端若按相反约定拆字节，位运算全部正确、数值全部错位。解法：采用与主流实现一致的约定，并写进文档——约定错误不抛异常，只会静默出错。

**问：实测 8.88% 的误差能直接推广到真实 LLM 吗？** 不能直接等同。8.88% 是高斯随机权重下 15 级刻度的理论水平；真实 LLM 权重分布更平滑，加上端到端推理对单层误差的容错，困惑度（perplexity，衡量语言模型预测质量的常用指标，越低越好）损失通常小于 1%。

合成数据只用来验证正确性，精度结论要以真实模型为准——这是量化内核开发的诚实边界。
