# 16 · GELU 与 mx.compile 融合

> 手写 GELU（Transformer 模型常用的激活函数）由 5 个逐元素算子组成——每个都把 64MB 搬一遍内存。mx.compile（MLX 的函数级编译接口）在编译期把它们缝成一个内核（GPU 上执行的小函数）：一次读、一次写。数值一位不变，实测加速 10.88×。读完你能掌握融合的原理、mx.compile 的边界，以及正确的计时方法。

## Background

不编译时，一条 5 步的逐元素算子链（逐元素：对数组每个位置独立做同一运算）里，每个算子各启动一次内核（kernel，GPU 上被大量线程各执行一遍的小函数），把整个数组从内存读回、算完再写回。

GELU 这类激活函数在 Transformer 模型的每个前馈层都要调用，数组又是 64MB 量级——数据 5 进 5 出，内存带宽全花在搬运中间结果上。

带宽受限算子（算术强度约 0.5——每搬运 1 字节数据只摊到 0.5 次运算，远低于"带宽受限与计算受限"的分界拐点 10，见 lab 06）唯一正确的优化方向就是融合：把多个算子缝成一个内核，中间结果不再落回内存。但手写融合内核要写 Metal、管理中间缓冲，成本不小。

mx.compile 让你"写清晰的链路，得融合的内核"：保持普通 Python 函数的写法，由编译器在编译期（程序运行前框架预先处理的阶段）自动完成缝合。这是 MLX 在 Apple Silicon 上的一个核心卖点。

## What

GELU（Gaussian Error Linear Unit）是一种激活函数（神经网络里对每个数做的非线性变换）。精确式 `x·Φ(x)`（Φ 是标准正态分布的累积分布函数，即输入落在正态分布上 x 点以下的概率）用误差函数（erf，一个特殊数学函数）计算 Φ。

工程标准普遍改用 tanh 近似（本实验采用）：`0.5x(1+tanh(√(2/π)(x+0.044715x³)))`——展开后正好是 5 个逐元素算子。

mx.compile 是 MLX 的函数级编译接口：把一段普通 MLX 代码写成的函数，在编译期改写成等价但更快的执行计划——把其中"逐元素为主"的算子链缝成一个内核，一次读、一次写。

一句话心智模型：**5×64MB 的搬运压缩成 1×64MB**。

可以把融合想象成合并快递单：五件包裹（中间结果）各自在仓库（内存）和收件站（计算单元）之间跑一趟，合并成一件后只跑一趟。但合并只对"顺路"的小件有效——遇到必须整车运输的大件（matmul 等大算子），mx.compile 会自动分段，不做强行合并。

## When to Use

典型场景：

- 模型热路径上有一段由多个逐元素算子组成的固定函数（激活、门控 gating——用算出的系数去逐元素乘主通路——归一化等算子的逐元素部分）。
- 已有清晰易读的 MLX 链路代码，想提速又不想改写计算语义。
- 大数组反复经过同一段计算，中间结果的搬运成为瓶颈时。

何时不用：

- 函数主体是 matmul（矩阵乘法）等大算子——mx.compile 会自动分段，收益有限。
- 数组很小、计算低频——编译开销摊不回来。
- 需要跨"逐元素 + 矩阵乘"边界或自定义内存模式时，改用手写融合内核（见 lab 20）。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 不编译的 MLX 链路 | 每个算子一次内核启动、一次内存往返 | 原型验证、低频路径 |
| mx.compile（本实验） | 自动融合逐元素子图，数值语义不变 | 清晰代码换融合性能的首选 |
| 手写 Metal 融合内核 | 完全控制访存与算子边界，成本高 | 跨算子类型边界、自定义内存模式（lab 20/24） |

## Quick Start

前置条件：`pip3 install mlx`。脚本负责运行实验。

```bash
./gelu_compile.sh           # 一条龙
```

真实输出：

```
=== MLX 16 · GELU 与算子融合 ===
✅ 正确性：融合前后逐元素一致
手写链路: 0.27 ms/次
mx.compile 融合: 0.03 ms/次（加速 10.88×）
访存视角: 5 算子链路搬 5×64MB，融合后 1×64MB——带宽受限算子的收益公式
✅ 验证通过：数值不变，融合显著更快
```

毫秒数与加速倍数每次运行会浮动，量级不变。

验证方法：allclose(atol=1e-6) 逐元素比对——融合是搬运优化，不许改数学。

程序在做什么：用 MLX 算子写出 tanh 近似的 GELU（手写链路），再用 mx.compile 包一层得到融合版；同一输入分别计时多轮取均值（首轮的编译开销由预热吸收），最后 allclose(atol=1e-6)（允许 1e-6 绝对误差的逐元素近似相等判断）做数值双验证。

```python
def gelu_manual(x):
    return 0.5 * x * (1 + mx.tanh(0.7978845608 * (x + 0.044715 * x**3)))
gelu_fused = mx.compile(gelu_manual)   # 一行触发融合
```

这段在做什么：`gelu_manual` 用普通 MLX 算子把 tanh 近似公式写成一串逐元素运算，是不融合的基准；`mx.compile(gelu_manual)` 一行完成编译缝合，得到语义相同、执行计划不同的融合版。

## How It Works

mx.compile 做的事发生在编译期，运行时只有一条执行路径：

- 扫描 `gelu_manual` 的计算图（框架记录"要做哪些运算、按什么依赖执行"的内部结构），识别出"逐元素为主"的子图（其中连续的一段逐元素运算）。
- 把这 5 个算子缝成一个内核（GPU 上被大量线程各执行一遍的函数）：一次读入 x、一次写出结果，中间量留在寄存器里，不再写回内存。
- 遇到 matmul 等大算子则自动分段——融合只作用于逐元素为主的区段，不强行跨越。

为什么这样能加速：带宽受限的算子链上，N 个算子意味着 N 次内存往返；缝成一个内核后变成 1 次，省下的搬运直接转化为时间收益。你在输出里看到的 0.27 ms → 0.03 ms（加速 10.88×）就来自这 5 次往返到 1 次的压缩。

它不改变数值语义：逐元素运算的定义不变，融合前后在 1e-6 内逐元素一致。与手写融合内核的本质区别在于省心——代价是灵活度低一档（lab 24 是手写融合内核版）。

## Pitfalls & Q&A

**Q：mx.compile 版第一次计时反而更慢，是坏了吗？**

现象：首次调用融合版耗时明显偏高。原因：首轮包含编译开销，编译本身要花时间。解法：先跑一遍预热吸收编译开销，正式计时取多轮均值——lab 22-30 的 benchmark 都沿用这套计时纪律。

**Q：mx.compile 会改变数值吗？**

不改，逐元素语义保持（本实验 1e-6 内一致）。但浮点累加顺序可能被微调，验证时用 allclose 而非 `==` 逐位比较。

**Q：什么时候必须手写融合内核？**

需要跨"逐元素 + 归约/矩阵乘"边界，或要自定义内存模式时——mx.compile 的自动分段到不了那里（见 lab 20）。
