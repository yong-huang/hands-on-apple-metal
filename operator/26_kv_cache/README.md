# 26 · KV Cache：环形写入与增量读取

> 自回归生成（每一步输出都依赖之前全部输出的生成方式）每步只算新 token（最小文本单元）的 K/V（键/值向量），历史躺在缓存里；缓存的布局与覆盖策略决定读写带宽。读完你能实现环形写入与零拷贝（不搬数据、只换一个看内存的视角）读取的 KV 缓存，并验证“定长显存跑无限上下文”的回绕（写满后回到开头覆盖最旧）语义。

## Background

没有 KV Cache 时，每生成一个 token 都要为"整段已有文本"重算注意力（attention，让新 token 回看全部历史并加权提取信息的机制）所需的 K/V（键/值向量，注意力用来"查"和"取"的两套数据）。

痛点随长度显现：生成第 1000 个 token 要重算前 999 个的 K/V，第 2000 个要重算前 1999 个——越写越慢，而其中绝大部分计算是把已经算过的东西原样再算一遍。显存（GPU 使用的内存）也撑不住无限制的增长。

KV Cache 因此成为生成式推理的标准配置：算过的 K/V 存进缓存，每步只算新 token 的那份，每步成本变成常数。缓存不可能无限大，环形缓冲（ring buffer，定长缓冲区，写满后从头继续写）就是显存受限下的必然选择。本实验实现的就是"环形写入 + 增量读取"这对操作。

## What

KV Cache 是一种生成期缓存：把每个 token 的 K/V 向量按顺序存进显存，让每步生成只计算新 token 的 K/V。环形 KV Cache 再加一条覆盖规则，用定长内存支撑无限增长的上下文。

一句话心智模型：**写进槽位 pos % CAP，读走连续段**。pos 是全局步号，CAP 是缓存容量（本实验 1024）——写第 pos 步时落在 pos % CAP 号槽位，读取时按连续布局整段取走。

可以把环形缓存想象成一盘定长的循环录像带：录满后回到带子开头继续录，最旧的画面被新内容覆盖。但和录像带不同的是，哪些段还有效需要上层明确约定——覆盖是否合法由注意力语义决定，缓存本身不负责标记。

内核层面的部件一共五样：

| 部件 | 内容 | 角色 |
|---|---|---|
| `kc` / `vc` | 两块 [CAP, 256] 的缓存，K 与 V 各一块 | 历史 K/V 的存储 |
| `k_new` / `v_new` | 新 token 的 256 个连续元素（H×D：本实验把 256 个元素分成 H=4 组、每组 D=64 个，每组对应注意力的一“头”——把一次注意力拆成多组并行计算的结构） | 每步增量写入的数据 |
| `pos` | 全局步号计数 | 决定写入哪个槽位 |

## When to Use

典型场景：

- 自己实现或魔改 LLM 推理循环时——没有缓存，每生成一个 token 都要重算全部历史的 K/V，长上下文慢到不可用。
- 显存预算固定、要跑流式长对话时——环形覆盖让定长内存能一直接收新 token。
- 想读懂 vLLM、llama.cpp 这类推理引擎的缓存设计时——本实验的槽位寻址与布局是它们的简化地基。

何时不用：

- 短文本一次性生成：整段一次算完更简单，缓存管理是纯开销。
- 训练阶段：整段序列一起做注意力，通常不需要逐步缓存。
- 生产推理：直接用现成引擎的缓存实现，不必手写内核。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 无缓存，每步全量重算 | 实现最简单，但每步成本随上下文线性增长 | 一次性短文本、教学验证 |
| 定长 KV Cache | 每步只算新 K/V，上下文超过容量后须截断 | 上下文长度可控、显存预算固定 |
| 环形缓存（本实验） | 定长显存跑无限上下文，旧槽位覆盖即失效 | 滑动窗口注意力（只回看最近 CAP 个 token 的注意力变体）、流式长对话 |
| vLLM（流行的 LLM 服务引擎）式分页缓存 | 把缓存切成页、按需分配，支撑多请求并发 | 多请求并发的生产服务 |

## Quick Start

本实验是 Metal 程序，需要一台 Apple Silicon Mac。一条命令跑完环形写入与增量读取：

```bash
./kv_cache.sh           # 一条龙
```

真实输出：

```
写入 300 步后：槽位 299 有效（范数 31.98），环形回绕逻辑正确
读取 300×256 KV 做 attention: 0.28 ms/步（布局连续，transpose 零拷贝）
✅ 验证通过：环形写入与增量读取语义正确
```

验证方法：写入 300 步后槽位 299 必须持有刚写入的数据（范数非零）；attention 读取走 `reshape + transpose` 零拷贝。

怎么读这份输出：范数（norm，向量整体长度的度量）31.98 说明槽位 299 里确实是最后一步写入的数据；0.28 ms/步 是读取 300×256 个 K/V 并做布局变换的耗时，"零拷贝"（不搬动数据，只换一个看内存的视角）是它快的原因。

## How It Works

内核按"写入 → 读取"两段工作，逐段拆开。

### 环形覆盖

`slot = pos % CAP`：写满 1024 个槽位后回到槽位 0，覆盖最旧的数据——这是滑动窗口注意力（只允许新 token 回看最近 CAP 个 token 的注意力变体）的显存基础。本实验写 300 步未触发回绕，但槽位公式本身已得到验证。

### 写内核的寻址

新 token 的 K/V 是 256 个连续元素，内核按全局索引写入 `kc[slot*256 + i]`——"以我编号写我的槽"模式的再次应用。核心代码只有一行源码：

```python
kv_write = metal_kernel(name="kv_ring_write", input_names=["k_new","v_new","pos"],
    output_names=["kc","vc"],
    source="uint slot = pos[0] % 1024; kc[slot*256+i] = k_new[i]; vc[slot*256+i] = v_new[i];")
```

这段代码分两步完成一次写入：

- `pos[0] % 1024`：把全局步号折算成本步槽位——回绕公式的落地。
- `kc[slot*256+i] = k_new[i]`、`vc[slot*256+i] = v_new[i]`：K、V 各自整段写进该槽位；`i` 是每个线程自己的编号，各写各的元素，线程之间无需协调。

为什么这样写：寻址只依赖全局步号 `pos`，与历史写入无关，任何两步之间互相独立、天然并行。

### 零拷贝读取

缓存的物理布局是 [CAP, H×D]（每个槽位占一行），attention 需要的形状却是 [1, H, CAP, D]。`reshape(1,CAP,H,D).transpose(0,2,1,3)` 把前者变成后者——只要布局连续，这两步就只是视图操作（重新解释内存，不搬数据），300×256 个元素一个都不用动。

Quick Start 输出里的"transpose 零拷贝"与 0.28 ms/步，就是这条路径的直接结果。

## Pitfalls & Q&A

**问：KV Cache 到底省了什么？** 省的是每步对全部历史的 K/V 投影（projection，用权重矩阵把每个 token 的向量变换出 K 和 V 的矩阵乘）。

没有缓存时，生成第 S 个 token 要做 O(S) 次投影（O(S) 表示成本随上下文长度 S 线性增长）；有缓存后每步只做 O(1) 次——只算新 token 自己的。

**问：环形覆盖的代价是什么？** 旧槽位被覆盖后不可读。这是滑动窗口注意力的语义选择；如果上层仍按"全历史可读"的假设来算，就会读到脏数据。要在覆盖后继续保留历史，只能配合换页策略把旧数据挪去别处。

**问：距离生产系统还差什么？** 三件事：掩码（mask，标记无效槽位、让注意力跳过它们的机制）——回绕后旧槽位必须被排除；增量 attention——每步只算新 Q（查询向量）对全部 K 的注意力；分页管理（vLLM 采用的方式，把缓存切成页按需分配）——支撑多请求并发。本实验是这三者的地基。
