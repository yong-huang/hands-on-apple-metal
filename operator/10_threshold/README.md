# 10 · 阈值二值化：解析解验证方法论

> 最简单的算子最适合练"最严格的验证"：给定阈值 T 和渐变输入，输出的每一列都有解析答案。读完你能掌握阈值二值化的精确语义（含取整与量化边界），以及一套把算子验证做成数学题的解析解方法。

## Background

写完一个算子（对图像的一种明确定义的变换），怎么确信它是对的？在自动化验证普及之前，常见做法是把输出图像投到屏幕上人眼检查，或随机抽几个像素手工核算。

痛点在于语义级错误看不出来：边界上多算或少算一列、保留值悄悄从"原值"变成统一的最大值，黑白图肉眼看上去完全正常。下游算法若依赖"保留的像素值仍有含义"，错误要到很晚才暴露。

对输入可控的简单算子，期望输出可以直接用公式算出——这就是解析解（用公式算出的精确答案，而非抽样近似）：把每个位置的期望值写成公式，让程序全量比对。阈值二值化（按亮度分界把像素分成"保留/清零"两类的操作）的输出恰好可手算，是练这套方法的最小对象。

## What

阈值二值化（thresholding）按一条亮度分界线处理图像：过线的像素保留、不过线的清零。

MPS（Metal Performance Shaders，苹果随 Metal 提供的预制 GPU 算子库）的 `ThresholdToZero` 滤镜（filter，图像到图像的一种变换）语义：**x > T 保留原值，否则清零**，T 是归一化到 0~1 的阈值（threshold，人为设定的亮度分界）。

可以把阈值化想象成"录取分数线"：分数（亮度）过线的原样录取，不过线的清零退回。但和录取不同的是，这里过线者保留的是自己的原始分数，而不是统一改成一个满分值——后者是另一种语义（见 Pitfalls 中 ToZero 与 Binary 的区别）。

本篇的验证方法：程序生成一张从 0 到 255 的线性渐变图（亮度沿水平方向逐列线性上升），用三档阈值分别二值化，把"保留了多少列"与手算公式精确比对。

## When to Use

典型场景：

- 文档扫描中把纸面文字与背景分离，只留笔迹做后续识别。
- 工业视觉里按亮度划出"合格/缺陷"区域，作为统计的前置分割。
- 生成掩膜（mask，标记哪些位置参与后续处理的辅助图），控制效果只作用在亮区或暗区。

何时不用：光照不均匀的图像，单一全局阈值会大面积误判——应先做光照校正或改用分界线随区域变化的自适应阈值；需要保留明暗层次的表达（如风格化）时，硬二值化会不可逆地丢信息。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| ThresholdToZero | 过线保留原值，欠线清零 | 保留值仍有含义、下游要用 |
| ThresholdBinary | 过线统一置最大值 | 只需要 0/1 掩膜 |
| 自适应/局部阈值 | 分界线随区域变化 | 光照不均的照片（如阴影下的文档） |
| 自写 Metal kernel（在 GPU 上并行执行的小函数） | 比较规则完全自定义 | 双阈值滞回等特殊规则 |

## Quick Start

前置条件：macOS + Xcode 的 Swift 工具链，机器支持 Metal。在实验目录下运行：

```bash
./threshold.sh           # 一条龙
```

真实输出（节选）：

```
…（程序标题与 Device 信息行省略）
T=0.25: 保留 192/256 列（理论 192），低于阈值的像素全部清零 ✓ → ✅
T=0.5: 保留 128/256 列（理论 128），低于阈值的像素全部清零 ✓ → ✅
T=0.75: 保留 64/256 列（理论 64），低于阈值的像素全部清零 ✓ → ✅
…（结尾的通用形态说明行省略）
```

验证方法：列数与解析解**精确相等**（不是近似），同时保留值必须 ≥ 阈值——两个断言（assert，程序自动检查结果是否符合预期并报告成败的语句）缺一不可。

验证代码的核心两行（完整程序见 `threshold.swift`）：

```swift
let v = Int(px[(32 * w + x) * 4])
if v > 0 { keptCols += 1; if Float(v) < tNorm * 255 - 1 { zeroOk = false } }
```

这段在做什么：遍历第 32 行逐列取像素值；值大于 0 说明该列被保留，计数加一；同时校验保留值不小于 T×255 减 1 的余量——防止实现悄悄从"保留原值"变成"置满最大值"。

## How It Works

数据流三步：生成宽 w=256 的渐变图（第 x 列亮度恰为 x，两端精确到 0 和 255）；分别用 T=0.25、0.5、0.75 执行 `ThresholdToZero`；统计每档的保留列数，与解析解全量比对。

解析解的推导：保留条件是像素值达到 T×255，即第 x 列保留当且仅当 x ≥ T×255。因此保留列数 = w − ceil(T×255)，其中 ceil 是向上取整。

T=0.25 时 T×255=63.75，向上取整为 64，保留 256−64=192 列——你在输出里看到的"保留 192/256 列（理论 192）"正是这个公式在三档 T 上的取值。

断言为什么是两条：只数列数，查不出"保留值被偷偷置满"的语义错误；只查保留值，查不出边界列多算少算。列数精确相等加上保留值 ≥ 阈值，两条同时成立才算通过——输出行尾的 `✓ → ✅` 表示每档都过了这两关。

## Pitfalls & Q&A

**断言总是差一列？** 现象：保留列数比理论值少 1。原因：把 ceil（向上取整）写成了 floor（向下取整），一字之差，边界列的归属就翻转，实际测试中出现过。解法：保留条件 x ≥ T×255 对应保留列数 = w − ceil(T×255)，取整方向不能反。

**边界列的断言偶发失败？** 现象：理论值与实测值偶有 1 的偏差。原因：8-bit 量化（把连续亮度取整到 0~255 整数存储）让边界值偏离理论值 1 以内——1 个 LSB（最小量化单位）。解法：断言比较留 1 个 LSB 的余量，对应代码里的 `tNorm * 255 - 1`。

**渐变两端不是精确的 0 和 255？** 现象：解析解整体错位，断言大面积失败。原因：渐变的除法分母用了 w 而不是 w−1，两端取不到精确端点值。解法：分母用 w−1，保证首列精确 0、末列精确 255。

**ThresholdToZero 与 ThresholdBinary 怎么选？** 前者过线保留原值，后者过线统一置最大值。选错的后果：下游依赖"保留值仍有含义"的量化逻辑失效。本篇"保留值必须 ≥ 阈值"的断言，就是防止实现悄悄变成 Binary。

**解析解验证适用于所有算子吗？** 只适用于输入输出关系可手算的算子。复杂算子（如大尺寸模糊）退化为"不变量（无论输入如何都应成立的性质，如像素总数不变）+ 抽样验证"。
