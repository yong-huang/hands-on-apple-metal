# 27 · 融合 GEMM + GELU：epilogue 融合

> LLM 推理 80% 的计算是“GEMM（矩阵乘）后接激活（对每个元素做一次非线性变换）”的组合。分离执行要把结果写回显存（GPU 使用的内存）、再读出来做激活；epilogue（写回前的收尾阶段）融合让激活就地完成。读完你能实现“一个内核（GPU 上大规模并行执行的小函数）两种模式”的融合 GEMM，并量出省掉的往返开销。

## Background

GEMM（General Matrix Multiply，矩阵乘，深度学习里最基础的大块计算）和激活（activation，对每个元素做一次非线性变换的函数，给网络引入非线性）历来是两步执行：先启动一个 GEMM 内核把结果矩阵写进显存（GPU 使用的内存），再启动第二个激活内核把它读出来、处理、写回去。

痛点在中间那段路：以本实验 1024×1024 的输出为例，中间结果落显存就是 8 MB 写 + 8 MB 读——数据明明已经在计算单元手里，却要先寄存到内存再取回来，还多付一次内核启动的固定开销。LLM 推理里"GEMM 后接激活"的组合出现得极频繁，这段冤枉路每次都要走。

epilogue 融合因此出现：把激活塞进 GEMM 内核写回前的收尾阶段，在累加结果离开计算单元之前就地完成。本实验把基础 GEMM 与融合手法接上，构成手写 GEMM 融合的最小完整案例。

## What

epilogue 融合是一种把"逐输出元素的后处理"并入 GEMM 写回阶段的实现方式：GELU（Gaussian Error Linear Unit，主流 LLM 常用的激活函数）在累加器（acc，GEMM 逐项累加求和的工作变量）里就地完成，中间结果不落显存。

一句话心智模型：**累加结果还没落地，激活就地完成**。

可以把 epilogue 想象成快递出库前的最后一站：包裹（累加结果）在离开仓库（寄存器，GPU 线程私有的高速存储）之前就地贴上标签（激活），而不是先入库上架、再取出来贴、再送回去。但和贴标签不同的是，只有"逐输出元素"的后处理能这样就地做——需要看整行、整列信息的操作放不进来。

内核部件一览：

| 部件 | 内容 | 角色 |
|---|---|---|
| 累加器 `acc` | GEMM 逐项累加出的和，在寄存器里 | 激活的直接输入 |
| `C` | 输出矩阵 | 激活后一次性写回 |
| `fused` | `constant bool` 开关 | 切换"裸 GEMM"与"GEMM+GELU"两种输出 |

## When to Use

典型场景：

- 写 LLM 推理的算子（operator，模型计算的基本单元）层时——每个"GEMM 后接激活"的组合都适用 epilogue 融合。
- 矩阵中等偏小、带宽（内存与计算单元之间每秒能搬的数据量）紧张时——省下的 8 MB×2 往返在总时间里占比越大，收益越明显。
- 想看懂生产推理栈（MLX、llama.cpp）的融合内核时——bias、残差都是同款写法。

何时不用：

- 后处理需要跨行、跨列的信息（如对整块矩阵求最大值）：epilogue 每次只看得到一个输出元素。
- 场景简单、矩阵很小：往返开销可以忽略，先保证正确与简单，融合是后置优化。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 分离两内核（GEMM + 激活） | 逻辑清晰、激活可单独替换，但多一次全量写+读与一次内核启动 | 激活逻辑复杂多变、需要独立调试时 |
| epilogue 融合（本实验） | 激活就地完成，省一次全量往返与一次启动 | 后处理固定为逐元素操作时 |
| PyTorch（MPS 后端） | 框架负责调度与部分自动融合，无需手写内核 | 快速搭原型、不追求极限性能时 |
| MLX 内置内核 | 融合写法已内建，抽象度高 | Apple Silicon 上日常推理与实验 |

## Quick Start

本实验是 Swift + Metal 程序，需要一台 Apple Silicon Mac（需 Xcode Command Line Tools；首次使用 swiftc 时系统会提示安装）。一条命令跑完融合版计时、分离版计时与验证：

```bash
./fused_gemm_act.sh           # 一条龙
```

真实输出：

```
融合（GEMM+GELU 一趟）: 3.6 ms
分离（GEMM 裸奔，另需 +1 次全量往返做激活）: 3.6 ms + 往返开销
省掉的往返: 1048576 × 4 字节 = 8 MB 的写+读
✅ 融合结果与 CPU 参照一致（64 点抽样）
```

验证方法：C 与"CPU GEMM + GELU"的 64 点抽样一致——注意验证要在融合运行之后读缓冲（本实验实测踩过"验证读了分离结果"的顺序坑）。

怎么读这份输出：两行都是 3.6 ms——融合省掉的是分离版"额外"的那次 8 MB 往返，不是把 3.6 ms 再砍一刀；朴素 GEMM 的计算时间占主导，往返占比越大融合收益越明显。"64 点抽样"指从 1048576 个输出里抽查 64 个，与 CPU 参照（用 CPU 上的普通实现算出的标准答案）比对。

## How It Works

### epilogue 的含义

epilogue 指 GEMM 累加完成后、写回 C 之前的插入点。GELU 三行代码在寄存器里完成——无中间物化（物化：把中间结果写进内存成为实体数据）、无额外内核启动。

### 单内核双模式

`constant bool& fused` 切换输出是否激活（constant 表示编译期常量，编译器能据此裁掉不用的分支）：同一个内核既当融合版用，也当分离版的 GEMM 段用——对照组免写第二份内核。

### 核心代码

```metal
if (fused) {
    acc = 0.5 * acc * (1.0 + tanh(0.7978845608 * (acc + 0.044715 * acc * acc * acc)));
}
C[row * dims.y + col] = acc;    // 激活后一次性写回
```

这段代码是整个实验的落点：

- `if (fused)` 里的三行是 GELU 的 tanh（双曲正切函数）近似公式（0.7978845608 ≈ √(2/π)，0.044715 是该近似的拟合系数），直接作用在寄存器里的 `acc` 上——累加结果从未落过显存。
- 写回语句放在 `if` 之外：无论融合与否，C 都只写一次。分离版多出的"写 C → 读 C → 激活 → 写 C"在这里不存在。
- 为什么这样写：激活吃的正是累加值本身——数据在寄存器里最便宜，不用过内存总线。

### 本内核仍是朴素 GEMM

融合省的是激活往返（8 MB×2），但 GEMM 本体还是朴素实现（naive，未做访存优化的直接写法，速度约 12 GFLOPS 量级，GFLOPS 为每秒 10 亿次浮点运算）。

融合优化与 GEMM 本体优化（见 lab 05、12）是正交（互不影响、可叠加）的两件事：先优化 GEMM 本体，epilogue 原样保留，生产中两者叠加使用。

## Pitfalls & Q&A

**坑：验证读了分离结果。** 现象：融合结果"验证失败"，数值却不像激活出错的样子。原因：缓冲区里永远躺着"最后一次运行"的结果——先计时分离版再验证，读到的就是未融合的数据，假失败。解法：固定顺序——跑融合 → 验证 → 计时对照。

**问：epilogue 还能放什么？** bias（偏置，加在每个输出元素上的常数）、残差相加（把层的输入直接加回输出）、缩放、量化——任何"逐输出元素"的后处理都能零成本融合。

**问：为什么不干脆写成两个内核？** 代价是一次全量读写加一次内核启动（见 How It Works 的写回分析）；数据在寄存器里最便宜。本实验仍保留了分离路径——它当对照组用，验证正确性与计时对比都靠它。
