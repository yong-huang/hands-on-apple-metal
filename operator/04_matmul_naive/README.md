# 04 · 矩阵乘法 Naive：基线内核

> 矩阵乘法（GEMM）是深度学习的心脏，占大模型约 80% 的算力。本篇先写一个"慢但对"的 Naive（朴素直译式）版本：每个线程算输出矩阵的一个元素。它作为一切优化的对照组——读完可掌握 2D 线程网格映射、访存瓶颈分析与逐位一致的验证设计。

## Background

这节解释：明明要写"快"的矩阵乘法，为什么第一篇却是刻意写"慢"的基线版本。

在 CPU 上，矩阵乘法是经典的三层 for 循环：对每个输出元素，沿内层维度累加乘积。Accelerate/BLAS（Basic Linear Algebra Subprograms，经典 CPU 线性代数运算库）这类成熟库把它优化得很好，但对学习者是黑盒——看不见数据怎么流、瓶颈在哪。

没有基线的优化是盲目的：改一版 kernel（运行在 GPU 上的函数，见 01_vector_add），快了是优化有效还是运气？慢了是改坏了还是本来如此？没有"慢但对"的参照物，性能变化无法归因，正确性也没有对照。

Naive GEMM 因此成为标准的第一步：它的结构最简（一眼看懂数据映射），同时暴露全部性能问题（重复访存）。本系列后续的 Tiled 优化与 MPS 对照实验，都以这个基线为原点衡量收益。

## What

GEMM（General Matrix Multiply，通用矩阵乘法）计算 C = A × B：输出矩阵 C 的每个元素，等于 A 的一行与 B 的一列对应相乘再求和（即一次点积）。Naive 指最直接的 GPU 实现：派发一个与 C 同形状的 2D 线程网格，每个线程只负责 C 的一个元素。

一句话心智模型：**线程坐标 = 输出坐标**。

可以把这个网格想象成一场考试：每个学生（线程）负责答题卡（输出矩阵）上的一个格子，用自己的行列号（`gid.x`/`gid.y`）定位格子，然后逐项读取 A 的一行和 B 的一列算出答案。

但和考场不同的是，学生之间互不通信、也不共享草稿——正因如此，同一份"题目数据"被全场反复读取，这就是本实验性能低下的根源（分析见 How It Works）。

## When to Use

这节给出判断：Naive GEMM 什么时候值得写，什么时候应该换现成方案。

典型场景：

- 在为手写 GEMM 做优化时——先跑通 Naive 版本，立起"慢但对"的基线，之后每个优化都跟它比。
- 在评估是否值得手写算子时——拿 Naive 版本与 MPS/MLX 的输出对照性能，量化差距再决定投入。
- 在学习 GPU 编程时——它是理解 2D 线程网格与访存瓶颈的最小载体，比任何讲义都直观。

何时不用：

- 生产代码里不要用 Naive GEMM 做实际计算——本实验实测仅 11.7 GFLOPS，重复访存使性能远低于可用水平。实际需求交给 MPS、MLX 或 Accelerate。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| Accelerate / BLAS | CPU 上成熟且优化充分的矩阵乘库 | 数据在 CPU、规模中小 |
| Naive Metal GEMM（本篇） | 每线程算一个输出元素，结构最简、性能低 | 立基线、学原理 |
| Tiled Metal GEMM | 用共享内存分块复用数据（见 05_matmul_tiled） | 手写优化的下一步 |
| MPS | Apple 预置的 GPU 矩阵乘算子，无需手写 | 生产中在 GPU 上跑 GEMM 的直接选择 |
| MLX | 高层框架，自动调度 GPU 计算 | 模型实验，关心结果不关心 kernel |

## Quick Start

前置条件：一台装有 Xcode 的 Apple Silicon Mac。实现在 `matmul_naive.swift`：朴素内核加 CPU 端抽样验证。

```bash
./matmul_naive.sh           # 一条龙
```

真实输出：

```
每线程组最大线程数（内核）: 1024
Naive GEMM 256x256x256: 2.9 ms ≈ 11.7 GFLOPS
✅ 128 个抽样点与 CPU 逐位一致
```

验证方法：系数取"整数倍的 0.25/0.5"，乘加无舍入误差 → CPU/GPU 结果应**逐位一致**（抽样 128 点）——比相对误差更严格的验证。

输出的三行各有含义：第一行是设备支持的线程组上限；第二行是本基线的成绩（256×256×256 的矩阵乘，2.9 毫秒）；第三行是正确性结论。这个 11.7 GFLOPS 为什么这么低，见 How It Works 的访存分析。

## How It Works

这节讲清三件事：2D 网格如何映射到输出、访存为什么构成瓶颈、逐位一致的验证如何设计。

**2D 线程网格**。`gid.x` 对应列、`gid.y` 对应行，16×16 的线程组铺满 M×N 的输出矩阵——网格形状与矩阵形状直接对应，这就是"线程坐标 = 输出坐标"的落地。

**核心循环：一个输出元素的计算**。

```metal
float acc = 0;
for (uint k = 0; k < dims.z; k++)
    acc += A[row * dims.z + k] * B[k * dims.y + col];   // 行主序索引
C[row * dims.y + col] = acc;
```

为什么这样写：矩阵按行主序（row-major，同一行的元素在内存里相邻）存储，`row * dims.z + k` 把二维下标折算成一维偏移，B 侧同理。维度打包成 `dims` 用 `setBytes` 传入 3×uint32——比三个独立参数更整洁。每个线程沿 K 维累加，正好是 What 里"点积"的定义。

**访存瓶颈分析**。每个输出元素要读 A 的一行加 B 的一列，即 2K 次访存；全矩阵合计 2×M×N×K 次——A 的每一行被读 N 遍、B 的每一列被读 M 遍。

折算下来每次浮点运算都要等 4 字节数据从显存到位；算术强度（arithmetic intensity，每 1 字节访存摊到几次浮点运算，06_roofline 会专门测它）因此只有约 0.25，远低于 GPU 的平衡点。**这就是输出里 11.7 GFLOPS 的全部原因**——数据搬运，而不是计算，构成了瓶颈。

**逐位一致的验证设计**。数据初始化用 `k % 13 * 0.25` 这类二进制精确小数（0.25 是 2 的负二次幂，乘加不产生舍入误差），GPU 与 CPU 虽然乘加次序不同，结果却无舍入差，因此可以用 `==` 逐位比对，抽样 128 点。验证强度要与数据特性匹配：能构造精确数据时，就用零成本的最严格验证。

## Pitfalls & Q&A

这节收集一个越界坑、一个线程组尺寸的决策问答。

**坑：网格非整除时崩溃或结果错乱**。现象：矩阵尺寸不是 16 的整数倍时，程序崩溃或输出越界数据。原因：2D 网格按"向上取整"派发，会多出落在矩阵之外的越界线程，`row`/`col` 可能超出边界。

解法：kernel 开头检查 `row >= M || col >= N`，命中就直接 return。

**Q：线程组为什么选 16×16？** 这是线程协作粒度（tile，即 05 实验的分块边长）、占用率（活跃线程占硬件可容纳线程的比例）与共享内存用量三者的折中；硬上限受 `maxTotalThreadsPerThreadgroup` 约束（本机为 1024，即 Quick Start 输出的第一行）。

16×16 = 256 线程，既在限额之内，又与后续 Tiled 实验的分块尺寸对齐。
