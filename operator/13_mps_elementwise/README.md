# 13 · 逐元素加法：带宽实测

> 逐元素算子（对数组每个位置独立执行同一运算的算子，如 A+B、激活（对每个数做的非线性变换）、缩放）的速度上限是内存带宽——GPU 每秒能从内存读写的数据总量。本实验用 Metal（苹果的 GPU 编程框架）手写 A+B，实测带宽并与硬件上限对标。读完你能掌握这一类算子的通用优化方法：向量化搬运（让每次内存访问搬运更多数据）+ 带宽对标。

## Background

在用 GPU 之前，给大数组做一次 A+B 通常靠 CPU：写一个 C 循环，或调用 NumPy、Accelerate（苹果的 CPU 向量加速库）。数据量到几十 MB 时，CPU 的并行度跟不上。

而推理（inference，用训练好的模型做预测的计算过程）流水线里数据本来就在 GPU 侧，搬回 CPU 处理还要多两次拷贝。

痛点在推理场景尤其明显：逐元素算子占推理算子数量的多数（偏置 bias、激活 activation、缩放等，都是对每个数独立做的小运算），个个都是"算得少、搬得多"，速度完全由搬运决定。

想直接用苹果的 GPU 算子库 MPS（Metal Performance Shaders，一套现成的 GPU 图像与矩阵运算算子库）时又会撞上边界——它没有公开的"矩阵加法"类。

于是这类算子有两条生产路线：手写 Metal 内核（GPU 上被大量线程各执行一遍的小函数，下文详述），或用 MPSGraph（用计算图（描述"要做哪些运算、按什么依赖执行"的内部记录）描述并执行算子的上层框架）。本实验走手写路线，把这类算子的优化逻辑完整演示一遍：一个加法内核，测出带宽，对标硬件上限。

## What

逐元素算子是这样一类运算：输出数组的每个元素，只由输入在相同位置的元素决定。A+B、激活函数、乘缩放系数都属于这一类。本实验取其中最简单的 A+B，把它当作测量带宽的"温度计"。

一句话心智模型：**算术强度 0.5 的算子，优化 = 把带宽打满**。算术强度指每搬运一字节数据能摊到多少次运算；这个值越低，耗时越由搬运而非计算决定。

可以把逐元素内核想象成流水线上的搬运工：货物（数据）远比动作（加法）费时，提速只能靠加快搬运。但这个类比只在带宽受限时成立——换成计算密集的算子（如大矩阵乘法），瓶颈就转移到运算本身。

内核（kernel）指 GPU 上会被大量线程各执行一遍的小函数，每个线程用拿到的编号处理数据的一个切片。优化方向有两条：让每个线程每次搬得更多（向量化），让足够多的线程同时干活（占用率，即同时驻留 GPU 的线程数占硬件容量的比例）。

## When to Use

典型场景：

- 推理引擎需要一个 MPS 没有现成实现的算子（如某个二元组合运算），要自己补一个 GPU 版本。
- 写完一个自定义算子后，想知道还有没有优化空间——换算出带宽、对标硬件上限即可判断。
- 决定是否值得把一串小算子合并（融合，即多个算子合成一个内核以省掉中间读写）之前，先测单算子带宽，估算收益。

何时不用：

- MPS 已有现成类、且不追求极限带宽时，直接用现成算子。
- 张量（多维数组）只有 KB 量级时，内核启动开销占比过大，CPU 或更简单的方案更划算。
- 不想维护 Metal 代码时，用 MPSGraph 组合现成算子。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| PyTorch（MPS 后端） | 框架托管，一行代码调用，不接触内核 | 原型验证、模型训练，不追求单算子极限带宽 |
| MPS 现成算子类 | 苹果预先调优，免写内核代码 | 所需算子在 MPS 里有时，首选 |
| MPSGraph | 用计算图（描述"要做哪些运算、按什么依赖执行"的内部记录）描述一串算子，由系统统一调度 | 多个算子组合、MPS 无现成类时 |
| 手写 Metal 内核（本实验） | 完全控制访存方式与向量化粒度 | MPS 没有的算子，或要逼近带宽上限 |
| NumPy / Accelerate（CPU） | 不依赖 GPU，数据留在 CPU 侧 | 数据量小、离线批处理 |

## Quick Start

前置条件：macOS 与 Swift 工具链。Swift 工具链随 Xcode 命令行工具提供：终端运行 `xcode-select --install`（已装会提示已安装），用 `swiftc --version` 验证。若脚本报 "swiftc: command not found"，就是缺这一步。

脚本负责编译 Swift 源文件并运行实验。

```bash
./mps_elementwise.sh           # 一条龙
```

## How It Works

核心内核只有一行运算：

```metal
kernel void mat_add(device const float4* a [[buffer(0)]],
                    device const float4* b [[buffer(1)]],
                    device float4* c [[buffer(2)]],
                    uint i [[thread_position_in_grid]]) {
    c[i] = a[i] + b[i];      // 一条指令完成四个加法
}
```

逐条拆解"为什么这样写"：

- `kernel` 声明这是 GPU 内核；`thread_position_in_grid` 是当前线程在整张线程网格里的编号，每个线程负责 C 中一个 float4 位置的加法。
- `device` 表示指针指向 GPU 可访问的内存；`const` 把 A、B 标为只读。`[[buffer(0)]]` 等是缓冲槽位编号，宿主侧按编号传入对应缓冲。
- `float4` 是 4 个单精度浮点打包成的向量类型（16 字节），一条指令同时对 4 个数做加法（SIMD，单指令多数据）。这是收益来源：每线程一次搬 16 字节 ×3（读 A、读 B、写 C），指令数除以 4，访存粒度对齐缓存行（缓存与内存之间搬运数据的最小单位）。实测 112 GB/s，而一次只处理一个数的标量版约 30 GB/s。

数据不必离开 MPS 的抽象：三块数据仍装在 MPSMatrix（MPS 的矩阵对象 = 底层缓冲 + 形状/类型描述符）里，通过 `.data` 取出底层缓冲，直接绑定给内核的三个缓冲槽位。抽象层与手写内核可以共存。

带宽换算与对标方法：带宽 = 3×16MB ÷ 耗时（读 A、读 B、写 C 各搬运一次 16 MB）。输出里的 0.45 ms 换算出 112 GB/s，约为 lab 06 实测上限 220 GB/s 的 51%。

单内核到不了上限属正常：内核启动与尾波（最后一批线程不满员）有固定开销，占用率受线程组（GPU 调度线程的最小分配单位）的资源限制。持续流水运行的多算子链或更大的数据规模才能逼近上限。

## Pitfalls & Q&A

**Q：想用 MPS 做"矩阵加法"，为什么找不到现成的类？**

MPS 没有"矩阵加法"的公开类，二元算子需要子类化 MPSMatrixBinaryKernel（MPS 为二元算子预留的基类）才能实现，成本不低。解法是两条生产路线：手写 Metal 内核（本实验），或用 MPSGraph 组合现成算子（见 lab 11），按是否需要融合来选择。

**Q：单内核实测只有上限的一半左右，是写错了吗？**

现象：0.45 ms 换算出 112 GB/s，距离 220 GB/s 的上限很远。原因：内核启动与尾波开销固定存在，线程组资源限制压低占用率。解法：让多个算子持续流水，或用更大的数据规模摊薄开销；避免把中间结果写回内存再读出（物化），能合并的算子直接融合。
