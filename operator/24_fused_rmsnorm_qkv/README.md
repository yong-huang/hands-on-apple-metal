# 24 · 融合算子：RMSNorm + QKV 缝成一个内核

> LLM 解码每步都要 RMSNorm（按整行均方根值缩放元素的归一化层）加 Q/K/V（attention，即注意力机制的查询/键/值）三次投影（线性变换）。分离执行要把中间激活写回显存再读出三次；融合内核让数据"算完不落地"。读完你能理解手写融合与 mx.compile（MLX 的自动融合工具）的本质区别——自己决定数据留在哪，并跑通一个融合内核与分离参照对答案。

## Background

LLM（大语言模型）解码期的每一步都执行同一条流水线：先对当前向量做 RMSNorm 归一化，再用三份权重把它线性变换成 attention 的 Q、K、V 三份输入。常规框架按算子逐个调度：RMSNorm 一个内核（kernel，GPU 上运行的最小编译执行单元）算完，把结果写进显存；三个投影再各自把它读出来。

解码期批大小（batch，一次同时处理的样本数）为 1，算力大量富余，耗时几乎全花在数据搬运上。中间激活每多一次显存往返，就多一份纯浪费——这是分离执行在小批量推理里的主要开销。

融合（fusion，把多个连续运算合并进一个内核）是针对性的解法：数据算完不落地。RMSNorm+QKV 是 LLM 推理最高频的融合对，也是手写融合的最佳教学样本。

## What

融合算子（operator，执行单一数学运算的基本计算单元）是把多个连续运算合并成一个内核执行的形式。本实验把 RMSNorm 与 QKV 三次投影缝进一个 Metal 内核，与分离执行的参照对答案。

一句话心智模型：**归约（reduction，把一组数合并成一个数）一次 rms（均方根：先求各元素平方的均值，再开方），然后 Q/K/V 三条投影并行奔流**。可以把分离执行想象成流水线每做完一道工序就把半成品搬回仓库、下道工序再领出来；融合让半成品一直留在工人手边（寄存器，线程私有的最快存储）。

失效边界：融合不改数学——数值只差浮点累加顺序的舍入（输出里 9.54e-07 量级的差）；且本实验规模下两者同为 0.009 ms，收益要规模放大才显现。

核心卖点是"中间激活零次显存往返"：归一化结果不出内核，直接进入投影计算。

## When to Use

典型场景：

- **LLM 推理引擎的热点路径**：解码每步固定执行的算子对（归一化 + 投影）值得缝成一个内核。
- **小批量访存受限场景**：batch=1 或小 batch 时算力富余，省一次显存往返就是省大头。
- **mx.compile 覆盖不到的计算图**（计算图：把程序里一连串运算按依赖关系连成的数据流图）：跨"归约 + 矩阵乘"边界的融合，自动工具做不了，必须手写。

何时不用：

- 逐元素（对每个数独立施加同一运算）为主的简单计算链：mx.compile 一行即可完成，安全便捷。
- 规模大到计算受限：融合省下的访存占比变小，收益有限。
- 数学还没定型的原型阶段：先用分离算子对齐数学，再动手融合。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 手写融合内核 | 可跨归约/矩阵乘边界，控制内存驻留 | 热点路径、访存受限场景 |
| mx.compile 自动融合 | 安全便捷，但限逐元素子图（计算图中不含归约/矩阵乘的部分） | 逐元素链条的默认优化 |
| 框架现成融合算子 | 官方预置的常见融合 | 有现成实现时优先 |
| 分离算子 | 无融合成本，代码最直白 | 原型对答案、非热点路径 |

## Quick Start

前置条件：macOS 与 Apple Silicon 设备，装有 MLX（Apple 为 Apple Silicon 出品的机器学习框架）。

```bash
./fused_rmsnorm_qkv.sh           # 一条龙
```

真实输出：

```
融合 vs 分离 最大绝对差: 9.54e-07
分离执行: 0.009 ms | 融合内核: 0.009 ms
✅ 验证通过：融合内核与分离执行数值一致
```

验证方法：融合输出与分离参照的最大绝对差 < 1e-6 量级——融合是搬运优化，不改数学。

关键代码（节选，省略号处是归并细节；这段在做什么：步骤 1 由全组树形归约算出均方值，换算成缩放系数 rms，512 是行维度数、e 是防除零的小常数；步骤 2 每个输出维度用归一化后的激活直接与权重行做点积，中间激活不离开寄存器）：

```metal
// 步骤1：组内归约 rms
for (uint st = lsize/2; st > 0; st >>= 1) { ... }
float rms = 1.0 / sqrt(s[0] / 512.0 + e);
// 步骤2：norm 与三投影一气呵成
q[d] = Σ_c nv(c) * wq[d*512+c];   // nv = x[c]*rms*wn[c]
```

## How It Works

**两步结构。** 步骤 1：全组协作归约出 rms(x)——lab 03 的树形归约骨架再次复用。步骤 2：每个线程负责若干输出维度，归一化后的激活直接在寄存器里与三组权重做点积（projection，线性变换）。中间激活零次显存往返。

**单 token 的特殊性。** 解码期 batch=1，每次只算一个 token（模型逐个生成的最小文本单位）：x 只有一行，一个线程组即可覆盖整行——归约与投影在同一组内完成，不需要跨组通信。跨组通信会让融合复杂得多，这是选这个样本的原因之一。

**内核里的权重约定。** 代码里 `wq[d*512+c]` 按 (out, in) 行主序（按行连续存储）取权重：d 是输出维度、c 是输入维度。这一约定必须与 MLX 侧参照的用法对齐，对不齐就是本实验最大的坑（见下节）。

**性能解读。** 本实验规模下两者同为 0.009 ms——内核启动开销（每次派发的固定成本）主导，融合省下的访存还显不出来；规模放大后优势才逐渐出现。融合的收益要从访存量算，不要从小规模计时猜。

## Pitfalls & Q&A

**坑：权重布局约定混用。** 现象：融合内核与分离参照对答案时差异巨大（本实验实测差 2.19），且不报错。原因：内核按 (out, in) 行主序取权重 `wq[d*512+c]`，参照侧却写成 `normed @ wq`（即 in×out 约定），两种约定混用。

解法：参照统一改用 `wq.T`，让框架约定与自己内核的约定对齐——这是手写融合的第一戒律。

**坑：归约缺少 barrier。** 现象：结果偶发出错数，且每次运行不一样。原因：树形归并时若缺少 barrier（组内同步点：所有线程到齐才继续），部分线程读到了还没写完的共享内存。解法：归并的每一步之后加组内同步，再进入下一步。

**Q：手写融合与 mx.compile 的本质区别？** mx.compile 只能融合逐元素子图，安全便捷；手写可跨归约/矩阵乘边界，并且由自己决定数据驻留在寄存器还是显存（见 lab 16 的 compile 实验）。

**Q：为什么融合在 batch=1 时收益最大？** 访存占比最高、算力富余，省一次显存往返就是省大头；批量大起来后计算本身成为瓶颈，融合的相对收益缩小。
