# 09 · Bloom 辉光：三滤镜组合拳

> 用三条 MPS 滤镜串成流水线实现 Bloom（辉光）——游戏画面里霓虹灯与魔法特效的来源。读完你能掌握多滤镜组合时中间图像怎么接力、命令缓冲怎么排序，以及用正反双断言验证组合语义的方法。

## Background

真实效果很少由单个算子（对图像的一种明确定义的变换，如模糊、提亮）完成。在滤镜库普及之前，做"亮部发光"这类复合效果有两条路：在 CPU 上逐像素手写全部步骤；或每算完一步就把图像从显存（GPU 的高速内存）读回内存，喂给下一步。后者在大分辨率下每帧都要往返一次，成本难以接受。

痛点具体到场景：游戏画面里的霓虹灯、魔法弹道要求"高光向四周晕开"，而且每帧都要重新计算。手工搬运数据既慢，步骤之间图像格式与尺寸的衔接也容易出错。

MPS（Metal Performance Shaders，苹果的预制 GPU 算子库）给出第三条路：滤镜（filter，图像到图像的一种变换）的输出直接是显存里的图像，可作为下一个滤镜的输入，多步在同一条提交给 GPU 的指令队列里按序执行。本篇用"提取高光 → 晕开 → 叠回原图"三步实现 Bloom（辉光）。

## What

Bloom 是一种画面后处理（在主画面生成之后、输出之前追加的图像处理）效果：提取画面中较亮的区域，模糊晕开，再叠加回原图，让高光看起来在向外发光。一句话心智模型：**高光提取后糊开再贴回去**。

可以把 Bloom 想象成贴"光雾"：先复印一张只含高光的透明片，把透明片揉糊，再对齐叠回原件。但和手工叠片不同的是，三步都发生在 GPU 显存内的纹理（texture，显存中可直接读写的图像容器）上，全程不回 CPU。

本篇流水线的三个组成滤镜：

| 步骤 | 滤镜（参数） | 作用 |
|---|---|---|
| 1 | ThresholdToZero(0.3) | 亮度低于 0.3 的像素清零，只留高光 |
| 2 | GaussianBlur(8) | 把高光点晕成光斑 |
| 3 | Add | 光斑与原图相加，亮处自然过曝发白 |

## When to Use

典型场景：

- 游戏或实时渲染中，让霓虹灯、爆炸火光、魔法弹道等高亮元素"发光"。
- 界面与数据可视化里给高亮状态加氛围光，突出重点元素。
- 照片后处理里营造柔和光感，弱化高光的生硬边界。

何时不用：画面没有明显高光时无光可提；只需要单步模糊或阈值，直接用对应滤镜，不必叠三层；Bloom 是屏幕空间（只看最终二维画面、不知道场景三维信息的处理方式）的近似效果，不考虑光线遮挡，需要物理正确的光散射时它不适用。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 自写 Metal kernel（在 GPU 上并行执行的小函数） | 三步可融合、逐像素可控；调优维护自己做 | 差异化辉光风格、需与其他效果融合 |
| Core Image | 更上层的滤镜框架，带颜色管理与滤镜链 | App 层照片/视频滤镜，不关心纹理细节 |
| 引擎内置后期 | Unity、Unreal 等自带 Bloom 后处理栈 | 项目已在引擎内，直接启用 |
| MPS 三滤镜串联 | 滤镜现成、各段参数可调、纹理接力不回 CPU | 自研渲染管线、学习组合原理 |

## Quick Start

前置条件：macOS + Xcode 的 Swift 工具链，机器支持 Metal。在实验目录下运行：

```bash
./bloom.sh           # 一条龙
```

真实输出（节选）：

```
…（程序标题与 Device 信息行省略）
原图光晕环亮度: 10 → Bloom 后: 54（亮点周围）
暗点同位置: 10（应仍接近背景 10）
✅ Bloom 验证通过：只有高光产生辉光
```

验证方法：在亮点外 17 像素处采样（读取该坐标一次像素值）"光晕环"——Bloom 后变亮；同位置的暗点光晕环保持背景值。正反两个断言（assert，程序自动检查结果是否符合预期并报告成败的语句）锁死语义。

核心实现三行（完整程序见 `bloom.swift`）：

```swift
threshold.encode(commandBuffer: cb, sourceTexture: scene, destinationTexture: bright)
blur.encode(commandBuffer: cb, sourceTexture: bright, destinationTexture: blurred)
add.encode(commandBuffer: cb, primaryTexture: scene, secondaryTexture: blurred, destinationTexture: final)
```

这段在做什么：三行都只是"登记"工作——把每段滤镜读哪张纹理、写哪张纹理记入同一条命令缓冲（command buffer，提交给 GPU 的指令队列），随后一次提交，GPU 按登记顺序执行。

## How It Works

三段滤镜的接力关系就是 Bloom 的全部机制。数据流与代码一一对应：

```
scene   → ThresholdToZero(0.3) → bright
bright  → GaussianBlur(8)      → blurred
scene + blurred → Add          → final
```

逐站语义：

1. **提取高光**：`ThresholdToZero(0.3)` 把亮度低于阈值（threshold，人为设定的亮度分界线）的像素清零；高于阈值的保留原值而非置满——高光的强度信息保留，晕开后的辉光才有明暗层次。
2. **晕开**：`GaussianBlur(8)` 用高斯模糊（按正态分布权重对邻域像素取加权平均）把点状高光抹成光斑，sigma（模糊强度参数，数值越大晕得越开）取 8 决定晕开半径。
3. **叠回**：`Add` 把光斑与原图逐像素相加，高光周围被额外加亮，超过显示上限就成为过曝（亮度超出可显示范围，一片死白）的白斑，即"发光感"。

为什么三段能无缝接力：三行 `encode` 登记进同一条命令缓冲，GPU 按序执行——前一段写完 `bright`，下一段才去读它，CPU 不需要在中间等待或搬运数据。你在输出里看到的 `10 → 54` 正是 `Add` 把晕开的光斑加到亮点周围的结果；暗点周围没有高光可晕，读数 `10` 与背景值一致。

## Pitfalls & Q&A

**断言采样不到辉光？** 现象：光晕环采样点的读数与背景无异，断言失败。原因：采样距离超出光斑的扩散范围，sigma=8 的辉光在更远处已衰减为零。解法：采样距离要落在模糊半径内——本实验取 17 像素，该处仍有明确响应。

**叠加后高光一片死白、层次全无？** 现象：`Add` 之后亮区变成纯白块。原因：8-bit 纹理（每通道 8 位、上限 255）相加超过上限即截断。解法：学习阶段可接受；专业做法是 HDR（高动态范围，用浮点纹理保存超过 1.0 的亮度）管线加色调映射（把高动态范围压缩回显示区间），截断前先保留层次。

**中间纹理需要手动释放吗？** 每段一张纹理，用完可复用池化（预先建好、循环取用，避免反复分配显存）；同一命令缓冲内纹理的生命期由 GPU 按序执行保证——最后一段读完，纹理才不再被引用。

**为什么正反都要断言？** 只测"亮点变亮"不够：若阈值失效、暗点也漏进辉光，单侧断言照样通过。"亮点环变亮"与"暗点环不变"同时成立，才能锁死"只有高光产生辉光"的语义。
