# 09 · 打砖块 Breakout：第一个 CPU 状态机 + GPU 渲染的游戏

> 拍、球、72 块砖、3 条命——游戏逻辑全部跑在 CPU，画面交给 Metal 实例化渲染；
> 两条无人值守验收断言（自动 AI 通关 + 空闲拍丢命）让"游戏能玩"变成可重复执行的命令。
> 读完本篇你能掌握游戏主循环、AABB 碰撞、子步进防隧穿与游戏状态机的标准搭法。

## Background

打砖块（Breakout）1976 年由雅达利推出的街机经典（工程原型出自后来与乔布斯创立苹果的沃兹尼亚克之手）。对学习者而言，它是从"画面演示"迈向"真正的游戏"的第一步：状态机、碰撞、生命与得分，一个都不少。

实现时最先撞上的两堵墙：一是渲染——72 块砖颜色各异，逐个提交绘制调用会拖垮帧率，实例化渲染（instance rendering，一次调用画出全部砖块）是标准解法。

二是物理——球速到 500 px/s 时每帧位移 8 像素，薄薄的球拍会被"隧穿"（tunneling，两帧位置跨过薄物体导致碰撞漏检），需要把每帧拆成多个子步积分。

CPU 管逻辑、GPU 管画面的分工在这里成形：状态机与碰撞检测是天然的串行逻辑，GPU 只负责把几百个矩形一次画完。

## What

打砖块是一个最小的完整游戏状态机：serving（球粘拍待发射）→ playing（物理与碰撞）→ win / gameover（终态），由玩家输入与碰撞事件驱动流转。

可以把球拍想象成"用整只手掌接落下的网球"：手掌中心接球球会笔直弹回，用手掌边缘接球球会斜着飞出——命中位置决定反弹角。但和真实网球不同的是，这里的反弹是瞬时重定向（速度大小不变、只转方向），没有任何动量传递的弹性形变过程。

## When to Use

- **游戏开发入门**：状态机 + 碰撞 + 实例化渲染，是 2D 游戏的最小完整拼图
- **物理碰撞的练手场**：圆 vs AABB（轴对齐包围盒）是最易写的碰撞对，子步进防隧穿思路通用于所有实时物理
- **验收驱动开发的范例**：用无人值守 AI 替玩家跑通关流程，把"能玩"变成回归测试

何时不用：需要旋转物体或复杂形状的碰撞时，圆 vs AABB 不再够用，应升级到 SAT（分离轴定理）或物理引擎。

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| SpriteKit 等游戏框架 | 物理引擎自带；黑盒行为难微调 | 快速原型 |
| Canvas/DOM 逐矩形绘制 | 代码直白；几十个对象后帧率吃紧 | 极小规模 |
| **Metal 实例化渲染 + CPU 物理** | 一次绘制调用画完全部砖块，物理完全可控 | 本实验：数百对象的实时 2D 游戏 |

## Quick Start

前置条件：装好 Xcode Command Line Tools（`xcode-select --install`）；Metal（Apple 的 GPU 编程框架，Swift 可直接调用）为系统自带。

```bash
./breakout.sh                 # 一条龙：build → observe → clean
./breakout.sh observe         # 鼠标控拍 · 点击发射 · R 重开
./breakout.sh test            # 无人值守两条验收断言（通关 AI + 丢命状态机）
./breakout.sh export out.png  # 离屏导出开局画面
```

真实输出（`./breakout.sh test`，退出码 0=通过）：

```
=====> [test] 无人值守两条验收断言（通关 + 丢命状态机）
断言一（自动追踪通关，档位 5）：WIN · 用时 33341 帧 · 剩余砖 0 · 得分 72
✅ 通过：砖全清进入 WIN
断言二（空闲拍丢命，档位 8）：终态 GAMEOVER · 丢命 3 次 · 剩余生命 0
✅ 通过：恰丢 3 命进入 GAMEOVER
✅ 验收全部通过
```

- 观察要点：72 块六色砖、白色球拍、金色球；点击发射后按命中位置反弹——拍边缘接球斜飞、中心接球笔直上行；砖块清空后标题栏出现 WIN，按 R 重开且球速升一档
- 验证方法：`test` 两条断言可无限次重复执行（固定种子、结果确定）；通关断言把球速档拉到 5、空闲断言拉到 8，高速下的子步进防隧穿同时被覆盖
- 诚实预期：自动 AI 通关需要约 33000 帧（约 556 秒模拟时间，无渲染瞬时完成）；人工游玩时球速随得分递增，档位只影响重开后的初始速度

## How It Works

**游戏主循环与状态机。** 每帧做三件事：读输入（鼠标位置）、以固定 1/60 秒步进物理、重建实例缓冲并绘制。状态流转由事件驱动——发射点击把 serving 切到 playing；球落底扣命，命尽进 gameover；砖块清零进 win。

**碰撞：圆 vs AABB 与最小穿透轴。** 球对每块砖做"最近点"检测：把球心钳制到矩形范围内取最近点，距离小于半径即命中。反弹方向取穿透最浅的轴（|dx| 与 |dy| 谁大翻谁），这是圆 vs AABB 的标准最小代价写法：

```metal
// Swift 侧
let cx = max(b.x, min(ballPos.x, b.x + b.w))
let cy = max(b.y, min(ballPos.y, b.y + b.h))
let dx = ballPos.x - cx, dy = ballPos.y - cy
if dx * dx + dy * dy <= 49 { /* 命中：按 |dx| vs |dy| 反射 */ }
```

**子步进防隧穿。** 每帧的 1/60 秒再拆成 4 个子步：球速档 8 时约 520 px/s，每子步位移 2.2 像素，远小于拍高 14 像素——隧穿在物理上不可能发生。若不拆步，整帧位移 8.7 像素已接近拍高，漏检只是时间问题。

**实例化渲染：一次调用画 72 块砖。** 每个实例是一个 32 字节的结构（中心、半尺寸、颜色），CPU 每帧把存活砖块 + 拍 + 球打包写入一个缓冲；顶点着色器按 `instance_id` 取实例、把单元四边形平移缩放到目标位置。砖与球用两个渲染管线区分外观——砖是圆角矩形，球是片元里按离中心距离着色的圆。

**抖动与死循环。** 开发时实测到两种卡死：球以近水平角度在两墙间 forever 弹；以及自动追踪 AI 让命中点恒居拍心、球笔直上下永不偏航。解法是每次砖块与拍面反弹后叠加一个固定种子的小角度抖动（±4.3°）——既是游戏性的"扑朔迷离"，也是自动验收能收敛的前提。

## Pitfalls & Q&A

- **球被围进"顶墙 + 残砖"的死口袋**：现象是球在小空间里永远弹、不再破坏新砖。原因：砖块间隙只有 4 像素、球径 14 像素，掉进封闭空腔后无处可去。解法：砖块反弹叠加小角度抖动，让球沿口袋壁"磨"出新出口——每次磨蹭都会再破一块砖。
- **自动追踪 AI 永远笔直上行**：现象是通关断言卡在 7 分。原因：拍每帧精确对齐球的 x 坐标，命中偏移恒为 0，反弹恒为竖直。解法：拍面反弹后叠加抖动（同上），球会横向游走出列。
- **MSL 报 redefinition / undeclared identifier 'discard'**：现象是运行时编译着色器失败。原因：顶点与片元源码拼接后结构体重复定义；MSL 的片元丢弃语义是 `discard_fragment()` 而非 GLSL 的 `discard`。解法：结构体只在顶点源里定义一次；丢弃用 `discard_fragment()`。
- **Swift 属性初始化引用了另一个属性**：现象是编译报 `cannot use instance member 'paddleY' within property initializer`。原因：属性默认值按声明顺序求值，此时 self 尚不可用。解法：给字面量初值，真正依赖关系的值放到 init 或首个使用处赋值。

**Q：为什么物理放 CPU、渲染放 GPU，而不是全 GPU？**
碰撞检测是串行事件链（砖块存活状态相互影响、命中顺序不可并行），放 GPU 反而要为同步付出代价；实例数据每帧只有约 2 KB，回传成本可忽略。分工原则：串行逻辑归 CPU，大规模重复归 GPU。

**Q：反弹角为什么由拍上的命中位置决定，而不是镜面反射？**
镜面反射会让玩家只能被动接球；命中位置控角给了玩家"瞄准"的操作深度——这是打砖块五十年来手感的核心。拍边缘以约 60° 弹出，直攻边角砖。

**Q：两条验收断言为什么这样设计？**
通关断言用"每帧对齐球心"的完美拍验证游戏可被打通（碰撞、计分、状态流转全链路）；空闲断言用完全不动的拍验证丢命计数与终态。一个测"能赢"，一个测"会输"，合起来覆盖主状态机的全部转移。
